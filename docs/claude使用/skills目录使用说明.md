# skills/ 目录使用说明

> 📚 **官方文档**：[Claude Code Skills（Agent Skills）](https://code.claude.com/docs/en/skills)

## 什么是 skills/

`skills/` 目录用于存放**可重用的技能**。每个技能是一个包含 `SKILL.md` 的目录，通过 `/技能名` 调用，或由 Claude 根据 description 判断相关性后自动使用。

> **通俗理解**：就像给 Claude 定义"技能包"或"工作流程模板"。每个技能是一个完整的多步骤任务流程，比如"代码审查流程"、"部署流程"等。

## 文件位置

```
项目/.claude/skills/<name>/SKILL.md    # 项目级（团队共享）
~/.claude/skills/<name>/SKILL.md       # 用户级（个人全局）
```

技能名称就是目录名。

## 目录结构

```
.claude/skills/
├── review/
│   └── SKILL.md          # 代码审查技能
├── test/
│   └── SKILL.md          # 测试技能
└── deploy/
    ├── SKILL.md          # 部署技能
    └── checklist.md      # 可选：辅助文件
```

技能目录中除了必需的 `SKILL.md`，还可以放辅助文件（参考文档、模板、配置等），在 SKILL.md 中用相对路径引用它们。

## 为什么需要 skills/

### 问题场景

有些任务复杂且重复，每次都要详细说明：
- 代码审查：检查风格、查找 bug、验证测试、检查文档...
- 部署流程：测试、构建、上传、重启、验证...
- 文档生成：分析代码、提取接口、生成文档、检查格式...

### 解决方案

通过技能定义，这些任务只需一行：
- `/review` — 执行代码审查流程
- `/deploy` — 执行部署流程
- `/docs` — 生成文档

## 与 commands/ 的区别

| 特性 | skills/ | commands/ |
|------|---------|-----------|
| 目录结构 | `<name>/SKILL.md` | `*.md` 单文件 |
| 支持文件 | 可包含辅助文件 | 不支持 |
| 适用场景 | 复杂技能、多步骤流程 | 简单命令 |
| 触发方式 | `/名称` 调用 + Claude 自动选用 | 仅 `/名称` 调用 |

> **通俗理解**：
> - **commands** 是"快捷方式"：一键完成简单任务
> - **skills** 是"工作流"：复杂的多步骤任务流程，还能附带参考资料

## 文件格式

### 基本结构

````markdown
---
name: review
description: 审查代码变更。当用户请求代码审查、检查 PR 质量时使用
---

# 代码审查

## 执行步骤

1. 第一步
2. 第二步
3. 第三步

## 输出格式

<!-- 结果应该怎样呈现 -->
````

### Frontmatter 字段

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| name | string | ✅ | 技能唯一标识（小写连字符，与目录名一致） |
| description | string | ✅ | 技能的功能描述和使用时机。**Claude 依据它判断何时自动使用该技能** |
| allowed-tools | string | ❌ | 限制技能执行时可使用的工具 |

> **关键**：description 是技能能否被正确触发的核心。要写清楚"做什么"和"什么时候用"，两者兼备自动触发才准确。

## 如何使用技能

### 1. 斜杠命令调用

```
/review
/test
/deploy 修复登录页
```

斜杠调用时输入的参数会传递给技能，在 SKILL.md 中用 `$ARGUMENTS` 接收：

```markdown
请审查以下范围的代码：$ARGUMENTS
```

### 2. 自动触发

Claude 会根据当前任务与各技能的 description 匹配，需要时自动加载技能内容。例如设置了代码审查技能后，用户说"帮我审查这段代码"，Claude 可能自动应用该技能的流程。

## 技能示例

### 1. 代码审查技能

````markdown
---
name: review
description: 审查代码变更的质量与安全性。当用户请求代码审查、检查提交或 PR 时使用
---

# 代码审查

审查范围：$ARGUMENTS（未指定则审查当前未提交的变更）

## 审查步骤

### 1. 变更概览
- 查看所有变更的文件
- 理解变更的目的
- 确认变更范围

### 2. 代码质量
- 检查代码风格
- 查找潜在 bug
- 验证错误处理

### 3. 最佳实践
- 检查安全性问题
- 验证性能考虑
- 确认可维护性

### 4. 测试
- 检查测试覆盖
- 验证测试质量

### 5. 文档
- 确认文档更新
- 检查注释质量

## 输出格式

### ✅ 通过项
- 项目 1
- 项目 2

### ⚠️ 建议改进
- 问题 1
- 问题 2

### ❌ 必须修复
- 严重问题 1
- 严重问题 2
````

### 2. 测试技能

````markdown
---
name: test
description: 运行测试并修复失败用例。当用户要求跑测试、修复测试失败时使用
---

# 测试执行

## 步骤

### 1. 运行测试
- 运行完整测试套件
- 收集测试结果

### 2. 分析失败
- 定位失败原因
- 分类失败类型

### 3. 修复问题
- 修复代码
- 更新测试

### 4. 验证修复
- 重新运行测试
- 确认全部通过

## 处理逻辑
- 单个测试失败：修复该测试
- 多个测试失败：分析共同原因
- 超时失败：检查异步逻辑
````

### 3. 部署技能

````markdown
---
name: deploy
description: 执行应用部署流程。当用户要求部署、发版时使用
---

# 部署流程

## 前置检查
- [ ] 所有测试通过
- [ ] 代码已合并到主分支
- [ ] 环境变量已配置

## 部署步骤
1. 拉取最新代码
2. 安装依赖
3. 运行构建
4. 执行数据库迁移
5. 重启服务
6. 运行冒烟测试

## 回滚计划
如果部署失败：
1. 停止新版本
2. 恢复到上一版本
3. 检查错误日志
````

### 4. 文档生成技能

````markdown
---
name: docs
description: 根据代码生成 API 文档。当用户要求生成或更新接口文档时使用
---

# API 文档生成

## 内容

### 1. 概览
- API 用途
- 认证方式
- 基础 URL

### 2. 端点列表
- 方法 + 路径
- 描述
- 参数
- 响应格式

### 3. 示例
- 请求示例
- 响应示例
- 错误处理

## 输出格式
生成 Markdown 格式的文档，保存到 `docs/api.md`
````

## 命名规范

### 技能目录命名

使用小写字母和连字符：

```
# ✅ 好的命名
code-review/
run-tests/
deploy-prod/

# ❌ 不好的命名
CodeReview/
runTests/
deploy_prod/
```

### 技能文件

每个技能目录下必须有一个 `SKILL.md` 文件：

```
skills/
├── my-skill/
│   └── SKILL.md      # 必需文件
├── another-skill/
│   ├── SKILL.md      # 必需文件
│   └── config.json   # 可选辅助文件
```

## 最佳实践

### 1. 单一职责

每个技能只做一件事：

```
# ✅ 好的设计
review/     # 只做代码审查
test/       # 只做测试
deploy/     # 只做部署

# ❌ 不好的设计
everything/  # 什么都能做
```

### 2. 写好 description

description 决定技能能否被正确触发，要同时说明"做什么"和"什么时候用"：

```markdown
---
description: 审查代码质量和安全性。当用户请求代码审查时使用    # ✅ 清晰
description: 做一些审查工作                                  # ❌ 模糊
---
```

### 3. 参数处理

明确说明需要的参数：

````markdown
## 参数
- `--scope`：审查范围（all/changed/file）
- `--strict`：严格模式（true/false）

## 使用示例
/review --scope=changed --strict=true
````

### 4. 错误处理

包含错误情况的说明：

````markdown
## 错误处理
- 如果找不到文件，提示用户检查路径
- 如果测试失败，提供修复建议
- 如果构建错误，显示完整错误信息
````

### 5. 复杂技能附带辅助文件

流程复杂时，把检查清单、模板等拆成辅助文件放在技能目录中，在 SKILL.md 里引用，保持主文件精炼。

## 选择建议

### 使用 skills/ 的场景

- 复杂的多步骤流程
- 需要配置或辅助文件
- 需要独立的文档说明
- 团队共享的复杂功能

### 使用 commands/ 的场景

- 简单的单功能命令
- 不需要辅助文件
- 快速定义和修改
- 频繁使用的操作

## 注意事项

1. **技能名称不能与内置命令冲突**
2. **description 要有辨识度**，避免多个技能描述雷同导致触发混乱
3. **复杂技能考虑拆分**或使用辅助文件
4. **项目级技能文件应该提交到代码库**
5. **更新技能时同步更新文档**

## 工作流程

### 创建新技能

```
1. 确定技能需求
   ↓
2. 创建技能目录（如 .claude/skills/review/）
   ↓
3. 编写 SKILL.md（含 name 和 description）
   ↓
4. 测试技能功能（/技能名）
   ↓
5. 提交到代码库
```

### 更新技能

```
1. 修改 SKILL.md
   ↓
2. 调整 description（如需要）
   ↓
3. 测试变更
   ↓
4. 提交更新
```

## 常见问题

### Q：技能和代理（agents）有什么区别？

**A**：技能是可重用的工作流程，共享主会话上下文；代理是独立的子会话，有独立的系统提示和工具限制。

### Q：技能修改后需要重启吗？

**A**：不需要。技能修改后立即生效。

### Q：技能为什么没有被自动触发？

**A**：自动触发基于 description 匹配。检查 description 是否准确描述了当前任务的类型和关键词，必要时直接用 `/技能名` 手动调用。

### Q：如何测试技能是否工作？

**A**：直接使用 `/技能名` 测试，观察输出是否符合预期。

### Q：技能文件应该提交到代码库吗？

**A**：项目级技能应该提交，让团队共享一致的流程；用户级技能保存在本地。
