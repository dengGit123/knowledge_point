# output-styles/ 目录使用说明

> 📚 **官方文档**：[Claude Code Output Styles](https://code.claude.com/docs/en/output-styles)

## 什么是 output-styles/

`output-styles/` 目录用于存放**自定义输出风格文件**，控制 Claude Code 的响应方式、输出格式和详细程度。

> **通俗理解**：就像给 Claude 设置"说话风格模板"，可以让它在不同场景下用不同方式回应——有时简洁直接，有时详细教学，有时像审计报告一样严谨。

## 工作机制

- 输出风格会**替换系统提示中关于输出格式的部分**（项目规则 CLAUDE.md 仍然生效）
- 通过 `/output-style` 命令切换，或修改 settings.json 中的 `outputStyle` 字段
- **同一时间只有一个风格生效**，直到再次切换
- 切换是持久的，会保留到后续会话

```bash
# 查看并列出可用风格
/output-style

# 直接切换到指定风格
/output-style concise

# 恢复默认风格
/output-style default
```

## 文件位置

```
项目/.claude/output-styles/*.md    # 项目级（团队共享）
~/.claude/output-styles/*.md       # 用户级（个人全局）
```

## 为什么需要 output-styles/

### 问题场景

在不同场景下，需要不同的输出风格：
- 快速问答时：需要简洁明了的回答
- 学习新知识时：需要循序渐进的教学风格
- 代码审查时：需要严谨的清单格式
- 问题排查时：需要结构化的调试信息

### 解决方案

通过输出风格文件，可以：
- 预定义多种响应模板
- 按场景切换，保持输出格式一致
- 提高沟通效率

## 文件格式

输出风格文件就是一份 Markdown 指令文档，描述 Claude 应该如何组织输出：

````markdown
# 简洁输出风格

请使用简洁的风格回应：
- 直接给出答案
- 避免冗余说明
- 使用列表形式
- 省略背景信息
````

## 常用风格详解

### 1. 简洁风格 (concise.md)

适用于快速问答、命令执行结果等场景。

`````markdown
# 输出规范

## 原则
- 只输出结果，不解释
- 使用最少的文字
- 省略所有客套话
- 直接给出核心信息

## 示例

用户: 简洁地说如何安装 Vue

回复:
1. `npm create vue@latest`
2. `cd 项目名`
3. `npm install`
4. `npm run dev`
`````

### 2. 详细风格 (detailed.md)

适用于复杂问题、方案设计等需要深入说明的场景。

`````markdown
# 输出规范

## 原则
- 详细解释每个步骤
- 提供背景信息
- 说明决策原因
- 包含相关资源链接
- 考虑边界情况

## 结构模板
1. 背景说明（为什么这样做）
2. 分析过程（如何思考）
3. 执行步骤（具体操作）
4. 结果验证（如何检查）
5. 后续建议（还有什么需要注意）

## 示例

用户: 详细解释如何优化 Vue 应用性能

回复:
### 背景
Vue 性能优化主要是减少不必要的渲染和减小产物体积...

### 优化策略
1. 使用 `v-memo` 跳过未变化的子树渲染
   - 原理: 缓存 vnode，依赖不变时直接复用
   - 适用场景: 大列表中的部分项频繁更新
   ...
`````

### 3. 教学风格 (teaching.md)

适用于学习新概念、讲解技术原理等场景。

`````markdown
# 输出规范

## 原则
- 像老师一样循序渐进
- 使用通俗的类比
- 鼓励思考和提问
- 提供练习建议

## 结构模板
### 问题引入
从一个实际问题开始

### 概念解释
用通俗语言解释核心概念

### 类比说明
使用生活中的类比帮助理解

### 示例演示
提供具体代码示例

### 练习建议
给出练习方向

## 示例

用户: 教学风格讲解什么是闭包

回复:
### 从一个问题开始
想象你需要一个计数器，每次调用都增加...

### 什么是闭包
闭包就像一个"背包"...
`````

### 4. 审计风格 (audit.md)

适用于代码审查、安全检查等需要清单式输出的场景。

`````markdown
# 输出规范

## 原则
- 客观记录，不带感情色彩
- 使用详细清单
- 问题按严重程度分类
- 提供风险评估

## 格式模板
### ✅ 正常项
- 项目 1

### ⚠️ 警告项
- 项目 1: 问题描述，可能影响

### ❌ 错误项
- 项目 1: 问题描述，严重程度，修复建议

## 示例

用户: 审计风格检查这段代码

回复:
### ✅ 通过项
- 变量命名规范
- 错误处理完整

### ⚠️ 建议改进
- 缺少类型注解: 可能导致维护困难
- 未使用 const: 可能被意外修改

### ❌ 必须修复
- SQL 注入风险: 用户输入未转义，严重安全漏洞
`````

### 5. 报告风格 (report.md)

适用于总结汇报、项目文档等正式场景。

`````markdown
# 输出规范

## 结构模板

### 执行摘要
简要说明主要发现和结论（1-2 段）

### 详细分析
1. 问题 1
   - 描述
   - 影响
   - 建议

### 总结
整体评估和后续行动

## 示例

用户: 生成一份代码质量报告

回复:
### 执行摘要
本次审查覆盖 15 个文件，发现 3 个严重问题，5 个建议改进项...

### 详细发现
1. 安全问题
   - 描述: 存在 XSS 漏洞
   - 影响: 用户数据可能泄露
   - 建议: 使用输入清理库过滤用户输入
`````

### 6. 调试风格 (debug.md)

适用于问题排查、错误诊断等场景。

```````markdown
# 输出规范

## 原则
- 显示完整上下文
- 列出所有可能原因
- 提供诊断步骤
- 给出修复方案

## 格式模板
### 问题分析
```
错误信息: xxx
发生位置: xxx
相关代码: xxx
```

### 可能原因
1. 原因 1: 说明
2. 原因 2: 说明

### 诊断步骤
1. 检查 xxx
2. 验证 xxx

### 修复方案

## 示例

用户: 调试风格分析这个错误

回复:
### 问题分析
```
错误信息: TypeError: Cannot read properties of undefined (reading 'toLowerCase')
发生位置: src/components/UserCard.vue 第 23 行
相关代码: const name = user.name.toLowerCase()
```

### 可能原因
1. `user` 对象为 undefined（异步数据未返回时模板已执行）
2. 接口返回的数据结构变化，`user.name` 不存在

### 诊断步骤
1. 在第 23 行前打印 `console.log(user)`
2. 检查 API 返回的数据结构
3. 验证 props 是否正确传递

### 修复方案
```typescript
// 方案1: 可选链兜底
const name = user?.name?.toLowerCase() || '未知用户'

// 方案2: 在模板层加守卫
// <template>
//   <div v-if="user">{{ user.name.toLowerCase() }}</div>
//   <div v-else>加载中...</div>
// </template>
```
```````

## 最佳实践

### 1. 明确场景定位

每个风格对应特定使用场景，避免混淆：

```
✅ 好的设计
concise.md    → 快速问答
teaching.md   → 学习教学
audit.md      → 代码审查

❌ 不好的设计
style1.md     → 含义不明确
template.md   → 场景模糊
```

### 2. 使用一致的格式

同类输出使用统一格式，便于解析和理解。

### 3. 保持结构清晰

输出应该有清晰的组织结构，使用标题、列表、表格等。

### 4. 适当详细程度

根据场景调整详细程度：
- 快速问答: 简洁
- 教学场景: 详细
- 审计场景: 全面

### 5. 考虑机器可读性

如果需要自动化处理，考虑使用结构化格式（表格、代码块）。

## 工作流程

### 创建新输出风格

```
1. 确定使用场景
   ↓
2. 设计输出结构
   ↓
3. 编写风格文件（.claude/output-styles/xxx.md）
   ↓
4. /output-style xxx 切换测试
   ↓
5. 根据反馈调整
```

## 注意事项

1. **只影响输出方式**：输出风格不会覆盖 CLAUDE.md 中的项目规则，只影响 Claude 如何表达
2. **同一时间只有一个风格生效**：切换是持久的，记得在需要时切回 `default`
3. **风格文件应该提交到代码库**：团队共享统一的输出风格
4. **定期审查和更新**：根据团队反馈调整风格定义

## 常见问题

### Q：输出风格和项目规则有什么区别？

**A**：
- **项目规则 (CLAUDE.md)**：定义"做什么"，比如"使用 TypeScript 编写"
- **输出风格 (output-styles/)**：定义"怎么说"，比如"用列表格式输出"

### Q：可以同时使用多个输出风格吗？

**A**：不可以。同一时间只有一个风格生效，切换后覆盖之前的风格。

### Q：如何测试输出风格是否生效？

**A**：使用 `/output-style` 确认当前风格，然后提出一个典型问题，观察输出格式是否符合预期。

### Q：如何恢复默认？

**A**：执行 `/output-style default`。
