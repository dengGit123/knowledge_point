应用上线不是终点，是「**值班**」的开始。日志是应用的「黑匣子」，监控是应用的「体检仪」——出了问题，日志告诉你**发生了什么**，监控告诉你**什么时候快出问题**。这一篇配置好这两样，部署闭环才算完成。

大白话：没日志的应用出事就像「飞机没黑匣子」——坠机了都不知道为啥；没监控的应用像「从不体检的人」——查出问题已是晚期。部署的最后一课：**让应用可观测**。

### 二、日志落盘与轮转

#### 1. Spring Boot 默认行为

Spring Boot 默认只输出到**控制台**（stdout）。systemd 场景下控制台日志被收进 `journalctl`，但 journal 不适合长期保存和检索，**文件日志仍是标配**。

#### 2. 配置文件日志

```yaml
# application-prod.yml
logging:
  file:
    name: /var/log/myapp/app.log        # 日志文件位置（目录要存在且应用可写）
  level:
    root: INFO                           # 生产根级别 INFO
    com.myapp.mapper: DEBUG              # 只对特定包开 DEBUG 排查问题
  logback:
    rollingpolicy:
      file-name-pattern: /var/log/myapp/app.%d{yyyy-MM-dd}.%i.gz   # 按天+按大小滚动，历史压缩；按大小滚动必须保留 %i
      max-file-size: 50MB                # 单文件超过 50MB 切割
      max-history: 30                    # 只保留 30 天，自动删除更早的
      total-size-cap: 5GB                # 日志总量上限，防磁盘打满（需与 max-history 配合才生效）
```

> ⚠️ **注意：** 「磁盘被日志打满」是新手生产事故第一名——数据库、本机应用、SSH 全会因磁盘满而异常。`max-history` + `total-size-cap` 两个参数就是保险丝，**必配**。另外确认日志目录归属运行用户：`chown appuser:appuser /var/log/myapp`。

#### 3. 日志级别怎么选

| 级别 | 用途 | 生产建议 |
| --- | --- | --- |
| `ERROR` | 出错了但应用还活着 | 必须告警 |
| `WARN` | 可自动恢复的异常（重试成功等） | 关注趋势 |
| `INFO` | 关键业务动作（下单、支付） | 生产默认级别 |
| `DEBUG` | 详细过程数据 | 按包临时开，用完关 |
| `TRACE` | 最细粒度 | 生产禁用 |

线上临时调整级别不必重启（Spring Boot Actuator 的 `loggers` 端点，或配合配置中心），前提是 Actuator 安全暴露（见下文）。

### 三、Actuator：给应用装上体检仪

#### 1. 引入与最小配置

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
```

引入后自动获得 `/actuator/health` 端点。**默认只暴露 health 一个端点**，这是刻意的安全设计。

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics    # 按需暴露，不要写 "*"
  endpoint:
    health:
      show-details: never               # 不对外泄露组件细节（默认即 never）
```

#### 2. health 端点的价值

```bash
curl http://127.0.0.1:8080/actuator/health
# {"status":"UP"}

# 它不是摆设：内置 HealthIndicator 会真的去探测 DB、Redis、磁盘……
# 数据库挂了 → status 变 DOWN → 配合探活脚本/负载均衡可自动摘除
```

> ⚠️ **注意：** Actuator 端点**不要直接暴露公网**。`env`（泄露配置与密码）、`heapdump`（下载整个堆内存，密码全在里面）都是高危端点。正确姿势：只暴露 `health,info,metrics`，并绑定内网端口（`management.server.port`）或由 Nginx 做访问控制。

### 四、基础监控方案

#### 1. 最小可用：探活脚本 + 告警

没有专业监控栈时，一个 cron 探活也能兜底：

```bash
# /opt/myapp/health-check.sh 配合 crontab 每 1 分钟执行
#!/bin/bash
STATUS=$(curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8080/actuator/health)
if [ "$STATUS" != "200" ]; then
    # 发告警（企微/钉钉/邮件 webhook，此处以日志代替）
    echo "$(date) health check failed: $STATUS" >> /var/log/myapp/alert.log
fi
```

```bash
# crontab -e 添加（每分钟执行一次）
* * * * * /opt/myapp/health-check.sh
```

#### 2. 进阶：指标采集栈

| 组件 | 作用 |
| --- | --- |
| `micrometer-registry-prometheus` | 暴露 `/actuator/prometheus` 指标端点 |
| Prometheus | 定时抓取并存储指标（QPS、JVM 内存、GC、接口耗时） |
| Grafana | 可视化大盘 |
| Alertmanager | 阈值告警（错误率、内存水位、响应时间） |

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,prometheus     # 暴露指标端点给 Prometheus 抓取
```

> 💡 **提示：** 监控告警的核心原则：**告警必须可行动**。收到的每条告警都应该明确「谁、看到后、做什么」；让人麻木的告警（CPU 80% 每天报）不如没有。

### 五、日常运维速查

```bash
# 看实时日志
journalctl -u myapp -f
tail -f /var/log/myapp/app.log

# 找错误
grep ERROR /var/log/myapp/app.log | tail -20

# 磁盘水位（日志是头号嫌疑）
df -h

# JVM 内况（应用还在时）
jps -l                          # 找到进程 PID
jstat -gcutil PID 1000          # 每秒打印 GC 情况
jcmd PID GC.heap_info           # 堆配置与使用（JDK 9+；老的 jmap -heap 已移除）
jstack PID > stack.txt          # 线程栈（排查卡死必备）
```

> ⚠️ **注意：** OOM 时留存的堆快照（`-XX:HeapDumpPath` 指定的 `.hprof` 文件）用 **MAT**（Eclipse Memory Analyzer）或 VisualVM 分析，定位内存泄漏利器。快照文件通常与堆一样大，分析完记得清理，别让它占着磁盘。

### 六、注意事项汇总

| 类别 | 注意事项 |
| --- | --- |
| 🔴 轮转参数必配 | `max-history` + `total-size-cap`，日志打满磁盘是连环事故之源 |
| Actuator 别裸奔公网 | 只暴露 `health,info,metrics`；`env`/`heapdump` 高危 |
| ERROR 日志要告警 | 没人看的日志等于没记；接入 IM/邮件通知 |
| 日志目录权限 | 归属运行用户，否则应用启动即报文件创建失败 |
| 监控指标看趋势 | 单点数值意义有限，Grafana 曲线才能暴露「每天凌晨一次 Full GC」这类规律 |

### 七、总结

部署闭环的最后一块拼图是**可观测性**：日志落盘轮转（`logging` + 轮转保险丝）、健康检查（Actuator `health` 只暴露必需端点）、指标与告警（探活脚本起步，Prometheus + Grafana 进阶）。至此，从「买服务器」到「值班有底」的完整链路走通：**安全的服务器 → 匹配的 JDK → 干净的打包 → 可靠的守护 → 清晰的日志监控**——这就是 Java 部署的全貌。
