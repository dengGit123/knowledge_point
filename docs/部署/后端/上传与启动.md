### 一、概述

> 📖 [Spring Boot - 运行你的应用](https://docs.spring.io/spring-boot/reference/using/running-your-application.html) ｜ [OpenSSH scp 手册](https://man.openbsd.org/scp)

Jar 打好了，服务器也备好了，接下来是**运过去、跑起来**。这一篇覆盖：用什么命令上传、JVM 启动参数怎么给、第一次 `java -jar` 怎么验证、启动失败怎么排查。

大白话：上传是「**把货送到店里**」，启动是「**开业试营业**」——先手动跑一遍确认没问题，再交给 systemd 正式「注册营业」（下一篇的主题）。

### 二、上传 Jar 到服务器

#### 1. scp：简单直接

```bash
# 在本地执行：把 target 下的 Jar 传到服务器 /opt/myapp/
scp target/myapp-1.0.0.jar appuser@服务器IP:/opt/myapp/

# 指定私钥（未配免密时）
scp -i ~/.ssh/id_ed25519 target/myapp-1.0.0.jar appuser@服务器IP:/opt/myapp/
```

#### 2. rsync：重复部署的首选

```bash
# -a 保留属性 -z 压缩 -P 显示进度+支持断点续传
rsync -avzP target/myapp-1.0.0.jar appuser@服务器IP:/opt/myapp/
```

| 对比项 | scp | rsync |
| :---: | :--- | :--- |
| 传输内容 | 全量 | **只传差异部分**（大 Jar 更新快） |
| 断点续传 | ❌ | ✅（`--partial`） |
| 保留权限/时间戳 | 部分 | ✅ |
| 适用场景 | 偶尔传一次 | 日常反复部署 |

> 💡 **提示：** 生产部署建议**带版本号上传 + 软链接切换**：传 `myapp-1.0.0.jar`，然后 `ln -sfn /opt/myapp/myapp-1.0.0.jar /opt/myapp/app.jar`，systemd 永远指向固定的 `app.jar`。回滚 = 把软链接指回旧版本，一条命令的事。

#### 3. 上传后验证

```bash
# 在服务器上确认文件完整（大小与本地对比）
ls -lh /opt/myapp/
# 更严谨：本地和服务器各算一次 MD5 对比
md5 /path/to/myapp.jar          # 本地（macOS）
md5sum /opt/myapp/myapp.jar     # 服务器（Linux）
```

### 三、JVM 启动参数：生产必给的三类

直接 `java -jar app.jar` 能跑，但生产环境必须显式给参数——**内存边界**、**OOM 现场**、**运行环境**。

```bash
java -Xms1g -Xmx1g \
     -XX:+HeapDumpOnOutOfMemoryError \
     -XX:HeapDumpPath=/opt/myapp/dumps/ \
     -jar /opt/myapp/app.jar \
     --spring.profiles.active=prod
```

| 参数 | 含义 | 建议 |
| --- | --- | --- |
| `-Xms` / `-Xmx` | 初始堆 / 最大堆 | **设成一样**，避免运行期堆伸缩带来的停顿 |
| `-XX:+HeapDumpOnOutOfMemoryError` | OOM 时自动保存堆快照 | 「免费的保险」，OOM 后没有现场 = 排查无门 |
| `-XX:HeapDumpPath=...` | 堆快照保存路径 | 指到有空间的目录，避免默认写进工作目录 |
| `-jar app.jar` | 运行 Fat Jar | 固定写法 |
| `--key=value` | 覆盖 application.yml | 高优先级，适合临时改端口/Profile |

> 💡 **提示：** Java 9+ 默认垃圾收集器已是 **G1**，小内存应用不必再手动指定 `-XX:+UseG1GC`。内存给的公式参考：容器/机器内存的 50%~70% 给 `-Xmx`，**剩余留给元空间、线程栈、堆外内存**——1 核 2G 的机器 `-Xmx` 建议 1g 以内，防止被系统 OOM Killer 杀掉。

### 四、首次启动：先手动验证

不要一上来就配 systemd。先**前台跑一遍**，亲眼看日志：

```bash
# 切到专用用户
sudo su - appuser

# 前台启动（Ctrl + C 可停止）
java -Xms512m -Xmx512m -jar /opt/myapp/app.jar --spring.profiles.active=prod
```

看到的正常启动日志形如：


```bash
# ① 进程在

# ② 端口监听中

curl http://127.0.0.1:8080/actuator/health
# 返回 {"status":"UP"} 即正常
```

### 五、启动失败排查（三类高频问题）

#### 1. 端口被占用

```
日志特征：Web server failed to start. Port 8080 was already in use.
```

```bash
# 找出谁占了端口
ss -tlnp | grep 8080
# 杀掉旧进程（确认不是误伤）
kill 旧进程PID
```

#### 2. 内存不足

```
日志特征：Cannot allocate memory / java.lang.OutOfMemoryError
或进程直接消失（被系统 OOM Killer 杀死）
```

```bash
# 查系统内存
free -h
# 查是否被 OOM Killer 杀过（内核日志）
dmesg | grep -i "killed process"
# 处理：调小 -Xmx，或升级内存
```

#### 3. 连不上数据库

```
日志特征：Communications link failure / HikariPool-1 - Exception during pool initialization
```

```bash
# 在服务器上测试数据库连通性（最常被忽略：安全组没放行 3306）
telnet 数据库IP 3306
# 检查 Profile 是否激活对了：日志里搜 "The following profiles are active: prod"
```

### 六、注意事项汇总

| 类别 | 注意事项 |
| --- | --- |
| 🔴 手动启动只是验证 | 生产长期运行必须交给 systemd，别用 `nohup ... &` 凑合 |
| 堆内存留余量 | `-Xmx` ≈ 可用内存的 50%~70%，给堆外内存留活路 |
| OOM 现场保护 | `HeapDumpOnOutOfMemoryError` + 指定路径，出事才有据可查 |
| 版本化文件名 | `app-1.0.0.jar` + 软链接指向 `app.jar`，回滚只需改链接 |
| 先本机验证再开公网 | `curl 127.0.0.1` 通了再测外部访问，避免半成品暴露 |

### 七、总结

上传与启动环节：**rsync 传版本化 Jar → 显式 JVM 参数前台试跑 → 三项验证（进程/端口/健康检查）**。手动跑通只是及格线，进程的长期守护——崩溃自动拉起、开机自启、优雅停机——要交给下一篇的主角 systemd：[[systemd 进程守护]]。
