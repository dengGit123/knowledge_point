# 响应式图片

> 📖 官方文档：[MDN - Responsive images](https://developer.mozilla.org/zh-CN/docs/Web/HTML/Guides/Responsive_images) ｜ [WHATWG HTML 规范 - 选择图片源算法](https://html.spec.whatwg.org/multipage/images.html#selecting-an-image-source) ｜ [web.dev - 响应式图片](https://web.dev/learn/images/responsive-images)

---

### 一、概述

**响应式图片（Responsive Images）** 指根据用户的**设备特性**（屏幕宽度、像素密度、网络状况、格式支持）加载**最合适的那一张图**，而不是所有设备都下载同一张大图。

为什么需要它？两张账单：

- **流量账单**：一张 2000px 宽的原图约 500KB，而手机竖屏实际只需要 400px 宽（约 30KB）。给所有用户都发原图，手机用户多花了 **90% 以上的流量**。
- **清晰度账单**：在 2x 高分屏（Retina）上显示一张按 1x 设计的小图，会明显模糊——反过来在低端设备上发 3x 图，纯属浪费。

> 💡 **通俗理解**：响应式图片就像"点奶茶选杯型"——店员（浏览器）先看你的需求（屏幕多大、几分糖/什么网速），再决定给你中杯还是大杯（下载 400w 还是 1200w 的图），而不是不管三七二十一都上超大杯。

> ⚠️ **先分清两个问题**，整篇文档都围绕它们展开：
> 1. **分辨率切换**：同一张图，提供多个"尺寸版本"，按屏幕选——用 `srcset` + `sizes`；
> 2. **艺术指导**：不同设备用**构图不同**的图（如手机上显示裁剪后的特写）——用 `<picture>` + `media`。

### 二、核心问题：为什么 CSS 媒体查询救不了 `<img>`

页面布局可以用 CSS 媒体查询自适应，但图片有个根本矛盾：

```
浏览器的两阶段困境：

阶段① 解析 HTML，开始请求图片      ← 此刻 CSS 还没生效、布局还没算！
         │
         │  浏览器不知道：<img> 最终会显示多宽？
         │  （宽度取决于 CSS，而 CSS 可能还没下载）
         ▼
阶段② 布局完成，图片插入页面        ← 图早就按"瞎猜的宽度"下载完了
```

- 如果等 CSS 布局算完再下载图片，页面会白屏很久（**性能差**）；
- 如果立刻下载，浏览器只能瞎猜宽度（**浪费流量**）。

**响应式图片方案的精髓**：让 HTML 在请求发生前，就把"各个版本的图 + 显示宽度的计算规则"提前告诉浏览器——`srcset` 给候选列表，`sizes` 给宽度规则。浏览器在预解析阶段就能算出该下载哪张。

### 三、实现一：分辨率切换（srcset + sizes）

#### 1. 密度描述符（`x`）：按像素密度切换

最简单的场景：同一显示尺寸，为高分屏提供高清版本。`1x`、`2x` 指设备像素比（DPR）：

```html
<!-- 显示区域固定 400px 宽：
     1x 屏幕（DPR=1）用 400px 宽的图，2x 屏（DPR=2）用 800px 宽的图 -->
<img
  src="photo-400w.jpg"
  alt="风景照"
  srcset="photo-400w.jpg 1x, photo-800w.jpg 2x, photo-1200w.jpg 3x" />
```

> ⚠️ **注意：** 用了 `x` 描述符就**不要再写 `sizes`**。`x` 模式下浏览器只看 DPR 选图，`sizes` 会被忽略；而且同一 `srcset` 里 `x` 和 `w` 描述符**不能混用**（规范禁止）。

#### 2. 宽度描述符（`w`）+ `sizes`：按布局宽度切换（主流方案）

绝大多数图片宽度是**随视口变化**的，这时用 `w` 描述符声明每个文件的**真实像素宽度**，用 `sizes` 告诉浏览器"这个图最终会显示多宽"：

```html
<img
  src="photo-800w.jpg"
  alt="风景照"
  srcset="
    photo-400w.jpg   400w,
    photo-800w.jpg   800w,
    photo-1600w.jpg 1600w
  "
  sizes="(max-width: 600px) 480px, (max-width: 1024px) 50vw, 800px" />
```

两份声明的分工：

| 属性 | 回答的问题 | 写的是什么 |
|------|-----------|-----------|
| `srcset` | 有哪些候选？ | 每个候选文件的真实**像素宽度**（`w` 描述符），用于计算"哪张够用" |
| `sizes` | 会显示多宽？ | 一组**媒体条件 → 显示宽度**规则，近似布局占位（不是精确值） |

`sizes` 的解读（从上到下，第一个命中的条件生效）：

```text
sizes="(max-width: 600px) 480px, (max-width: 1024px) 50vw, 800px"
       └──── 条件 ────┘ └─值─┘  └───── 条件 ─────┘ └─值─┘  └─值─┘
       视口 ≤ 600px：   显示 480px  视口 ≤ 1024px：显示 50vw  其余情况：显示 800px
```

浏览器的实际决策（以 iPhone 视口 375px、DPR 3 为例）：

```
① 375 ≤ 600 命中第一个条件 → 槽位宽度 = 480px
② 目标像素 = 480 × 3(DPR) = 1440px
③ 各候选的等效密度 = 候选宽度 ÷ 槽位宽度：
     400w → 0.83x（不够）  800w → 1.67x（不够）  1600w → 3.33x ≥ 3x ✅
④ 结论：下载 1600w（首个"够用"的候选，再大就没必要了）
```

> 💡 **提示：** 浏览器还可能结合**网络状况**微调（弱网时倾向选小一号的），且会把已缓存的候选纳入决策——所以最终选择是"设备 + 网络 + 缓存"的综合结果，并非固定公式。

#### 3. `sizes` 的合法单位与默认值

| 写法 | 是否合法 | 说明 |
|------|:-------:|------|
| `480px` | ✅ | 绝对像素 |
| `50vw` | ✅ | 视口宽度的百分比 |
| `33em` | ✅ | em（相对当前字号），适合字号驱动的布局 |
| `calc(50vw - 32px)` | ✅ | calc 表达式 |
| `480rem`、`480pt` | ❌ | **不支持的单位**——整个 `sizes` 会被当作无效，浏览器按 `100vw` 兜底 |
| 不写 `sizes` | —— | 等效于 `100vw`：所有 `w` 描述符按"全屏宽"计算，**几乎必然下载过大图** |

> ⚠️ **注意：** `sizes` 写错单位比不写更隐蔽——浏览器静默回退到 `100vw`，不会报错。若你的图只占半屏，等于让用户多下载一倍的图。**只要用了 `w` 描述符，就认真写 `sizes`。**

#### 4. `sizes="auto"`：懒加载图片的新选择（渐进增强）

对 `loading="lazy"` 的图片，可用 `sizes="auto"` 让浏览器**布局完成后**按实际渲染宽度选图（解决懒加载图"尺寸未知"的老问题）：

```html
<!-- auto 写在最前，不支持的浏览器忽略它，回退到后面的显式规则 -->
<img
  src="gallery-800w.jpg"
  srcset="gallery-400w.jpg 400w, gallery-800w.jpg 800w, gallery-1600w.jpg 1600w"
  sizes="auto, (max-width: 600px) 480px, 800px"
  loading="lazy"
  decoding="async" />
```

> ⚠️ **注意（兼容性）：** `sizes="auto"` 需要 `loading="lazy"` 配合才生效；Chrome 126+（2024 标准化版本）、Firefox 133+ 支持，**Safari 尚未支持**。所以始终写成 `sizes="auto, ...回退规则..."` 的双保险形式，而不是只用 `auto`。

### 四、实现二：艺术指导（picture + source）

#### 1. 按屏幕条件切换构图（media）

手机竖屏适合"竖构图特写"，桌面宽屏适合"横构图全景"——这不是缩放能解决的，需要**不同的图**：

```html
<picture>
  <!-- 从上往下逐个匹配：手机竖屏用窄长裁剪版 -->
  <source
    media="(max-width: 600px)"
    srcset="mobile-crop-480w.jpg 480w, mobile-crop-800w.jpg 800w"
    sizes="92vw" />
  <!-- 平板用方形裁剪版 -->
  <source
    media="(max-width: 1024px)"
    srcset="tablet-crop-800w.jpg 800w"
    sizes="60vw" />
  <!-- 兜底：桌面/不支持 picture 的浏览器 -->
  <img
    src="desktop-wide-1600w.jpg"
    srcset="desktop-wide-1600w.jpg 1600w, desktop-wide-2400w.jpg 2400w"
    sizes="(max-width: 1440px) 70vw, 1200px"
    alt="海滩日落" />
</picture>
```

结构规则：

| 规则 | 说明 |
|------|------|
| `<img>` 是**必填兜底** | `<picture>` 里没有 `<img>` 标签是非法的；所有全局属性（`alt`、`loading` 等）都写在 `<img>` 上 |
| `<source>` 自上而下**逐个匹配** | 命中第一个 `media` 匹配的 `source` 后停止；都不匹配用 `<img>` |
| `media` 用**视口条件** | 语法同 CSS 媒体查询；建议按"从小到大"排列 |

#### 2. 按格式支持切换（type）：AVIF / WebP 降级链

现代格式（AVIF、WebP）体积比 JPEG 小 30%~50%，但并非所有浏览器都支持——`type` 让浏览器**不下载就能判断**是否支持：

```html
<picture>
  <!-- 顺序原则：新格式在前，旧格式兜底 -->
  <source type="image/avif" srcset="hero.avif" />
  <source type="image/webp" srcset="hero.webp" />
  <img src="hero.jpg" alt="产品主图" decoding="async" />
</picture>
```

工作方式：

```
浏览器逐个检查 <source>：
  ① type="image/avif" → 支持吗？支持 → 下载 hero.avif，结束 ✅
                      └→ 不支持 → 跳过（不发起请求！）
  ② type="image/webp" → 同上
  ③ <img> src="hero.jpg" → 兜底 ✅
```

> ⚠️ **注意（两个易错点）：**
> 1. **`type` 必须与文件真实格式一致**。如果把 AVIF 文件虚标成 `type="image/jpeg"`，不支持 AVIF 的浏览器（旧 Safari）会信以为真去下载，结果解不出图——页面直接裂图。
> 2. **浏览器只对"格式不支持"降级，不对"下载失败"降级**：如果 `hero.avif` 下载失败（404），浏览器**不会**回头去下 WebP 版本。格式降级链 ≠ 容灾方案。

#### 3. media 与 type 组合使用

两种维度可以叠加——同一 `media` 分组内，把该断点的所有格式变体**连续排列**：

```html
<picture>
  <!-- 断点①：手机（先试 AVIF，再 WebP，最后落到 img 的 JPEG） -->
  <source media="(max-width: 600px)" type="image/avif" srcset="m-480.avif 480w, m-800.avif 800w" sizes="92vw" />
  <source media="(max-width: 600px)" type="image/webp" srcset="m-480.webp 480w, m-800.webp 800w" sizes="92vw" />
  <!-- 断点②：平板及以上 -->
  <source media="(min-width: 601px)" type="image/avif" srcset="d-1200.avif 1200w, d-2000.avif 2000w" sizes="70vw" />
  <source media="(min-width: 601px)" type="image/webp" srcset="d-1200.webp 1200w, d-2000.webp 2000w" sizes="70vw" />
  <img src="d-1200.jpg" srcset="d-1200.jpg 1200w, d-2000.jpg 2000w" sizes="70vw" alt="示例" />
</picture>
```

> ⚠️ **注意：** 浏览器逐个评估 `<source>`：`media` 不匹配或 `type` 不支持就**跳过、继续看下一条**，第一条"条件匹配且格式支持"的生效。因此同一断点的格式变体建议**相邻排列**——若把平板断点的 source 插在两个手机格式变体中间，源码的可读性和维护性都会变差，容易在改动时错配断点与文件（并非浏览器机制报错，而是人犯错的高发区）。

### 五、实现三：CSS 与 JavaScript 方案

HTML 方案解决 `<img>`，但**背景图**、装饰图需要别的手段：

#### 1. CSS：媒体查询切换背景图

```css
/* ❌ 反模式：一个大背景图打天下 */
.hero {
  background-image: url("hero-2400w.jpg");  /* 手机也要下 2400w，纯浪费 */
}

/* ✅ 按视口切换不同尺寸的背景图 */
.hero {
  background-image: url("hero-600w.jpg");   /* 手机：小图 */
  background-size: cover;
}
@media (min-width: 601px) and (max-width: 1024px) {
  .hero {
    background-image: url("hero-1200w.jpg"); /* 平板：中图 */
  }
}
@media (min-width: 1025px) {
  .hero {
    background-image: url("hero-2400w.jpg"); /* 桌面：大图 */
  }
}
```

局限性：CSS 方案只能按**视口**切换，无法像 `srcset` 那样感知 **DPR 和网络**；且所有候选可能都被打包进 CSS 文件的引用里。内容型图片（有语义、需要 `alt`）请坚持用 `<img>`。

#### 2. `image-set()`：CSS 版的 srcset

CSS 分辨率切换的官方方案，语法与 `srcset` 的密度描述符类似：

```css
/* 双保险：不支持的浏览器用第一行，支持的用 image-set 覆盖 */
.hero {
  background-image: url("hero-1x.jpg");
  background-image: image-set(
    url("hero-1x.jpg") 1x,
    url("hero-2x.jpg") 2x
  );
}

/* 进阶：image-set 内还可按格式声明（较新，渐进增强） */
.hero-avif {
  background-image: image-set(
    url("hero.avif") type("image/avif"),
    url("hero-1x.jpg") 1x   /* 不支持 avif 的浏览器落到这行 */
  );
}
```

> 💡 **提示：** `image-set()` 已是 Baseline 广泛可用特性（所有现代浏览器支持，旧版 Safari 需 `-webkit-image-set()` 兜底）。浏览器会优先选择**自己支持的最优候选**（按声明顺序），所以把新格式写在前面、兼容格式殿后。

#### 3. JavaScript：动态方案的适用边界

```js
// 典型场景：艺术画廊/灯箱，需要根据容器实际宽度动态选择图片
function pickImage(containerWidth: number, dpr: number): string {
  const target = Math.ceil(containerWidth * dpr);  // 实际需要的像素宽
  const candidates = [
    { w: 480, url: '/img/480.jpg' },
    { w: 800, url: '/img/800.jpg' },
    { w: 1600, url: '/img/1600.jpg' },
  ];
  // 选第一个"够宽"的候选，都不够就取最大
  return candidates.find((c) => c.w >= target)?.url ?? candidates[candidates.length - 1].url;
}
```

什么时候才需要 JS？

- 图片来自**运行时接口**（用户上传的图，尺寸不可预知）；
- 需要**监听容器变化**动态换图（配合 `ResizeObserver`）；
- 图片 CDN 的**动态裁剪参数**拼接（`?width=` 这类，本质是服务端响应式）。

> ⚠️ **注意：** JS 方案无法参与浏览器的**预解析扫描**——加载器在 HTML 解析阶段就开始请求图片，JS 执行晚于这一步。首屏关键图用 JS 插入会显著推迟加载，能用 `srcset` 就别用 JS。

### 六、原理：浏览器的选择算法

把 `srcset` + `sizes` 的内部决策完整串一遍（简化自 [WHATWG 规范的"选择图片源"算法](https://html.spec.whatwg.org/multipage/images.html#selecting-an-image-source)）：

```
输入：srcset 候选列表 + sizes 规则 + 设备信息
        │
        ▼
① 解析 sizes：按当前视口宽度求出"槽位宽度"（px）
   未写 sizes → 槽位 = 100vw
        │
        ▼
② 计算目标像素：槽位宽度 × 设备像素比(DPR)
   例：480px × 2 = 960px
        │
        ▼
③ 遍历候选：每个候选的"有效像素密度 = 候选宽度 ÷ 槽位宽度"
   选出 ≥ 目标密度中"最接近"的那个（够用且最小）
        │
        ▼
④ 兜底修正：
   • 网络慢（如 2G/弱网）→ 倾向选择更小的候选
   • 候选已被缓存 → 优先复用缓存
   • 都不达标 → 选最大的候选
        │
        ▼
输出：确定下载哪个文件
（整个过程发生在 HTML 预解析阶段，早于 CSS 布局 —— 这正是 srcset 的价值）
```

两个重要推论：

1. **`w` 描述符本质上还是密度计算**：浏览器把"候选宽度 ÷ 槽位宽度"折算成等效密度再比较，所以 `sizes` 的准确性直接决定选图合理性；
2. **选择发生在布局之前**：浏览器只知道视口宽度和 DPR，**不知道容器真实宽度**（`sizes` 只是人工提供的近似值）——`sizes` 写得越贴近实际布局，选图越准。

### 七、实际应用场景

#### 场景一：电商商品主图（分辨率切换 + 现代格式）

商品图是典型的"同一构图、多尺寸版本"，流量敏感度最高：

```html
<picture>
  <source type="image/avif" srcset="shoe-400.avif 400w, shoe-800.avif 800w, shoe-1600.avif 1600w" sizes="(max-width: 600px) 92vw, 480px" />
  <source type="image/webp" srcset="shoe-400.webp 400w, shoe-800.webp 800w, shoe-1600.webp 1600w" sizes="(max-width: 600px) 92vw, 480px" />
  <img src="shoe-800.jpg" srcset="shoe-400.jpg 400w, shoe-800.jpg 800w, shoe-1600.jpg 1600w" sizes="(max-width: 600px) 92vw, 480px" alt="缓震跑步鞋" loading="lazy" decoding="async" />
</picture>
```

效果：2x 手机屏下载 800w 的 AVIF（约 40KB），而不是 1600w 的 JPEG（约 220KB），**单图节省 80%+**。

#### 场景二：新闻资讯头图（艺术指导）

头图需要按设备裁剪不同构图——手机看"人物特写"，桌面看"全景带背景"：

```html
<picture>
  <source media="(max-width: 600px)" srcset="story-mobile.jpg" sizes="92vw" />
  <img src="story-desktop.jpg" srcset="story-desktop-1200w.jpg 1200w, story-desktop-2000w.jpg 2000w" sizes="(max-width: 1440px) 70vw, 1100px" alt="记者在现场" fetchpriority="high" />
</picture>
```

头图是 **LCP（最大内容绘制）元素**，加 `fetchpriority="high"` 提升加载优先级，且**绝不要加** `loading="lazy"`。

#### 场景三：LCP 大图与普通内容的加载策略组合

```html
<!-- ✅ 首屏 LCP 图：高优先级 + 立即加载 -->
<img src="banner-1200w.jpg" srcset="banner-800w.jpg 800w, banner-1200w.jpg 1200w, banner-2000w.jpg 2000w" sizes="100vw" alt="横幅" fetchpriority="high" decoding="async" />

<!-- ✅ 首屏普通图：默认优先级即可 -->
<img src="logo.svg" alt="站点 Logo" width="120" height="40" />

<!-- ✅ 首屏以下图片：懒加载 + 异步解码 + 显式尺寸防跳动 -->
<img src="card-800w.jpg" srcset="card-400w.jpg 400w, card-800w.jpg 800w" sizes="(max-width: 600px) 92vw, 400px" alt="文章配图" loading="lazy" decoding="async" width="800" height="450" />
```

三档策略速查：

| 位置 | `loading` | `fetchpriority` | 附加 |
|------|-----------|-----------------|------|
| 首屏 LCP 图 | 默认（eager） | `high` | 尽量预加载（`<link rel="preload" as="image">`，配合 `imagesrcset`） |
| 首屏普通图 | 默认 | 默认 | 写 `width`/`height` 防 CLS |
| 首屏以下 | `lazy` | 默认 | `decoding="async"`；可用 `sizes="auto, ..."` |

#### 场景四：Vue 3 组件封装（组合式 API）

把响应式图片的样板代码封装成组件，业务侧只传素材前缀：

```vue
<script setup lang="ts">
interface Props {
  /** 图片路径前缀，如 /img/hero（不含尺寸后缀与扩展名） */
  base: string
  /** 候选宽度列表（需与构建产物一致） */
  widths?: number[]
  /** 传给 sizes 的规则 */
  sizes?: string
  alt: string
  lazy?: boolean
}

const props = withDefaults(defineProps<Props>(), {
  widths: () => [400, 800, 1600],
  sizes: '100vw',
  lazy: true,
})

// 拼出 srcset："xxx-400.jpg 400w, xxx-800.jpg 800w, ..."
const srcset = computed(() =>
  props.widths.map((w) => `${props.base}-${w}.jpg ${w}w`).join(', '),
)
const fallback = computed(() => `${props.base}-800.jpg`)
</script>

<template>
  <img
    :src="fallback"
    :srcset="srcset"
    :sizes="sizes"
    :alt="alt"
    :loading="lazy ? 'lazy' : 'eager'"
    :fetchpriority="lazy ? 'auto' : 'high'"
    decoding="async"
  />
</template>
```

```vue
<!-- 使用 -->
<RImg base="/img/hero" :widths="[800, 1200, 2000]" sizes="100vw" alt="横幅" :lazy="false" />
```

#### 场景五：构建工具自动生成多尺寸（Vite/图片服务）

手工导出 N 个尺寸不现实，生产环境两种主流方式：

```js
// vite.config.ts —— 用 vite-imagetools 插件在导入时自动生成 srcset
import { imagetools } from 'vite-imagetools'

export default defineConfig({
  plugins: [
    imagetools(),   // import hero from './hero.jpg?w=400;800;1600&format=avif;webp;jpg'
  ],
})
```

```js
// 组件中直接使用导入结果（不是 URL 字符串，而是元数据对象）
import hero from './hero.jpg?w=400;800;1600'

// hero.srcset  → "xxx-400w.jpg 400w, xxx-800w.jpg 800w, xxx-1600w.jpg 1600w"（现成的 srcset 属性值）
// hero.src     → 默认尺寸的 URL
// <img :src="hero.src" :srcset="hero.srcset" sizes="..." />
```

> 💡 **提示：** 更省事的路线是**图片 CDN / 云服务的动态裁剪**（如 OSS 的 `?x-oss-process=image/resize,w_800`），按 URL 参数实时生成尺寸与格式，再配合 `<picture>` 的 `type` 降级链使用——规模较大的站点基本都走这条路线，本地只存一份原图。

### 八、常见问题与注意事项

#### 1. 陷阱速查表

| 陷阱 | 后果 | 正确做法 |
|------|------|---------|
| 用了 `w` 描述符但不写 `sizes` | 按 `100vw` 算，几乎必下载超大图 | 每个 `w` 候选都配准确 `sizes` |
| `sizes` 写了 `rem`/`pt` 等单位 | 整个属性失效，静默回退 `100vw` | 只用 `px`、`vw`、`em`、`calc()` |
| 同一 `srcset` 混用 `x` 和 `w` | 规范禁止，行为未定义 | 二选一；响应布局场景用 `w` + `sizes` |
| `x` 描述符配了 `sizes` | `sizes` 被忽略 | `x` 模式不写 `sizes` |
| `<picture>` 里 `<source type>` 虚标格式 | 不支持的浏览器下载后解不出图，裂图 | `type` 必须与文件真实格式一致 |
| `fetchpriority="high"` 和 `loading="lazy"` 同用 | 语义矛盾，lazy 优先级必然低 | LCP 图要 `high` 就别 lazy；懒图不要 `high` |
| 首屏图加 `loading="lazy"` | LCP 变慢（要等接近视口才加载） | lazy 只用于首屏以下 |
| `<img>` 不写 `width`/`height` | 图片加载后撑开布局，CLS 劣化 | 显式写宽高（浏览器按比例占位） |
| `alt` 留空或写"图片" | 可访问性差 | 描述图片内容；纯装饰图用 `alt=""` |

#### 2. `width` / `height` 与响应式的配合

```html
<!-- 显式声明原始宽高比，浏览器加载前就预留空间，防止 CLS -->
<img
  src="photo-800w.jpg"
  srcset="photo-400w.jpg 400w, photo-800w.jpg 800w"
  sizes="(max-width: 600px) 92vw, 400px"
  width="800"
  height="450"
  alt="示例" />
```

```css
/* 实际显示宽度交给 CSS 控制宽高比不变 */
img.responsive {
  width: 100%;
  height: auto;      /* 关键：覆盖 height 属性，保持宽高比 */
}
```

> 💡 **提示：** 现代浏览器会根据 `width`/`height` 属性自动推导宽高比（aspect-ratio）用于占位，所以"写了会被 CSS 覆盖"完全不用担心——两个都要写。

#### 3. 常见问题

**Q1：`srcset` 选中的图，窗口缩放后会重新下载吗？**

基本不会。选择发生在**加载时**，加载完成后浏览器通常不会因视口变化主动换图（换图意味着重新下载，反而伤害体验）。需要"随容器换图"的少数场景（艺术画廊）才用 JS + `ResizeObserver`。

**Q2：`srcset` 里的候选会被全部下载吗？**

不会，浏览器只下载选中的一个（外加 `<picture>` 里未命中的 `source` 也不下载）。但要注意：用 DevTools 的"禁用缓存 + 刷新"测试时看到多张图被下载，往往是 `<picture>` 结构写错（如 `media`/`type` 全不匹配落到 `<img>`），而不是 `srcset` 的问题。

**Q3：已有图片 CDN，还需要 `srcset` 吗？**

需要，两者互补：CDN 解决"怎么生成多尺寸"（服务端），`srcset`/`sizes` 解决"浏览器怎么选"（客户端）。只配 CDN 不写响应式属性，浏览器依然只会请求 URL 里的那一个尺寸。

**Q4：SVG 需要响应式处理吗？**

不需要。SVG 是矢量格式，无限缩放不失真，天然"响应式"。给它配 `srcset` 反而多余。

**Q5：`loading="lazy"` 的触发时机？**

图片接近视口时才开始加载——Chrome 的启发式距离约为：快速网络下 1250px、慢速网络下 2500px（数值随网络状况动态调整，非固定承诺）。所以它适合"即将要看"的图，不适合首屏关键图。

### 九、与相关技术对比

| 方案 | 解决的问题 | 感知能力 | 适用 |
|------|-----------|---------|------|
| `srcset` + `sizes`（`w`） | 分辨率切换 | 视口、DPR、网络、缓存 | **默认首选**：内容图、随布局缩放的图 |
| `srcset`（`x`） | 分辨率切换 | 仅 DPR | 固定尺寸的图标、头像 |
| `<picture>` + `media` | 艺术指导 | 视口 | 需要不同构图/裁剪的场景 |
| `<picture>` + `type` | 格式降级 | 格式支持 | AVIF/WebP 降级链 |
| CSS 媒体查询切背景图 | 分辨率切换 | 仅视口 | 纯装饰背景图 |
| CSS `image-set()` | 分辨率切换 | DPR（+格式） | 背景图的 srcset 等价物 |
| JS 动态换图 | 一切（但要自己写） | 任意 | 运行时才知道尺寸/来源的图 |
| 图片 CDN 动态裁剪 | 生成多尺寸 | 无（服务端按参数） | 配合上述方案提供候选 |

决策口诀：**内容图用 `img` + `srcset`/`sizes`，换构图用 `picture` + `media`，降格式用 `picture` + `type`，背景图用 CSS，运行时才知道的用 JS。**

### 十、总结

| 知识点 | 核心要点 |
|--------|---------|
| 两大问题 | 分辨率切换（`srcset` + `sizes`）与艺术指导（`<picture>` + `media`） |
| `x` vs `w` | `x` 按 DPR 选（固定尺寸用）；`w` 按布局宽选（必须配 `sizes`），不可混用 |
| `sizes` 本质 | 人工告诉浏览器"图会显示多宽"的近似规则，单位限 `px`/`vw`/`em`/`calc` |
| `<picture>` 规则 | `source` 自上而下匹配，`<img>` 必填兜底；`type` 只对"不支持"降级，不对"下载失败"降级 |
| 选择时机 | HTML 预解析阶段（早于 CSS 布局），这是它优于 CSS/JS 方案的根本原因 |
| 加载三件套 | LCP 图 `fetchpriority="high"`；下方图 `loading="lazy"` + `decoding="async"`；都写 `width`/`height` 防 CLS |
| 生产配套 | 构建工具批量生成尺寸（vite-imagetools）或图片 CDN 动态裁剪 |

**记住三句话**：

1. **`srcset` 报清单（每张图多宽），`sizes` 报规则（会显示多宽），浏览器两相乘决定下载哪张——发生在布局之前。**
2. **换尺寸用 `srcset`，换构图用 `picture` + `media`，换格式用 `picture` + `type`，`img` 永远是兜底。**
3. **首屏 LCP 图要 `fetchpriority="high"` 绝不 lazy，下方图 `loading="lazy"` + `decoding="async"`，所有图写 `width`/`height` 防 CLS。**
