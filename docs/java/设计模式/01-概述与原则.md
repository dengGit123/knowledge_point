## 一、概述

### 1. 什么是设计模式

**设计模式（Design Pattern）** 是前人在长期的软件开发实践中，总结出来的、**可复用的**、针对特定问题的**面向对象设计经验**。

更具体地说：设计模式是一套被反复使用、多数人知晓的、经过分类的、代码设计经验的总结。它描述了在特定场景下，类与对象之间如何组织、如何交互，才能让系统更灵活、可维护、可扩展。

1994 年，四位作者（Erich Gamma、Richard Helm、Ralph Johnson、John Vlissides，合称 **GoF / 四人帮**）出版了《设计模式：可复用面向对象软件的基础》一书，归纳出了经典的 **23 种设计模式**，从此成为面向对象设计的「圣经」。

### 2. 通俗类比

可以把设计模式理解成**建筑工程的图纸模板**：

| 类比对象 | 设计模式中的对应 |
| --- | --- |
| 建筑图纸模板（如「三室一厅户型图」） | 设计模式（如「单例模式」「工厂模式」） |
| 遇到「需要建一栋只有一户的楼」 | 遇到「全局只需要一个实例」的问题 |
| 直接套用成熟的「独栋别墅图纸」 | 直接套用「单例模式」 |
| 照图纸施工，细节可微调 | 按模式骨架编码，具体实现可变化 |

> 💡 **提示：** 设计模式**不是发明出来的算法**，而是**总结出来的经验**。它的价值在于提供了一套「共同词汇」——你说「这里用个工厂模式」，团队成员就立刻明白你的设计意图，无需长篇大论。

### 3. 为什么要学习设计模式

| 收益 | 说明 |
| --- | --- |
| 提高代码可复用性 | 模式鼓励面向接口编程，减少重复 |
| 提高代码可扩展性 | 遵循开闭原则，新增功能不改老代码 |
| 提高代码可读性 | 模式是通用词汇，团队沟通成本降低 |
| 应对变化 | 把「变化的部分」和「稳定的部分」分离 |
| 面试加分项 | 几乎所有 Java 后端面试都会涉及设计模式 |

> ⚠️ **注意：** 设计模式不是银弹。**滥用模式 = 过度设计**，反而让系统更复杂。学习模式是为了「遇到合适的问题时知道有这个工具」，而不是「拿着锤子看什么都像钉子」。

## 二、三大分类与 23 种一览表

GoF 把 23 种模式按**目的**分成三大类：

| 分类 | 关注点 | 数量 | 通俗理解 |
| --- | --- | --- | --- |
| **创建型** | 「如何创建对象」 | 5 种 | 把对象的创建过程封装起来 |
| **结构型** | 「如何组合类与对象」 | 7 种 | 像搭积木一样组装结构 |
| **行为型** | 「对象之间如何协作」 | 11 种 | 定义对象间的职责分配与通信 |

## 三、设计模式的六大原则

设计模式背后的灵魂是**面向对象设计原则**。理解了原则，模式就是原则的具体落地。

### 原则总览

| 原则 | 英文缩写 | 一句话核心 | 通俗理解 |
| --- | --- | --- | --- |
| 单一职责原则 | SRP | 一个类只做一个事 | 一个人只干一份工作 |
| 开闭原则 | OCP | 对扩展开放，对修改关闭 | 加新功能不改老代码 |
| 里氏替换原则 | LSP | 子类必须能替换父类 | 儿子能干的活，老爹交给他没问题 |
| 依赖倒置原则 | DIP | 依赖抽象，不依赖具体 | 找对象看人品（抽象），不看具体长相 |
| 接口隔离原则 | ISP | 接口要小而专 | 接口不要塞一堆用不到的方法 |
| 迪米特法则 | LoD | 最少知识，只和直接朋友说话 | 别和陌生人说话 |

---

### 1. 单一职责原则（Single Responsibility Principle, SRP）

**定义：** 一个类应该只有一个引起它变化的原因，即一个类只负责一项职责。

```java
// ❌ 一个类承担多个职责：既管用户数据，又管用户数据库存储
class UserManager {
    void register(User u) { /* 注册逻辑 */ }
    void login(User u) { /* 登录逻辑 */ }
    void saveToDb(User u) { /* 数据库存取 */ }
    void sendEmail(User u) { /* 发邮件 */ }
}

// ✅ 拆分职责，各司其职
class UserService {           // 业务逻辑
    void register(User u) {}
    void login(User u) {}
}
class UserRepository {        // 数据访问
    void save(User u) {}
}
class EmailService {          // 邮件发送
    void send(User u) {}
}
```

**核心思想：** 如果一个类承担了多个职责，那么当其中一个职责变化时，可能会影响其他职责的正常运行。拆分后每个类只对自己的那部分变化负责。

---

### 2. 开闭原则（Open-Closed Principle, OCP）

**定义：** 软件实体（类、模块、函数等）应该**对扩展开放，对修改关闭**。即：增加新功能时，尽量新增代码，而不是修改老代码。

```java
// ❌ 每新增一种形状都要改 GraphicEditor，违背开闭原则
class GraphicEditor {
    void drawShape(Shape s) {
        if (s.type == 1) drawCircle();
        else if (s.type == 2) drawRectangle();
        // 新增三角形又得改这里……
    }
}

// ✅ 通过抽象 + 多态扩展，新增形状不改老代码
interface Shape { void draw(); }            // 抽象稳定
class Circle implements Shape { public void draw() { /* ... */ } }
class Rectangle implements Shape { public void draw() { /* ... */ } }
// 新增三角形：只新增一个类即可
class Triangle implements Shape { public void draw() { /* ... */ } }
```

**核心思想：** 把系统中**稳定的部分（抽象/接口）**和**变化的部分（具体实现）**分离。通过新增实现类来扩展功能，而不是修改已有的、经过测试的代码。

---

### 3. 里氏替换原则（Liskov Substitution Principle, LSP）

**定义：** 所有引用基类（父类）的地方必须能透明地使用其子类的对象。通俗讲：**子类对象替换父类对象后，程序行为不能出错**。

经典反例：正方形不应继承长方形（重写 setter 后破坏了长方形「长宽可独立变化」的契约）。

```java
class Rectangle { protected int w, h; /* getter/setter */ }
// ❌ Square 继承 Rectangle 后，改一边会同时改两边，破坏了父类的行为契约
class Square extends Rectangle {
    @Override public void setW(int w) { this.w = w; this.h = w; }
}
```

**核心思想：** 子类可以扩展父类的功能，但不能改变父类原有的功能（契约）。违反 LSP 会导致多态调用时出现意外行为。

---

### 4. 依赖倒置原则（Dependency Inversion Principle, DIP）

**定义：**
- 高层模块不应该依赖低层模块，二者都应该依赖其抽象。
- 抽象不应该依赖细节，细节应该依赖抽象。

通俗讲：**面向接口编程**，而不是面向实现编程。

```java
// ❌ 高层直接依赖低层具体类，强耦合
class UserService {
    private MySQLUserDao dao = new MySQLUserDao();  // 写死
}

// ✅ 高层与低层都依赖抽象（接口），通过注入解耦
interface UserDao { void save(User u); }
class MySQLUserDao implements UserDao { public void save(User u) {} }
class UserService {
    private final UserDao dao;                     // 依赖抽象
    public UserService(UserDao dao) { this.dao = dao; }  // 构造注入
}
```

**核心思想：** 抽象（接口）是稳定的，具体实现是易变的。依赖抽象后，更换实现类无需修改高层代码。

---

### 5. 接口隔离原则（Interface Segregation Principle, ISP）

**定义：** 客户端不应该被迫依赖它不使用的方法。即：**接口要小而专**，不要设计臃肿的接口。

```java
// ❌ 接口太胖，不需要的方法也被迫实现
interface Worker {
    void work();
    void eat();
    void sleep();
}
class Robot implements Worker {
    public void work() {}
    public void eat() { throw new UnsupportedOperationException(); } // 机器人不吃饭
    public void sleep() { throw new UnsupportedOperationException(); }
}

// ✅ 拆成多个细粒度接口
interface Workable { void work(); }
interface Eatable { void eat(); }
class Robot implements Workable { public void work() {} }
class Human implements Workable, Eatable { /* ... */ }
```

**核心思想：** 一个类对另一个类的依赖应该建立在**最小的接口**上。胖接口会把不相关的职责强加给实现者。

---

### 6. 迪米特法则（Law of Demeter, LoD / 最少知识原则）

**定义：** 一个对象应该对其他对象保持最少的了解。只与「直接朋友」（成员变量、方法参数、方法返回值）通信，不要和「陌生人」说话。

```java
// ❌ 链式深入调用，耦合了太多内部结构
a.getB().getC().doSomething();

// ✅ 让直接朋友（a）提供需要的方法
a.doSomethingViaC();
```

**核心思想：** 降低类之间的耦合。只依赖真正需要的对象，不要深入其他对象的内部结构去调用。

---

### 7. 合成复用原则（CARP，补充）

**定义：** 尽量使用**对象组合/聚合**，而不是**继承**来达到复用目的。继承是强耦合（「is-a」），组合是松耦合（「has-a」）。

> 💡 **提示：** 六大原则可以浓缩成一句话——**「找出变化，隔离变化，面向接口编程」**。所有的设计模式，本质上都是在用不同的方式落地这句话。

## 五、总结

| 维度 | 要点 |
| --- | --- |
| **本质** | 设计模式 = 面向对象设计原则的具体落地 |
| **灵魂原则** | 单一职责、开闭、里氏替换、依赖倒置、接口隔离、迪米特 |
| **三大分类** | 创建型（5）+ 结构型（7）+ 行为型（11）= GoF 23 种 |
| **学习路径** | 理解原则 → 匹配模式 → 编码实践 → 阅读源码印证 |
| **核心心态** | 不过度设计，模式是重构的工具而非炫技 |

> 💡 **学习建议：** 先吃透六大原则——原则是根，模式是叶。理解原则后，模式自然融会贯通。
