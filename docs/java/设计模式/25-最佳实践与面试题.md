## 一、最佳实践

### 1. 黄金法则：不要过度设计

| 原则 | 含义 | 一句话 |
| --- | --- | --- |
| **KISS** | Keep It Simple, Stupid | 简单优先，能用最直白的方式解决就别上模式 |
| **YAGNI** | You Aren't Gonna Need It | 别为「将来可能的需求」预先设计，真需要时再重构 |
| **三次法则** | Rule of Three | 同样代码重复三次以上，再考虑抽象/模式 |

### 2. 设计模式是「重构方向」而不是「起步姿势」

```
┌──────────────────────────────────────────────────────┐
│  先理解问题  ──▶  看问题是否匹配某模式  ──▶  再选模式  │
│         （而不是反过来：先有模式再找问题）             │
└──────────────────────────────────────────────────────┘
```

绝大多数项目初期不需要任何模式，等到业务变化触发了痛点（如 if-else 爆炸、类爆炸、难以扩展），再用模式重构。**先让它 work，再让它 good。**

### 3. 何时该用模式（信号）

| 代码信号 | 推荐模式 |
| --- | --- |
| 大量 `if-else`/`switch` 分支 | 策略模式、状态模式 |
| `new` 关键字散落各处 | 工厂模式 |
| 想给对象动态加功能 | 装饰器模式 |
| 一个全局共享实例 | 单例模式 |
| 流程固定但步骤多变 | 模板方法 |
| 一处变化多处联动 | 观察者模式 |
| 一层层审批/过滤 | 责任链模式 |
| 对象参数多且大多可选 | 建造者模式 |
| 接口不兼容需要协同工作 | 适配器模式 |
| 需要控制对对象的访问 | 代理模式 |

## 二、常见误区

| 误区 | 说明 |
| --- | --- |
| ❌ 滥用模式 | 一个简单的 CRUD 接口硬套工厂+策略+责任链，过度设计 |
| ❌ 为炫技而用 | 代码评审时堆砌模式，反而让同事看不懂 |
| ❌ 不理解就照抄 | 不理解模式解决的问题，套错地方制造 bug |
| ❌ 忽视场景 | 比如单例乱用导致单元测试困难、隐藏依赖 |
| ❌ 模式万能 | 模式解决的是「设计灵活性」，解决不了「业务正确性」 |

## 三、学习路径建议

1. **先吃透六大原则**——原则是根，模式是叶。理解原则后，模式自然融会贯通。
2. **每个模式务必手写一遍**——看懂不等于会写，手写过才能内化。
3. **结合框架源码**——在 Spring、JDK 源码中找模式的身影，加深理解。
4. **实战中刻意练习**——日常开发遇到 if-else 爆炸、类爆炸时，主动尝试用模式重构。
5. **遵循 KISS 原则**——别为了用模式而用模式，简单才是最优解。

## 四、面试常见问题

### Q1：单例模式有哪几种实现？哪种最优？如何保证线程安全？

**答：** 常见五种——饿汉式、懒汉式（加 synchronized）、双重检查锁（DCL）、静态内部类、枚举。

- **线程安全**：饿汉式靠类加载天然安全；懒汉式需 `synchronized`；DCL 用 `volatile` + 双重检查；静态内部类靠类加载机制；枚举天然安全。
- **最优推荐**：**枚举**（防反射和反序列化攻击，写法最简洁）；其次**静态内部类**和 **DCL**（兼顾懒加载和性能）。
- **DCL 中 `volatile` 的作用**：防止 `new` 操作的指令重排序导致其他线程拿到未初始化完成的对象。

---

### Q2：工厂方法模式与抽象工厂模式的区别？

**答：**
- **工厂方法**：一个工厂只创建**一种**产品，针对「产品等级结构」（同一类型的不同实现）。新增产品只需新增对应工厂，符合开闭原则。
- **抽象工厂**：一个工厂创建**一族**相关产品（如现代风格家具族），针对「产品族」。适合「成套创建」场景。
- 一句话：工厂方法关注**单一产品的扩展**，抽象工厂关注**产品族的切换**。

---

### Q3：装饰器模式和代理模式有什么区别？

**答：** 两者结构非常像（都持有目标对象引用并实现同一接口），但**目的不同**：

| 维度 | 装饰器 | 代理 |
| --- | --- | --- |
| 主要目的 | **增强**功能（加新行为） | **控制**访问（加权限/延迟/日志等横切关注点） |
| 关注点 | 调用方关心（调用方主动包装） | 被代理方关心（调用方无感） |
| 典型场景 | Java IO 流 | Spring AOP、远程代理 |

---

### Q4：策略模式解决了什么问题？请举一个 JDK 的例子。

**答：** 策略模式解决了**算法可互换**问题，本质是**消除大量 if-else 分支**，让算法的变化独立于使用者。

JDK 经典例子：`java.util.Comparator`——给 `Collections.sort(list, comparator)` 传不同的比较器（策略），排序算法不变，排序规则可灵活替换。Lambda 表达式让策略模式写得更简洁。

---

### Q5：模板方法模式和策略模式有什么区别？

**答：**
- **模板方法**：基于**继承**，父类定义算法骨架（流程），子类重写某些步骤。**流程固定，步骤可变**。
- **策略**：基于**组合**，把整个算法封装成对象，运行时切换。**整个算法可换**。
- 一句话：模板方法重定义**算法的局部步骤**，策略重定义**整个算法**。

---

### Q6：观察者模式和发布-订阅模式是一回事吗？

**答：** 严格区分的话：
- **观察者模式**：主题（Subject）**直接通知**观察者，二者有直接依赖，通常同步。
- **发布-订阅模式**：发布者和订阅者**互不认识**，通过一个**事件总线/消息代理（Broker）**间接通信，通常异步、跨进程。
- 日常开发中常把两者混用，但分布式场景（如 Kafka、RabbitMQ）严格属于发布-订阅。

---

### Q7：Spring 框架中用到了哪些设计模式？（高频）

**答：** Spring 是设计模式的「百科全书」：
- **单例**：Bean 默认作用域
- **工厂**：`BeanFactory` / `ApplicationContext`
- **代理**：AOP（JDK 动态代理 / CGLIB）
- **模板方法**：`JdbcTemplate`、`RestTemplate`、`TransactionTemplate`
- **观察者**：`ApplicationEvent` 事件机制
- **责任链**：`HandlerInterceptor`、过滤器
- **适配器**：`HandlerAdapter` 适配不同 Controller
- **装饰器**：BeanWrapper、各种 Wrapper
- **策略**：`Resource` 实现、`InstantiationStrategy`

---

### Q8：为什么要使用设计模式？过度设计有什么危害？

**答：**
- **使用设计模式的好处**：提升代码可维护性、可扩展性、可读性，应对需求变化，提供团队通用词汇。
- **过度设计的危害**：增加系统复杂度（类爆炸、调用链变长）、降低可读性、增加维护成本、拖慢开发进度。
- **平衡原则**：遵循 KISS、YAGNI、三次法则，**先让它跑起来，再让它更优雅**。模式是重构的工具，不是起步的姿势。

---

### Q9：动态代理 JDK 和 CGLIB 的区别？

**答：**
- **JDK 动态代理**：基于**接口**，目标类必须实现接口；通过 `Proxy.newProxyInstance` + `InvocationHandler` 实现；JDK 自带无需依赖。
- **CGLIB**：基于**继承**（生成目标类子类），不要求接口；通过 `Enhancer` + `MethodInterceptor` 实现；需引入 CGLIB 库。
- **Spring AOP 选择规则**：目标类实现了接口默认用 JDK 代理；否则用 CGLIB；可强制使用 CGLIB（`proxyTargetClass=true`）。
- **性能**：高版本 JDK 下 JDK 动态代理性能已大幅提升，两者差距不明显。

---

### Q10：开闭原则是什么？如何实现？

**答：** 开闭原则（OCP）：**对扩展开放，对修改关闭**——加新功能时尽量新增代码，不改老代码。

实现手段：通过**抽象（接口/抽象类）+ 多态**。把变化点抽象成接口，新增需求时新增实现类，而不是改老类的逻辑。典型落地模式：策略、工厂、模板方法、装饰器、观察者。

---

### Q11：适配器模式和外观模式的区别？

**答：**
- **适配器模式**：解决**接口不兼容**的问题，把一个接口转成另一个接口（一对一）。
- **外观模式**：解决**子系统太复杂**的问题，提供统一简化接口（一对多）。
- 适配器是「翻译官」，外观是「统一入口」。

---

### Q12：状态模式和策略模式的区别？

**答：**
- **状态模式**：对象**内部状态自动切换**，状态之间有关联（如订单状态：待支付 → 已支付 → 已发货）。
- **策略模式**：客户端**主动选择**策略，策略之间互相独立。
- 结构几乎一样，但**意图不同**：状态是「我处于哪个状态」，策略是「我选哪个算法」。

## 五、总结

### 核心要点回顾

| 维度 | 要点 |
| --- | --- |
| **本质** | 设计模式 = 面向对象设计原则的具体落地 |
| **灵魂原则** | 单一职责、开闭、里氏替换、依赖倒置、接口隔离、迪米特 |
| **三大分类** | 创建型（5）+ 结构型（7）+ 行为型（11）= GoF 23 种 |
| **高频模式** | 单例、工厂、建造者、适配器、装饰器、代理、策略、模板方法、观察者、责任链 |
| **学习路径** | 理解问题 → 匹配模式 → 编码实践 → 阅读源码印证 |
| **核心心态** | 不过度设计，模式是重构的工具而非炫技 |

### 一句话总结

> 设计模式不是教你「怎么写代码」，而是教你「怎么把代码写得更灵活、更易维护」。掌握它，是为了在面对变化时游刃有余，而不是把简单问题复杂化。**先让它 work，再让它 good，最后让它 scale。**
