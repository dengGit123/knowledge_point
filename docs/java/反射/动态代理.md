# 动态代理——反射的高级应用

> 📖 官方文档：[Proxy (Java SE 21)](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/reflect/Proxy.html) ｜ [InvocationHandler (Java SE 21)](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/reflect/InvocationHandler.html)

## 一、概述

**动态代理（Dynamic Proxy）** 是 Java 反射家族里最「上层」的应用：它在**运行时动态生成一个代理类**，这个代理类实现了指定的若干接口；当外部调用代理对象的任何接口方法时，调用会被统一**转发**到一个 `InvocationHandler`（调用处理器）——你可以在转发前后插入任意逻辑（记日志、开事务、发请求……），也可以决定要不要真正调用目标方法。

一句话：**反射让框架能调用「运行时才知道的方法」，动态代理让框架能拦截「运行时才知道的一批方法」**。

你天天在用的技术，底层都是它：

| 上层技术 | 动态代理扮演的角色 |
| ---- | ---- |
| Spring AOP | 事务、日志、缓存等切面通过代理织入 |
| MyBatis | Mapper 接口没有实现类，代理拦截方法调用转成 SQL 执行 |
| Spring Cloud OpenFeign | 接口方法被代理拦截，转成 HTTP 请求 |
| Dubbo / RPC 框架 | 消费端代理把本地方法调用转成远程调用 |

> 💡 **类比：** 目标类是「明星」，代理是「经纪人」。外人想找明星（调用目标方法），都得先过经纪人（`InvocationHandler`）这一关：经纪人可以记个日志（前置通知）、谈好条件再放行（事务开启）、事情办完送客（后置通知），甚至直接替明星婉拒（不调用目标方法）。而「经纪人」是运行时才雇的——接口方法成百上千，写死拦截代码不现实，动态代理统一转发搞定。

## 二、为什么需要「动态」代理？

静态代理的痛点：

```java
// 静态代理：一个接口一个代理类，方法全要手写转发
interface UserService {
    void save(String name);
    void delete(int id);
}

class UserServiceProxy implements UserService {   // ❌ 手写代理类
    private final UserService target;
    UserServiceProxy(UserService target) { this.target = target; }

    @Override
    public void save(String name) {
        System.out.println("日志");        // 重复样板
        target.save(name);
    }
    @Override
    public void delete(int id) {
        System.out.println("日志");        // 又是重复样板
        target.delete(id);
    }
}
```

接口每加一个方法，代理类就要同步改一次；100 个接口就要写 100 个代理类。动态代理把这些**全部交给运行时生成**——一份 `InvocationHandler` 逻辑通吃所有接口、所有方法。

## 三、JDK 动态代理三件套

```text
┌────────────────┐  实现   ┌──────────────────────┐
│  目标接口 Foo   │ ◄──── │ Proxy 生成的动态代理类 │
└────────────────┘         │ （$Proxy0，final）     │
                           └──────────┬───────────┘
                                      │ 所有方法调用都转发给
                                      ▼
                           ┌──────────────────────┐
                           │  InvocationHandler    │
                           │  invoke(proxy, m, args)│
                           └──────────┬───────────┘
                                      │ 你决定是否真正调用
                                      ▼
                           ┌──────────────────────┐
                           │     目标对象 target    │
                           └──────────────────────┘
```

1. **接口**：被代理的对象必须实现接口——JDK 代理在**运行时生成一个实现这些接口的新类**（代理类不是目标类的子类，而是 `Proxy` 的子类）。
2. **`InvocationHandler`**：拦截逻辑的归宿，实现 `invoke(Object proxy, Method method, Object[] args)`。
3. **`Proxy.newProxyInstance(loader, interfaces, handler)`**：工厂方法，生成代理实例。

### 基本用法

```java
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Method;
import java.lang.reflect.Proxy;

// 1. 目标接口
interface UserService {
    String getUser(int id);
    void save(String name);
}

// 2. 目标实现
class UserServiceImpl implements UserService {
    @Override
    public String getUser(int id) { return "用户" + id; }
    @Override
    public void save(String name) { System.out.println("保存: " + name); }
}

// 3. 调用处理器：所有接口方法都会进入这里
class LogHandler implements InvocationHandler {
    private final Object target;

    public LogHandler(Object target) { this.target = target; }

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        // —— 前置增强 ——
        System.out.println("[日志] 调用 " + method.getName() + "，参数: " + java.util.Arrays.toString(args));

        // 反射调用目标对象的真实方法（核心一行）
        Object result = method.invoke(target, args);

        // —— 后置增强 ——
        System.out.println("[日志] " + method.getName() + " 返回: " + result);
        return result;
    }
}

// 4. 生成并使用代理
public class ProxyDemo {
    public static void main(String[] args) {
        UserService target = new UserServiceImpl();

        UserService proxy = (UserService) Proxy.newProxyInstance(
                target.getClass().getClassLoader(),      // 类加载器
                target.getClass().getInterfaces(),        // 要代理的接口列表
                new LogHandler(target));                  // 调用处理器

        String user = proxy.getUser(1);   // 输出两行日志 + 调用真实方法
        proxy.save("张三");
        System.out.println(user);
    }
}
```

输出：

```text
[日志] 调用 getUser，参数: [1]
[日志] getUser 返回: 用户1
用户1
[日志] 调用 save，参数: [张三]
保存: 张三
[日志] save 返回: null
```

（`proxy.getUser(1)` 打印前三行，`proxy.save("张三")` 打印随后三行——`save` 的返回值 `null` 在最后统一由 `System.out.println(user)` 输出。）

### newProxyInstance 的三个参数

| 参数 | 说明 | 常见取法 |
| ---- | ---- | ---- |
| `ClassLoader loader` | 用哪个类加载器加载生成的代理类 | `目标类.getClassLoader()` |
| `Class<?>[] interfaces` | 代理类要实现的接口列表 | `目标类.getInterfaces()` |
| `InvocationHandler h` | 方法调用的统一分发处 | 自定义增强逻辑 |

> ⚠️ **注意：** 接口顺序是有意义的——「相同接口组合、不同顺序」会生成**两个不同的代理类**（官方 javadoc 明确说明）。代理类类名以 `$Proxy` 开头（具体名未规范）、是 `final` 的、继承 `java.lang.reflect.Proxy`。

## 四、invoke 的细节与陷阱

`invoke(Object proxy, Method method, Object[] args)` 的三个参数都有讲究：

### 1. `proxy` 参数：小心递归调用

`proxy` 是代理对象自身。**如果在 handler 里调用 `method.invoke(proxy, args)`（而不是 `method.invoke(target, args)`），会再次转发回 handler，无限递归直到栈溢出**。正确姿势永远是调 `target`。

### 2. `Object[] args`：为 null 与包装

- 无参方法：`args` 是 `null`（不是空数组），处理前判空。
- 基本类型实参已自动装箱为包装类型。
- 可变参数方法：`args` 里对应位置是一个数组。

```java
@Override
public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
    if (args == null) {
        System.out.println("无参调用");
    }
    return method.invoke(target, args);
}
```

### 3. 异常的两种包装

handler 里抛出的受检异常，必须能赋值给目标方法 `throws` 声明中的某个异常类型，否则代理会把它包装成 `UndeclaredThrowableException`（未受检异常）抛出——官方 javadoc 明确了这一规则。

```java
@Override
public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
    try {
        return method.invoke(target, args);
    } catch (InvocationTargetException e) {
        Throwable real = e.getCause();     // ✅ 还原目标方法内部的真实异常
        System.out.println("异常: " + real);
        throw real;                        // 重新抛给调用方
    }
}
```

### 4. 拦截 `Object` 的方法

`toString`、`hashCode`、`equals` 这些 `Object` 方法在代理对象上的调用**也会进入 handler**（官方行为），做日志/计数的 handler 要留意别把它们也算进业务统计。真实项目里常见这样的过滤：

```java
if (method.getDeclaringClass() == Object.class) {
    return method.invoke(target, args);   // Object 方法直接放行，不做增强
}
```

## 五、JDK 代理的能力边界

| 限制 | 原因 |
| ---- | ---- |
| **只能代理接口** | 生成的代理类继承 `Proxy`（Java 单继承），无法再继承你的目标类 |
| 目标方法本身不被「替换」 | 拦截发生在「调用转发」层，方法体逻辑在目标类里不变 |
| `final`/`static` 方法无感 | 接口方法没有这些修饰符问题；但若 handler 里 `method.invoke(target)`，`final` 方法也能正常反射调用 |
| 非 public 接口有限制 | 同一代理的多个非 public 接口必须在同一包下（官方 javadoc 约束） |
| 代理类是 `final` 的 | 不能再被继承；`Proxy.isProxyClass()` 可判断某类是否代理类 |

类的继承限制正是 **CGLIB** 存在的理由：Spring AOP 对「没实现接口的类」会退化为 CGLIB 字节码子类代理（继承目标类重写方法，非 `final` 方法才可被拦截）。Spring Boot 默认策略是即使有接口也用 CGLIB（`proxyTargetClass=true`），保证注入行为一致。

## 六、实战：一个通用的 Mapper 代理（MyBatis 原理缩影）

接口没有实现类，调用却「有结果」——这就是动态代理的魔力：

```java
import java.lang.annotation.*;
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Method;
import java.lang.reflect.Proxy;
import java.util.*;

public class MiniMapperDemo {

    // ① 注解标记 SQL
    @Retention(RetentionPolicy.RUNTIME)
    @Target(ElementType.METHOD)
    @interface Select { String value(); }

    // ② 只有接口，没有实现类
    interface UserMapper {
        @Select("SELECT * FROM user WHERE id = ?")
        Map<String, Object> getById(int id);

        @Select("SELECT * FROM user")
        List<Map<String, Object>> listAll();
    }

    // ③ 代理：拦截方法 → 读注解里的 SQL → 「执行」→ 返回
    static class MapperHandler implements InvocationHandler {
        @Override
        public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
            if (method.getDeclaringClass() == Object.class) {
                return method.invoke(this, args);
            }
            Select sql = method.getAnnotation(Select.class);
            System.out.println("执行 SQL: " + (sql != null ? sql.value() : method.getName()));
            System.out.println("参数: " + Arrays.toString(args));
            // 真实框架在这里：解析 SQL → JDBC 查询 → 按返回类型映射结果
            return new HashMap<>();   // 演示用，返回空结果
        }
    }

    // ④ 工厂方法：给任何 Mapper 接口生成代理
    @SuppressWarnings("unchecked")
    static <T> T getMapper(Class<T> mapperInterface) {
        return (T) Proxy.newProxyInstance(
                mapperInterface.getClassLoader(),
                new Class<?>[] { mapperInterface },
                new MapperHandler());
    }

    public static void main(String[] args) {
        UserMapper mapper = getMapper(UserMapper.class);   // 拿到的是 $Proxy 对象
        System.out.println(Proxy.isProxyClass(mapper.getClass())); // true
        mapper.getById(1);   // 「执行」了 SQL
        mapper.listAll();
    }
}
```

## 七、注意事项

1. **`invoke` 里调 `target` 而不是 `proxy`**，否则无限递归。
2. **`args` 可能是 `null`**（无参方法），先判空再遍历。
3. **`InvocationTargetException` 要解包**：`getCause()` 拿目标方法真实异常，再按需抛出。
4. **受检异常受限**：handler 抛出的受检异常必须在目标方法 `throws` 范围内，否则被包装成 `UndeclaredThrowableException`。
5. **只代理接口**：需要代理类（无接口）时用 CGLIB / Byte Buddy 等字节码方案。
6. **代理对象不要序列化/深度拷贝后跨类加载器使用**：代理类属于生成它的类加载器，跨加载器强转会 `ClassCastException`。
7. **性能**：每次方法调用都经过 handler 一次反射 `invoke`，且参数装箱。热点路径上，`MethodHandle`、`LambdaMetafactory` 乃至 Class-File API（JDK 24 正式定稿，JEP 484）是更现代的选择；常规业务无感。

## 八、使用场景

| 场景 | 代理拦截后做什么 |
| ---- | ---- |
| Spring AOP / 事务 | 开事务 → 执行业务 → 提交/回滚；日志、耗时监控、限流同理 |
| MyBatis Mapper | 拦截接口方法 → 解析 SQL 注解/XML → 执行查询 → 结果映射 |
| OpenFeign / RPC | 拦截接口方法 → 序列化参数 → 发 HTTP/网络请求 → 反序列化响应 |
| 延迟加载 | 代理第一次被调用时才真正初始化目标对象（懒加载） |
| 权限控制 | 方法调用前校验当前用户权限，不通过直接抛异常 |
| 缓存 | 以方法名 + 参数为 key 查缓存，命中直接返回，未命中才调用目标 |

## 九、总结

- 动态代理 = 运行时生成「实现指定接口」的代理类（`$ProxyX`、`final`）+ 统一转发到 `InvocationHandler.invoke(proxy, method, args)`。
- 三件套：接口（必须有）、`InvocationHandler`（增强逻辑）、`Proxy.newProxyInstance(loader, interfaces, handler)`。
- handler 里永远对 **target** 做反射调用；`args` 判空；`InvocationTargetException` 解包；受检异常受 `throws` 限制。
- JDK 代理只能代理接口，类的代理交给 CGLIB；`Proxy.isProxyClass()` 可识别代理类。
- 它是 AOP、Mapper、RPC 客户端等「接口即服务」技术的共同底座——理解了它，Spring AOP 与 MyBatis 的工作方式就通了。
