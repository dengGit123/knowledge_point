# 反射性能优化——让反射快起来

> 📖 官方文档：[Oracle 反射教程](https://docs.oracle.com/javase/tutorial/reflect/index.html) ｜ [MethodHandles.Lookup (Java SE 21)](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/invoke/MethodHandles.Lookup.html)

## 一、概述

反射「慢」是出了名的，但**慢在哪、慢多少、怎么救**，很多文章说不清楚。本篇拆开反射调用的开销来源，给出从「立竿见影」到「釜底抽薪」的四层优化手段，并说明什么时候应该放弃反射。

先给结论：

| 手段 | 相对直接调用的耗时（数量级） | 改造成本 |
| ---- | ---- | ---- |
| 直接调用 | 基准（1x） | —— |
| 反射（每次查找 + 无优化） | 慢 10 ~ 50 倍 | —— |
| 反射 + 缓存 + `setAccessible(true)` | 慢 2 ~ 5 倍 | 低 |
| `MethodHandle` | 接近直接调用 | 中 |
| `LambdaMetafactory` 生成函数对象 | 接近直接调用 | 中 |
| 字节码生成（CGLIB/Byte Buddy） | 接近直接调用 | 高 |

> 💡 **具体倍数取决于场景**（JDK 版本、JIT 预热、调用频率），上表是社区基准测试的常见数量级。正确的优化姿势是：**先测量自己的场景，再选手段**——用 JMH 做微基准，不要靠拍脑袋。

## 二、反射为什么慢

一次「裸反射调用」（每次都重新查找并调用）要经历四步：

```text
① 查找：getMethod("foo", ...) 在方法表里线性匹配名字 + 参数类型
② 装箱：int → Integer 等参数/返回值的包装与拆包
③ 检查：每次 get/invoke 都做语言访问权限检查（调用方 vs 目标成员）
④ 分发：通过 Method.invoke 的原生入口调用，JIT 难以内联优化
```

对应地，优化就瞄准四点：**别反复查找（缓存）**、**跳过权限检查（setAccessible）**、**减少装箱（类型化 API）**、**绕开反射分发（MethodHandle/函数对象）**。

## 三、第一层：缓存反射对象（收益最大）

`getMethod` 的查找远比 `invoke` 贵。把 `Method`/`Field`/`Constructor` 存起来复用，是成本最低、收益最大的一步。

```java
// ❌ 反模式：每次调用都查找
public String readName(Object user) throws Exception {
    Method m = user.getClass().getMethod("getName");  // 每次都查！
    return (String) m.invoke(user);
}

// ✅ 正解：静态缓存（类不变则 Method 不变，Method 对象线程安全可共享）
public class UserAccess {
    private static final Method GET_NAME;
    static {
        try {
            GET_NAME = User.class.getMethod("getName");
        } catch (NoSuchMethodException e) {
            throw new ExceptionInInitializerError(e);
        }
    }

    public static String readName(Object user) {
        try {
            return (String) GET_NAME.invoke(user);
        } catch (Exception e) {
            throw new RuntimeException(e);
        }
    }
}
```

类不确定时用 `Map` 缓存（注意并发安全）：

```java
public class ReflectCache {
    /** key: 类；value: 该类的全部 getter */
    private static final Map<Class<?>, Map<String, Method>> CACHE = new ConcurrentHashMap<>();

    public static Object invokeGetter(Object bean, String prop) {
        Map<String, Method> getters = CACHE.computeIfAbsent(bean.getClass(), cls -> {
            Map<String, Method> m = new HashMap<>();
            for (Method method : cls.getMethods()) {
                if (method.getParameterCount() == 0
                        && method.getName().startsWith("get")
                        && method.getReturnType() != void.class) {
                    m.put(method.getName(), method);
                }
            }
            return m;
        });
        try {
            Method getter = getters.get("get" + Character.toUpperCase(prop.charAt(0)) + prop.substring(1));
            return getter == null ? null : getter.invoke(bean);
        } catch (Exception e) {
            throw new RuntimeException(e);
        }
    }
}
```

> 💡 **提示：** `Method`/`Field` 对象是线程安全的、可被多线程共享——放心放进 `static final` 或 `ConcurrentHashMap`。框架启动时做一次「注解扫描 + 反射缓存」，运行期纯查表，就是 Spring/MyBatis 的通用做法。

## 四、第二层：setAccessible(true) 跳过权限检查

每次 `get`/`set`/`invoke` 默认要做一次「调用方是否有权访问目标成员」的检查。`setAccessible(true)` 之后这个检查被跳过——既解锁了 private，也顺带提速。

```java
private static final Field AGE;

static {
    try {
        AGE = User.class.getDeclaredField("age");
        AGE.setAccessible(true);   // ✅ 一次解锁，终身免检
    } catch (NoSuchFieldException e) {
        throw new ExceptionInInitializerError(e);
    }
}

static int readAge(Object user) {
    try {
        return AGE.getInt(user);   // 无权限检查 + 类型化免装箱
    } catch (IllegalAccessException e) {
        throw new RuntimeException(e);
    }
}
```

细节见 [setAccessible.md](./setAccessible.md)。组合拳「**缓存 + setAccessible(true) + 类型化 API**」能把反射开销压到直接调用的 2~5 倍以内，对绝大多数低频场景已完全够用。

## 五、第三层：换掉反射——MethodHandle 与函数对象

高频路径（每秒百万次级别）上，2~5 倍也不够，这时应该换掉反射本身。

### 1. LambdaMetafactory：把方法变成函数对象

利用 `LambdaMetafactory` 在运行时把一个方法「编译」成函数式接口实现，之后调用它就是普通接口调用，性能接近直接调用。Spring 的 `BeanWrapper`、各类 JSON 库的属性访问器大量使用此方案。

```java
import java.lang.invoke.LambdaMetafactory;
import java.lang.invoke.MethodHandle;
import java.lang.invoke.MethodHandles;
import java.lang.invoke.MethodType;
import java.util.function.Function;

public class GetterFactory {
    /** 把任意 getter 编译成 Function：之后调用零反射开销 */
    @SuppressWarnings("unchecked")
    public static <T, R> Function<T, R> createGetter(Class<T> cls, String getterName) {
        try {
            MethodHandles.Lookup lookup = MethodHandles.lookup();
            MethodHandle handle = lookup.findVirtual(cls, getterName, MethodType.methodType(Object.class));

            return (Function<T, R>) LambdaMetafactory.metafactory(
                    lookup,
                    "apply",                                            // 函数接口方法名
                    MethodType.methodType(Function.class),              // 生成的函数对象类型
                    MethodType.methodType(Object.class, Object.class),  // 接口方法签名
                    handle,                                             // 目标方法句柄
                    handle.type()                                       // 实际实现签名
            ).getTarget().invokeExact();
        } catch (Throwable e) {
            throw new RuntimeException(e);
        }
    }

    public static void main(String[] args) {
        Function<User, String> nameGetter = createGetter(User.class, "getName");
        // 之后每次调用就是普通接口调用，JIT 可内联
        String name = nameGetter.apply(new User("张三", 20));
    }
}
```

### 2. MethodHandle：反射的「高性能表亲」

`MethodHandle`（Java 7 引入，`java.lang.invoke` 包）与 `Method` 的定位相似，但设计目标是「可被 JIT 深度优化」：

| 对比项 | `Method`（反射） | `MethodHandle` |
| ---- | ---- | ---- |
| 包 | `java.lang.reflect` | `java.lang.invoke` |
| 检查时机 | 每次调用都检查参数/访问 | `Lookup` 创建时一次性检查，`invokeExact` 不再检查 |
| 调用 API | `invoke(Object, Object...)`，返回 `Object` | `invokeExact(具体类型...)`，签名精确匹配 |
| JIT 优化 | 难以内联 | ✅ 签名具体化后可内联，接近直接调用 |
| 使用成本 | 低 | 高（签名必须精确，`invokeExact` 差一个类型就 `WrongMethodTypeException`） |

```java
import java.lang.invoke.MethodHandle;
import java.lang.invoke.MethodHandles;
import java.lang.invoke.MethodType;

public class HandleDemo {
    public static void main(String[] args) throws Throwable {
        MethodHandles.Lookup lookup = MethodHandles.lookup();

        // 拿到 getName 的方法句柄：签名写死 (User)String
        MethodHandle getName = lookup.findVirtual(
                User.class, "getName", MethodType.methodType(String.class));

        User user = new User("张三", 20);
        // invokeExact：参数与返回类型必须与句柄签名完全一致，无装箱无 Object 转换
        String name = (String) getName.invokeExact(user);
        System.out.println(name);
    }
}
```

> 💡 **提示：** 选型口诀——**低频一次性**（启动、配置解析）用普通反射无所谓；**中频**用「缓存 + setAccessible」；**高频**（解析器、序列化热路径）上 `LambdaMetafactory` 或 `MethodHandle`；追求极致且能接受构建复杂度，用 Byte Buddy/CGLIB 直接生成字节码。

## 六、第四层：架构层面减少反射

1. **启动期做，运行期不做**：把反射集中在应用启动（扫描注解、构建元数据表），运行期只查表。Spring 的 Bean 定义、MyBatis 的 Mapper 元数据都是这个思路。
2. **编译期生成替代运行期反射**：MapStruct（编译期生成 Bean 拷贝代码）、Dagger（编译期生成依赖注入代码）的存在意义就是消灭运行时反射。
3. **GraalVM Native Image 场景必须收敛反射**：AOT 编译无法感知运行期反射，所有反射点都要显式登记（`reflect-config.json`），倒逼框架「能不用反射就不用」——Spring Native 的 AOT 处理正是如此。
4. **热点代码兜底加监控**：对怀疑反射拖慢的路径先上 JMH 或链路追踪测量，确认瓶颈再优化——反射常常只是「背锅侠」。

## 七、注意事项

1. **微基准要用 JMH**，不要在 main 里循环计时——JIT 预热、逃逸分析会让结果完全失真。
2. **缓存 `Method`/`Field` 时注意所属类**：继承场景要明确用 `getDeclaredMethod`（本类）还是 `getMethod`（可到父类），缓存了「错误的类」的方法句柄会在多态场景下调错实现。
3. **`setAccessible(true)` 在模块化环境下可能失败**：用 `trySetAccessible()` 探测并降级，别让优化代码本身抛异常（见 [setAccessible.md](./setAccessible.md)）。
4. **`MethodHandle` 的 `invokeExact` 不做任何类型适配**：签名差一个转换就抛 `WrongMethodTypeException`；不确定时用宽松版 `invoke`（有适配开销）。
5. **反射对象缓存失效问题**：重新部署/热加载类加载器后，旧缓存的 `Method` 指向旧类，跨加载器调用会 `ClassCastException`——缓存生命周期要绑定类加载器。

## 八、总结

- 反射的四大开销：查找、装箱、权限检查、分发难内联；对应的优化手段一一对应。
- **优先级从高到低**：缓存反射对象（收益最大、成本最低）→ `setAccessible(true)` 跳过权限检查 → 类型化 API 免装箱 → 高频路径换 `MethodHandle`/`LambdaMetafactory` → 架构上「启动期反射、运行期查表」甚至编译期生成。
- 反射不总是瓶颈：低频场景（启动、配置）直接用，别过度优化；优化前先测量。
- 记住这个成本阶梯：直接调用 < MethodHandle/Lambda 函数对象 < 缓存后的反射 < 裸反射。
