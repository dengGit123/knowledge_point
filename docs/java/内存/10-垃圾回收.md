# 垃圾回收（Garbage Collection）

> 📖 官方文档：[HotSpot Virtual Machine Garbage Collection Tuning Guide](https://docs.oracle.com/en/java/javase/21/gctuning/) ｜ [JVM Specification - Heap](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-2.html#jvms-2.5.3)

---

### 一、概述

**垃圾回收（GC，Garbage Collection）** 是 JVM 自动管理内存的核心机制：自动找出"不再使用的对象"，释放它们占用的内存。程序员只管 `new`，不用手动 `free`——这既是 Java 最大的优点，也埋藏着"以为 GC 万能实则泄漏不断"的常见误区。

GC 主要工作在**堆**（方法区也会做低频回收），其核心要回答四个问题：

1. **哪些是垃圾？**——对象存活判定（可达性分析）
2. **什么时候收？**——GC 触发时机（分代回收）
3. **怎么收？**——回收算法（标记-清除/复制/整理）
4. **谁来收？**——垃圾收集器（Serial / Parallel / CMS / G1 / ZGC）

> 💡 **通俗理解**：GC 就像小区的"废品回收站"：
> - 每天高峰期快速扫一遍楼道（Minor GC，快、频繁）；
> - 定期来一次全小区大扫除（Full GC，慢、全停）；
> - 大扫除时所有住户都要"暂停活动"配合（STW，Stop The World）。

### 二、对象存活判定：哪些是垃圾？

#### 1. 两种判定算法

| 算法 | 原理 | 缺陷 | JVM 是否采用 |
|------|------|------|:-----------:|
| **引用计数法** | 每个对象带引用计数器，+1/-1，为 0 即垃圾 | **循环引用**无法回收（A→B、B→A，计数永不归零）；计数器维护开销 | ❌（JVM 不用） |
| **可达性分析** | 从 **GC Roots** 出发搜索引用链，**不可达**的对象即垃圾 | 需要 STW 保证引用关系快照一致（有优化手段） | ✅（主流 JVM 采用） |

```text
引用计数法死穴——循环引用：

  A.next = B;  B.ref = A;      A.count=1, B.count=1
  之后 A、B 再无外部引用，但计数器都是 1，永远收不掉 ❌

可达性分析——循环引用不是问题：

       GC Roots ──→ obj1 ──→ obj2        ✅ 可达：存活
              └──→ obj3                   ✅ 可达：存活

       obj4 ⇄ obj5  （互相引用）           ❌ 从 GC Roots 不可达：
                                           即便互相引用，仍判定为垃圾 ✅
```

#### 2. GC Roots 有哪些？

可作为 GC Roots 的对象（记"栈、静态、常量、Native、锁"五类）：

| GC Roots | 说明 |
|---------|------|
| **虚拟机栈**局部变量表引用的对象 | 正在执行的方法里的局部变量、参数 |
| **方法区**静态属性引用的对象 | `static` 变量指向的对象 |
| **方法区**常量引用的对象 | 字符串常量池中的引用 |
| **本地方法栈** JNI 引用的对象 | Native 代码持有的引用 |
| JVM 内部引用 | 基本类型 Class 对象、常驻异常对象、系统类加载器 |
| 同步锁持有的对象 | 被 `synchronized` 锁住的对象 |

#### 3. 引用的四级强度

对象是否"可达"取决于引用强度（详见 [08-对象在内存中.md](./08-对象在内存中.md) 的"四种引用强度"一节）：

| 引用 | 回收时机 | 典型用途 |
|------|---------|---------|
| 强引用 | 永不回收（宁可 OOM） | 日常对象 |
| 软引用 `SoftReference` | 内存不足时回收 | 缓存 |
| 弱引用 `WeakReference` | 下次 GC 必回收 | `WeakHashMap`、`ThreadLocal` key |
| 虚引用 `PhantomReference` | 随时可回收，仅回收时通知 | 堆外内存清理（NIO Cleaner） |

> 💡 **提示：** 可达性分析判定为"不可达"的对象**不会立即死亡**，还有一次"缓刑"机会——若重写了 `finalize()` 且未执行过，会被 F-Queue 队列安排 finalize 自救，成功与引用链建立联系即可"复活"。但 `finalize()` 在 JDK 9 起已标记 `@Deprecated`，**永远不要依赖它做资源清理**（无法保证执行时机与执行），资源释放请用 `try-with-resources` 或 `AutoCloseable`。

### 三、垃圾回收算法

#### 1. 三大基础算法

| 算法 | 步骤 | 优点 | 缺点 | 适用区域 |
|------|------|------|------|---------|
| **标记-清除**（Mark-Sweep） | ① 从 GC Roots 标记存活对象 ② 统一清除未标记的 | 简单；不移动对象 | **内存碎片**；效率随对象数量下降 | CMS 老年代 |
| **标记-复制**（Copying） | 内存分两块，把存活对象**复制**到另一块，整体清空原块 | 无碎片；分配快（指针碰撞）；存活少时极高效 | 浪费内存（最多一半）；存活多时复制开销大 | **新生代**（改良版：Eden + 双 Survivor） |
| **标记-整理**（Mark-Compact） | 标记存活对象后向一端**移动**，清理边界外内存 | 无碎片；不浪费内存 | 移动对象成本高（需调整所有引用） | **老年代** |

#### 2. 为什么分代搭配不同算法？（核心设计思想）

IBM 研究表明：绝大多数对象**朝生夕灭**（新生代 98% 在第一次 GC 前死亡），而熬过多次 GC 的对象会**越活越久**。两类对象生命周期天差地别，用同一套算法必然顾此失彼：

| 区域 | 对象特点 | 最优算法 | 原因 |
|------|---------|---------|------|
| **新生代** | 朝生夕灭、存活率极低 | **标记-复制** | 存活对象少，复制成本低；清空整块区域只需重置指针 |
| **老年代** | 存活率高、久经考验 | **标记-清除** 或 **标记-整理** | 存活对象多，复制不划算；整理可消除碎片 |

> 💡 **通俗理解**：新生代像"招聘市场"——人流量大但留下的少，每次直接把留下的人搬到新市场（复制），旧市场整体腾空；老年代像"老小区"——老住户（存活对象）多，不宜整体搬迁（复制），只能逐户登记（标记）后清理空房（整理）。

### 四、分代回收流程（GC 何时发生）

```
┌──────────────────────── 堆 ────────────────────────┐
│   新生代                                           │
│  ┌─────────┬─────────┬─────────┐                   │
│  │  Eden   │   S0    │   S1    │  ← Minor GC 区域  │
│  └─────────┴─────────┴─────────┘                   │
│  ┌─────────────────────────────────┐               │
│  │            老年代                │ ← Major GC 区域│
│  └─────────────────────────────────┘               │
└────────────────────────────────────────────────────┘

对象流转：
new 出来 → Eden（TLAB 加速）→ Eden 满 → Minor GC
  → 存活对象年龄+1 → Survivor（S0⇄S1 交替）
  → 年龄 ≥ 15（默认）或动态年龄达标 → 晋升老年代
  → 老年代满 → Major GC / Full GC
```

| GC 类型 | 回收范围 | 触发条件 | 频率 | 耗时 | STW |
|---------|---------|---------|:----:|------|-----|
| **Minor GC**（Young GC） | 新生代 | Eden 空间不足 | 频繁 | 短（毫秒级） | 短暂 STW |
| **Major GC**（Old GC） | 老年代 | 老年代空间不足 | 较少 | 较长 | 较长 STW |
| **Full GC** | 整个堆 + 方法区 | 老年代不足 / 元空间不足 / `System.gc()` 建议 | 最少 | 最长 | 全停，应极力避免频繁发生 |

> ⚠️ **注意：** Major GC 和 Full GC 常被混用，严格说 Major GC 只收老年代，Full GC 收整堆 + 方法区。很多资料（包括 CMS 场景）把两者等同，面试时说清口径即可，重点是理解**范围不同、代价不同**。
>
> `System.gc()` 只是"建议"JVM 做 Full GC，**不保证立即执行**，生产代码不要调用。

### 五、经典垃圾收集器

收集器是回收算法的**落地实现**。按演进顺序认识主流收集器：

| 收集器 | 作用区域 | 算法 | 特点 | 适配场景 |
|--------|---------|------|------|---------|
| **Serial** | 新生代 | 复制 | 单线程，STW 时全部暂停 | 客户端、小内存 |
| **ParNew** | 新生代 | 复制 | Serial 的多线程版 | 配合 CMS |
| **Parallel Scavenge** | 新生代 | 复制 | 多线程，追求**吞吐量** | 批处理、后台计算（JDK 8 默认新生代） |
| **Serial Old** | 老年代 | 标记-整理 | 单线程 | 客户端 |
| **Parallel Old** | 老年代 | 标记-整理 | 多线程，配 Parallel Scavenge（JDK 8 默认老年代） | 吞吐量优先 |
| **CMS** | 老年代 | 标记-清除 | **并发**收集，停顿短；有碎片；JDK 14 已移除 | 低延迟（历史方案） |
| **G1** | 整堆（Region 化） | 整体标记-整理 + 局部复制 | 可预测停顿、优先回收"垃圾最多"的 Region | **JDK 9+ 默认**，大堆服务端 |
| **ZGC** | 整堆 | 着色指针 + 读屏障 | 停顿 **< 1ms**，支持 TB 级堆 | 超低延迟、超大内存（JDK 15+ 生产可用） |

#### 1. G1（Garbage First，重点）

G1 最大的革新：把堆划分为多个大小相等的 **Region**（1MB~32MB），不再物理隔离新生代/老年代——Region 动态扮演 Eden、Survivor、老年代角色：

```
┌────┬────┬────┬────┬────┐
│ E  │ E  │ S  │ O  │ H  │   E=Eden  S=Survivor
├────┼────┼────┼────┼────┤   O=Old   H=Humongous（大对象）
│ O  │ E  │ O  │ O  │ E  │
├────┼────┼────┼────┼────┤
│ O  │ 空 │ E  │ O  │ 空 │
└────┴────┴────┴────┴────┘
G1 维护每个 Region 的"垃圾价值"（回收收益/成本），
优先回收价值最高的 Region —— 这就是 Garbage First 名字的由来
```

- **可预测停顿**：`-XX:MaxGCPauseMillis=200`（默认 200ms）设定目标停顿，G1 按目标挑选回收 Region 数量；
- **Humongous 区**：超过 Region 一半的大对象直接进 Humongous Region（逻辑上属老年代）；
- 整体上是标记-整理（Region 之间复制），局部（Region 之间）是复制算法，**不产生碎片**。

```bash
java -XX:+UseG1GC -XX:MaxGCPauseMillis=100 MyApp   # 启用 G1 并设定期望停顿
```

#### 2. ZGC 与低延迟方向

```bash
java -XX:+UseZGC MyApp    # 启用 ZGC（JDK 15+ 生产可用，JDK 21 支持分代 ZGC）
```

ZGC 的停顿时间**不随堆大小增长**（< 1ms），核心手段是把大部分 GC 工作（标记、转移、重定位）做成**与应用线程并发**执行。大内存、低延迟场景（实时风控、游戏服务器）的首选。

> 💡 **提示：** 选型口诀：**小内存求省心用默认（G1），大内存求极低停顿上 ZGC**。JDK 8 的默认组合 Parallel 适合吞吐量优先的批处理，但新项目建议直接用 JDK 17/21 + G1/ZGC。

### 六、GC 日志与调优入口

GC 调优的第一步是**读懂 GC 日志**：

```bash
java -Xlog:gc* -Xms1g -Xmx1g MyApp    # JDK 9+ 统一日志（JDK 8 用 -XX:+PrintGCDetails）
```

```text
[gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause)
[gc]   Eden regions: 60->0(60)        ← Eden 从 60 个 Region 清空
[gc]   Survivor regions: 0->10(10)
[gc]   Old regions: 0->2              ← 有 2 个 Region 晋升老年代
[gc]   Pause Young: 90M->12M(256M) 18.5ms   ← 回收了 78M，停顿 18.5ms
```

关键参数速查：

| 参数 | 含义 |
|------|------|
| `-Xms` / `-Xmx` | 初始/最大堆大小（生产建议相等，防扩容抖动） |
| `-Xmn` | 新生代大小（一般不手动设，交给收集器自适应） |
| `-XX:SurvivorRatio=8` | Eden:S0:S1 = 8:1:1 |
| `-XX:MaxTenuringThreshold=15` | 晋升老年代的年龄阈值 |
| `-XX:MaxGCPauseMillis=200` | G1 目标停顿时间 |
| `-XX:+HeapDumpOnOutOfMemoryError` | OOM 时自动 dump 堆快照 |

更深入的调优实践见 [JVM调优.md](../JVM调优.md)（本目录之外的同主题文档）。

### 七、常见问题与注意事项

#### Q1：有了 GC 还会内存泄漏吗？

会。GC 只回收"不可达"对象，**可达但无用**的对象它管不着：

```java
public class LeakDemo {
    private static List<byte[]> cache = new ArrayList<>();  // 静态集合持有引用

    public static void add(byte[] data) {
        cache.add(data);
        // ❌ 只加不减：data 一直可达，GC 永远不回收 → 缓慢泄漏直到 OOM
    }
}
```

典型泄漏源：静态集合、未关闭的资源、`ThreadLocal` 未 `remove()`（线程池场景）、监听器未注销、内部类持有外部引用。详见 [11-内存溢出与泄漏排查.md](./11-内存溢出与泄漏排查.md)。

#### Q2：对象一定会经历"Eden → Survivor → 老年代"吗？

不是。两种例外：**大对象**直接进老年代（或 G1 的 Humongous Region），跳过新生代倒腾；**动态年龄判定**下对象可能提前晋升（Survivor 中同龄对象总大小超过一半，不必等 15 岁）。

#### Q3：Stop The World（STW）为什么无法彻底消除？

GC 判定对象存活时需要**一致性的引用快照**——分析期间引用关系不能变。ZGC 通过着色指针 + 读屏障把停顿压到 1ms 内，但"短暂停顿"依然存在，只是几乎无感。

#### Q4：`finalize()` 能用来关闭资源吗？

不能。它执行时机不确定、甚至可能不执行，且会延缓对象回收。正确姿势：

```java
// ✅ try-with-resources：编译器保证 close() 一定执行
try (FileInputStream in = new FileInputStream("data.txt")) {
    in.read();
}   // 自动调用 in.close()，即使抛异常也会执行
```

### 八、总结

| 知识点 | 核心要点 |
|--------|---------|
| 存活判定 | 可达性分析（GC Roots 出发），循环引用不是问题；引用计数法 JVM 不采用 |
| GC Roots | 栈中局部变量、静态变量、常量、Native 引用、锁对象 |
| 三大算法 | 标记-清除（碎片）、标记-复制（新生代）、标记-整理（老年代） |
| 分代回收 | Minor GC（新生代，快而频）、Full GC（整堆，慢而少） |
| 收集器演进 | Serial → Parallel（吞吐）→ CMS（低延迟，已移除）→ G1（JDK 9+ 默认）→ ZGC（< 1ms） |
| 泄漏本质 | 可达但无用的对象，GC 无能为力 |

**记住三句话**：

1. **垃圾判定看可达性：从 GC Roots 摸不到的都是垃圾，循环引用不算数。**
2. **新生代复制、老年代整理——分代是对"朝生夕灭"规律的最优响应。**
3. **GC 只回收不可达对象；可达但无用的对象会泄漏，静态集合和 ThreadLocal 是重灾区。**
