# 内存溢出与内存泄漏排查

> 📖 官方文档：[Troubleshoot Memory Leaks (Oracle)](https://docs.oracle.com/en/java/javase/21/troubleshoot/memory-leaks.html) ｜ [jmap 命令参考](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jmap.html)

---

### 一、概述

**内存溢出（OOM，OutOfMemoryError）** 和**内存泄漏（Memory Leak）** 是 Java 应用最常见也最致命的线上问题。两者关系密切但概念不同：

| 概念 | 定义 | 关系 |
|------|------|------|
| **内存泄漏（Leak）** | 对象**已经无用**，但被引用链"锚住"，GC 无法回收 | 泄漏持续积累 → 逐渐挤占内存 → 最终引发溢出 |
| **内存溢出（OOM）** | 内存**真的不够用**，新对象无法分配，JVM 抛错终止请求甚至宕机 | 是"结果"；泄漏是常见"病因"之一 |

> 💡 **通俗理解**：内存泄漏是"下水道被头发慢慢堵住"（水流越来越慢）；内存溢出是"水彻底漫出来了"（爆了）。堵是因，漫是果。
>
> 另一个形象的类比：对象是"客人"，引用是"牵着客人的绳子"。GC 只收走"没有绳子牵的客人"。内存泄漏就是——客人早该走了，可你还死死牵着绳子。

### 二、OOM 的常见类型与对应区域

不同的报错信息直接指明了"哪个内存区域出了问题"：

| 异常信息 | 出问题区域 | 常见原因 |
|---------|-----------|---------|
| `OutOfMemoryError: Java heap space` | **堆** | 大量对象未释放、集合只增不减、大查询一次性加载全表数据 |
| `GC overhead limit exceeded` | 堆 | GC 花了 98% 以上时间却只回收不到 2% 内存——堆几乎满了 |
| `OutOfMemoryError: Metaspace` | 方法区（元空间） | 动态生成海量类：CGLib 动态代理、热部署反复加载类 |
| `OutOfMemoryError: unable to create native thread` | 线程栈/系统 | 创建线程过多（每个线程要分配 `-Xss` 栈内存） |
| `OutOfMemoryError: Direct buffer memory` | 直接内存 | NIO `allocateDirect` 分配的堆外内存用尽 |
| `StackOverflowError` | 虚拟机栈 | 递归无终止条件、调用链过深 |

> ⚠️ **注意：** 每个线程的栈内存（默认约 1MB）× 线程数，加上堆和元空间，总和不能超过系统物理内存。容器化部署（Docker/K8s）时尤其注意：JVM 可能"看到"的内存限制与容器实际限制不一致，需用 `-XX:MaxRAMPercentage` 按容器比例设置堆上限。

### 三、内存泄漏的典型场景

#### 1. 静态集合只增不减（最常见）

```java
public class StaticLeak {
    // ❌ static 保证集合永远可达 → 里面所有对象都跟着"永生"
    private static List<byte[]> cache = new ArrayList<>();

    public static void cache(byte[] data) {
        cache.add(data);            // 只进不出
    }

    // ✅ 解法 1：用弱引用容器（WeakHashMap / Guava Cache）
    private static Map<String, byte[]> safeCache = new WeakHashMap<>();

    // ✅ 解法 2：有界缓存 + 淘汰策略（如 LRU）
    private static Map<String, byte[]> boundedCache =
            new LinkedHashMap<>(16, 0.75f, true) {
                @Override
                protected boolean removeEldestEntry(Map.Entry<String, byte[]> eldest) {
                    return size() > 1000;     // 超过 1000 条自动淘汰最老数据
                }
            };
}
```

#### 2. ThreadLocal 用完不 remove（线程池场景重灾区）

```java
public class ThreadLocalLeak {
    private static ThreadLocal<byte[]> context = new ThreadLocal<>();

    public void handle(Request req) {
        context.set(new byte[1024 * 1024]);   // 1MB 上下文
        try {
            doBusiness();
        } finally {
            context.remove();                 // ✅ 必须手动清理！
        }
    }
}
```

> ⚠️ **注意：** `ThreadLocal` 的 Entry 的 key 是**弱引用**，GC 后 key 变 `null`，但 **value 是强引用**且被 `ThreadLocalMap` 持有——线程池的核心线程永不销毁，value 就一直堆着。所以 `remove()` 必须放在 `finally` 里，这是《阿里巴巴 Java 开发手册》明确要求的规范。

#### 3. 资源未关闭

```java
// ❌ 连接、流未关闭：底层资源（socket、文件句柄、缓冲区）无法释放
public byte[] badRead(String path) throws IOException {
    FileInputStream in = new FileInputStream(path);   // 异常时永远不会 close
    byte[] data = in.readAllBytes();
    in.close();                                       // 若上面抛异常，这行执行不到
    return data;
}

// ✅ try-with-resources：无论是否抛异常，close() 都会执行
public byte[] goodRead(String path) throws IOException {
    try (FileInputStream in = new FileInputStream(path)) {
        return in.readAllBytes();
    }
}
```

#### 4. 监听器/回调未注销

```java
public class ListenerLeak {
    public void register(EventBus bus) {
        bus.register(this::onEvent);    // ❌ 注册后从不注销
    }                                   // EventBus 持有 this → 本对象无法回收

    // ✅ 生命周期结束时注销
    public void destroy(EventBus bus) {
        bus.unregister(this::onEvent);
    }
}
```

#### 5. 其他常见泄漏源

| 场景 | 说明 |
|------|------|
| 内部类持有外部类引用 | 非静态内部类隐式持有外部 `this`，内部类实例长期存活会连带外部对象"永生" |
| 字符串 `intern()` 滥用 | 大量动态字符串调用 `intern()`，字符串常量池（堆中）持续膨胀 |
| 缓存的 value 引用 value | 缓存对象之间互相引用，形成"可达但无用"的孤岛 |
| 类加载器泄漏 | 热部署应用中，一个类被旧 ClassLoader 持有，整个应用的所有类都无法卸载 → `Metaspace` OOM |

### 四、排查流程与工具

#### 1. 标准排查流程

```
① 发现异常
   OOM 报错 / 内存持续上涨 / Full GC 频繁
        │
        ▼
② 拿到现场证据
   • OOM 时自动 dump：-XX:+HeapDumpOnOutOfMemoryError
   • 手动 dump：jmap -dump:live,format=b,file=heap.hprof <pid>
        │
        ▼
③ 分析 dump
   MAT / VisualVM / JProfiler 打开 .hprof
   看 Dominator Tree（谁占内存最多）→ Leak Suspects（泄漏嫌疑报告）
        │
        ▼
④ 定位引用链（GC Roots Path）
   从可疑对象反查：谁在引用它？ → 找到"该断没断"的那根引用
        │
        ▼
⑤ 修复代码 + 验证
   断开引用 / 加淘汰策略 / 补 close-remove-unregister
```

#### 2. 常用命令行工具

| 工具 | 作用 | 示例 |
|------|------|------|
| `jps` | 列出 Java 进程 PID | `jps -l` |
| `jstat` | 查看 GC 统计（各代占用、GC 次数/耗时） | `jstat -gcutil <pid> 1000`（每秒刷新） |
| `jmap` | 生成堆转储（JDK 9 起查看堆概况已改用 `jcmd`） | `jmap -dump:live,format=b,file=heap.hprof <pid>` |
| `jstack` | 查看线程栈（配合排查"线程过多"型 OOM） | `jstack <pid>` |
| `jcmd` | 综合诊断（推荐）：查看堆概况、生成 dump | `jcmd <pid> GC.heap_info`、`jcmd <pid> GC.heap_dump heap.hprof` |

```bash
# 实战：每秒输出一次各内存区域使用率
jstat -gcutil 12345 1000
#  S0     S1     E      O      M     CCS    YGC    YGCT   FGC   FGCT
#  0.00  45.20  78.30  92.10  95.40  88.00  1200   15.2   89    120.5
#  ↑ 老年代 92% 且 FGC 频繁、FGCT 高 → 典型的老年代泄漏特征
```

#### 3. MAT 分析要点

Eclipse MAT（Memory Analyzer Tool）打开 `.hprof` 后重点看三处：

| 视图 | 用途 |
|------|------|
| **Leak Suspects** | 自动生成泄漏嫌疑报告，直接指出可疑对象和可疑引用链 |
| **Dominator Tree** | 按"保留内存大小"排序对象，找到内存大户 |
| **Path to GC Roots** | 从可疑对象反查引用链，确定"谁锚住了它"（排除弱/软引用） |

### 五、预防策略

| 策略 | 说明 |
|------|------|
| **OOM 自动 dump** | 生产必备：`-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump/` |
| **合理堆大小** | `-Xms` = `-Xmx`，给容器留出堆外空间（堆 ≤ 容器内存的 75%） |
| **缓存必须有界** | 任何本地缓存都要有最大容量 + 淘汰策略（LRU/LFU/TTL） |
| **规范清理资源** | try-with-resources；ThreadLocal 在 `finally` 中 remove |
| **压测验证** | 上线前长时间压测观察内存曲线——健康曲线是"锯齿状回落"，持续爬坡不回落就是泄漏 |
| **监控告警** | 关注 Full GC 频率、老年代使用率（超过 80% 告警） |

```text
健康内存曲线（锯齿）：        泄漏内存曲线（爬坡）：

 usage                        usage
  │ ∿∿∿∿∿∿  GC 回落           │      ╱╱╱  只涨不跌
  │ ∿∿∿∿                      │   ╱╱
  │∿∿∿                        │ ╱╱
  └──────────→ time           └──────────→ time
```

### 七、总结

| 知识点 | 核心要点 |
|--------|---------|
| 泄漏 vs 溢出 | 泄漏是"无用但可达收不走"，溢出是"内存真不够"——泄漏常是溢出的病因 |
| 报错定位 | 看异常信息直接定位区域：heap space（堆）、Metaspace（方法区）、native thread（栈） |
| 高发场景 | 静态集合、ThreadLocal 不 remove、资源不 close、监听器不注销 |
| 排查三板斧 | dump（`jmap`/自动 dump）→ 分析（MAT）→ 反查引用链（Path to GC Roots） |
| 预防为主 | 缓存有界、资源必关、`finally` 清理、OOM 自动 dump、监控 Full GC 频率 |

**记住三句话**：

1. **GC 只收不可达对象；"可达但无用"的泄漏，GC 永远管不着——绳子在你手里。**
2. **报错信息就是地图：heap space 查堆、Metaspace 查类加载、native thread 查线程数。**
3. **ThreadLocal 用完必 remove（finally 里）、资源必 try-with-resources、缓存必须有界。**
