# 方法区（Method Area）

> 📖 官方文档：[The Java Virtual Machine Specification - Method Area](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-2.html#jvms-2.5.4) ｜ [JEP 122: Remove the Permanent Generation](https://openjdk.org/jeps/122)

---

### 一、概述

**方法区（Method Area）** 是各线程共享的内存区域，存放的是"关于类的一切"：**类元信息、运行时常量池、静态变量、JIT 编译后的代码缓存**。与堆存放"对象实例"相对，方法区存放的是"类的蓝图和全局数据"。

> 💡 **通俗理解**：如果说堆是"成品仓库"，方法区就是"图纸资料室 + 全局公告栏"：
> - 每个类的**设计图纸**（类结构、方法字节码）——类元信息；
> - 图纸上标注的**标准尺寸**（`final` 常量、字符串字面量）——运行时常量池；
> - 贴在墙上人人可见的**公告**（`static` 静态变量）——全局共享；
> - 常用流程被翻译好的**速查手册**（JIT 编译后的本地代码）——代码缓存。

> ⚠️ **概念与实现要分清：** "方法区"是 JVM **规范**里的逻辑概念；"永久代 / 元空间"是 HotSpot 虚拟机对它的**实现**。就像"发动机"是概念，"燃油机/电机"是不同实现。JDK 8 最大的变化就是换了实现。

### 二、存放的内容

| 内容 | 说明 | 示例 |
|------|------|------|
| **类元信息** | 类的全限定名、父类、接口列表、字段描述、方法信息（字节码）、访问修饰符 | `Person` 类的 `sayHi()` 方法字节码 |
| **运行时常量池** | 编译期常量 + 运行期可动态添加的常量，含字面量和符号引用 | `"hello"` 字面量、`Integer.MAX_VALUE` |
| **静态变量** | `static` 修饰的类变量，被所有实例共享 | `static int count` |
| **JIT 代码缓存** | 即时编译器把热点字节码编译成的本地机器码 | HotSpot 的 CodeCache |
| Class 对象 | 类加载后生成的 `java.lang.Class` 实例，是反射的入口 | `Person.class` |

> 💡 **提示：** 严格来说，JDK 7 起静态变量和 Class 对象已随字符串常量池一起移到**堆**中（作为 `java.lang.Class` 对象的一部分），元空间存放的主要是**类元信息**。但"静态变量逻辑上属于方法区"这个说法在面试中依然通用——重要的是理解它**被所有线程共享、随类存在而非随实例存在**。

### 三、永久代 → 元空间的演变（高频考点）

#### 1. 版本时间线

| JDK 版本 | 方法区实现 | 位置 | 上限控制 | 典型 OOM |
|---------|-----------|------|---------|---------|
| JDK 6 及以前 | 永久代（PermGen） | JVM 进程内存 | `-XX:PermSize` / `-XX:MaxPermSize` | `OOM: PermGen space` |
| JDK 7 | 永久代（开始瘦身） | 字符串常量池、静态变量逐步移入堆 | 同上 | `OOM: PermGen space` |
| **JDK 8+** | **元空间（Metaspace）** | **本地内存（Native Memory）** | `-XX:MetaspaceSize` / `-XX:MaxMetaspaceSize` | `OOM: Metaspace` |

#### 2. 为什么要废弃永久代？

1. **容易 OOM**：永久代大小固定（`-XX:MaxPermSize` 默认很小），动态生成类多时（反射、动态代理、JSP 热部署）极易 `PermGen space` 溢出。
2. **调优困难**：很难预估"类有多少"来给永久代定一个合适大小。
3. **统一架构**：Oracle 收购 BEA 后合并 JRockit 虚拟机代码，而 JRockit **从来没有永久代**，把类元数据放本地内存。
4. **为未来铺路**：本地内存天然可自动扩容，与堆解耦后互不挤占。

#### 3. 元空间使用本地内存的含义

```
JDK 7（永久代）                         JDK 8+（元空间）
┌──────── JVM 进程内存 ────────┐        ┌──────── JVM 进程内存 ────────┐
│ ┌─────────┐  ┌────────────┐ │        │ ┌─────────┐                 │
│ │  Java 堆 │  │   永久代    │ │        │ │  Java 堆 │  ← 类元数据     │
│ │         │  │ (类元数据)  │ │        │ └─────────┘     被移出去了  │
│ └─────────┘  └────────────┘ │        ├─────────────────────────────┤
└─────────────────────────────┘        │      本地内存（OS 管理）       │
 互相挤占：堆要大了，                    │  ┌─────────────────────────┐│
 永久代就得让位，反之亦然                │  │ 元空间：类元数据住这里     ││
                                       │  └─────────────────────────┘│
                                       └─────────────────────────────┘
                                        -Xmx 再大也影响不到元空间
```

```bash
# 元空间常用参数
java -XX:MetaspaceSize=256m MyApp        # 触发首次元空间 GC 的阈值（注意：不是初始大小！）
java -XX:MaxMetaspaceSize=512m MyApp     # 元空间上限，超过抛 OOM: Metaspace（默认无上限，受物理内存限制）
```

> ⚠️ **注意（易错点）：** `-XX:MetaspaceSize` 是"高水位线"——分配超过它就触发 Full GC 并上调水位，**不是**初始占用大小。生产环境建议 `MaxMetaspaceSize` 显式设一个上限，防止类加载泄漏吃光系统内存。

### 四、运行时常量池

#### 1. 是什么

`.class` 文件里有一张 **常量池表（Constant Pool Table）**，存放编译期生成的字面量和符号引用。类加载后，这张表的内容进入方法区的**运行时常量池（Runtime Constant Pool）**：

| 类别 | 说明 | 示例 |
|------|------|------|
| 字面量 | 直接写死的值 | `"hello"`、`100`、`final` 常量 |
| 符号引用 | 用"名字"描述的引用，类加载解析时转为直接引用 | `java/lang/Object`、`sayHi:()V` |

#### 2. 具备动态性

与 Class 文件常量池最大的区别：运行时常量池**运行期间也能往里加常量**，典型就是 `String.intern()`：

```java
public class InternDemo {
    public static void main(String[] args) {
        // "java" 在常量池中已存在（JDK 内部使用），intern() 直接返回池中引用
        String a = new StringBuilder("ja").append("va").toString();
        System.out.println(a.intern() == a);   // false：a 在堆中，intern() 返回的是池里原有的引用

        String b = new StringBuilder("hello").append(" world").toString();
        System.out.println(b.intern() == b);   // true（JDK 7+）：池中原本没有 "hello world"，
                                               // intern() 把堆中这个对象的引用记录进池，返回的就是它
    }
}
```

> 💡 **提示：** `intern()` 的行为在 JDK 6 和 JDK 7+ 不同：JDK 6 常量池在永久代，intern 会**复制**字符串到永久代；JDK 7 起常量池在堆中，intern 只是**记录首次出现对象的引用**，不再复制。这是 `new String("a")` 到底创建几个对象、`==` 比较结果等面试题的版本前提。

### 五、字符串常量池

字符串常量池（String Pool）是运行时常量池中最重要的部分，**位置随版本变迁**：

| JDK 版本 | 位置 | 原因 |
|---------|------|------|
| JDK 6 | 方法区（永久代） | —— |
| **JDK 7+** | **堆** | 永久代 GC 效率低（Full GC 才回收），字符串大量创建容易撑爆永久代；移到堆后可被 Minor GC 及时回收 |

```java
public class StringPoolDemo {
    public static void main(String[] args) {
        String s1 = "abc";            // 字面量：直接引用字符串常量池中的 "abc"（池里没有则先创建）
        String s2 = "abc";            // 池中已存在，直接复用
        String s3 = new String("abc"); // new：在堆中新造一个 String 对象，内容仍是 "abc"

        System.out.println(s1 == s2);        // true：同一池中引用
        System.out.println(s1 == s3);        // false：new 出来的是堆中的新对象
        System.out.println(s1 == s3.intern()); // true：intern() 返回池中引用
    }
}
```

字符串常量池的设计动机：字符串是程序中使用最频繁的数据，**同一个字面量全局只存一份**，能大幅节省内存。

> ⚠️ **注意：** 比较 String 内容一律用 `equals()`，`==` 比较的是引用是否同一对象——而"是否同一对象"取决于字符串是否来自常量池，极易踩坑。

### 六、方法区会垃圾回收吗？

会，但条件苛刻、收益不稳定，这也是"永久代 GC 效率低"的根源。方法区主要回收两类**废弃内容**：

| 回收对象 | 判定条件 |
|---------|---------|
| **废弃常量** | 常量池中的常量没有任何引用指向它（如 `"abc"` 已无任何 String 引用），即可清理 |
| **无用类** | 需同时满足三个条件：① 该类所有实例都已回收；② 加载它的 ClassLoader 已被回收；③ 对应的 `Class` 对象没有任何地方引用（无法通过反射访问） |

> ⚠️ **注意：** 无用类只是"**允许**"回收，JVM 可以选择不回收（HotSpot 默认不主动回收无用的类，除非 `-Xnoclassgc` 关闭类卸载或元空间紧张）。**方法区回收效率远低于堆**，这正是 JDK 7 把字符串常量池移到堆、JDK 8 干脆用元空间替代永久代的深层原因之一。

### 七、与相关区域的关联

| 关联对象 | 关系 |
|---------|------|
| **堆** | 堆中对象的对象头含类型指针 → 指向方法区的类元数据，对象据此知道"我是谁"；静态变量与 Class 对象（JDK 7+）实际存放在堆中 |
| **虚拟机栈** | 栈帧的动态链接引用方法区运行时常量池中的符号引用，方法调用由此解析 |
| **类加载** | 类加载的"加载、验证、准备、解析、初始化"全过程，产出物就落在方法区；详见 [07-类加载机制.md](./07-类加载机制.md) |
| **反射** | `Class` 对象是反射入口，而它就由类加载产生、与类元数据关联；详见 [../反射.md](../反射.md) |

### 八、常见问题与注意事项

#### Q1：方法区、永久代、元空间是什么关系？

方法区是 JVM 规范定义的**接口**，永久代和元空间是 HotSpot 的两个**实现版本**：JDK 7- 用永久代，JDK 8+ 用元空间。说"方法区"时指概念，谈版本细节时才区分实现。

#### Q2：静态变量到底存哪里？

逻辑上属于方法区（随类存在、全局共享）。物理上 JDK 7 起已移入**堆**，存放在 `java.lang.Class` 对象中。面试建议：先说"逻辑上方法区"，再补充"JDK 7+ 实现在堆中"，体现版本视野。

#### Q3：什么情况会遇到 `OutOfMemoryError: Metaspace`？

动态生成大量类且无法卸载时：CGLib/Byte Buddy 动态代理生成海量类、反射频繁调用生成委托类、热部署应用反复加载不同版本的类。解法：检查类生成逻辑，或用 `-XX:MaxMetaspaceSize` 限制并配合 dump 分析。

### 九、总结

| 知识点 | 核心要点 |
|--------|---------|
| 定位 | 线程共享，存"类相关的一切"：类元信息、常量池、静态变量、JIT 代码 |
| 演变 | 永久代（JVM 内存，易 OOM）→ 元空间（JDK 8+，本地内存） |
| 运行时常量池 | 编译期常量 + 运行期动态添加（`intern()`） |
| 字符串常量池 | JDK 6 在永久代，JDK 7+ 移入堆，全局唯一字面量 |
| GC | 可回收，但条件苛刻（无用类三条件）、效率低 |
| 异常 | JDK 8+ 为 `OOM: Metaspace`；参数 `-XX:MaxMetaspaceSize` |

**记住三句话**：

1. **方法区是概念，永久代/元空间是实现；JDK 8 起类元数据住本地内存。**
2. **字符串常量池 JDK 7 起在堆里，`intern()` 行为随版本变了。**
3. **静态变量逻辑上属于方法区，物理上 JDK 7 起在堆中——逻辑与实现分离是 JVM 的常态。**
