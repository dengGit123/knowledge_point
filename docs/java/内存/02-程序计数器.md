# 程序计数器（Program Counter Register）

> 📖 官方文档：[The Java Virtual Machine Specification - The pc Register](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-2.html#jvms-2.5.1)

---

### 一、概述

**程序计数器**（也叫 PC 寄存器）是一块很小的内存空间，可以看作当前线程所执行的字节码的**行号指示器**。它记录着线程"当前执行到了哪一条字节码指令"。

> 💡 **通俗理解**：程序计数器就像看书记录的"书签"。CPU 在多个线程之间来回切换（时间片轮转），每次切回来都得知道"我刚才读到哪一行了"——这个书签就是程序计数器。没有它，线程切换回来就会"忘了读到哪"，从头再读一遍。

它是五个运行时数据区中**最小**的一块，也是**唯一**在《Java 虚拟机规范》中没有规定任何 `OutOfMemoryError` 情况的区域。

### 二、工作原理

#### 1. 它记录的是什么？

Java 源代码编译后会变成字节码，每条字节码指令都有一个**地址（偏移量）**。程序计数器存的就是**下一条待执行指令的地址**。

```java
// 源代码
public int add(int a, int b) {
    return a + b;
}
```

```text
; 对应的字节码（javap -c 反编译查看）
0: iload_1        ← 字节码偏移量 0
1: iload_2        ← 偏移量 1
2: iadd           ← 偏移量 2
3: ireturn        ← 偏移量 3
```

线程执行到 `iadd` 时，程序计数器的值就是 `3`——指向下一条指令 `ireturn`。字节码解释器工作时，就是**不断改变程序计数器的值**来选取下一条要执行的指令，实现分支、循环、跳转、异常处理、线程恢复。

#### 2. 为什么必须线程私有？

CPU 对多线程是**抢占式调度**的：任意时刻一个核只能执行一个线程，时间片用完就切到别的线程，稍后再切回来。

```
CPU 时间线：  ──[线程A 执行]──[线程B 执行]──[线程A 恢复]──→
                        ▲                 ▲
                  A 被暂停，A 的程序计数器      A 恢复，读自己的
                  记住"执行到第 88 行"          计数器：从 88 行继续
```

如果程序计数器是共享的，线程 A 暂停时计数器会被线程 B 改掉，A 恢复时就不知道该从哪继续了。所以**每个线程都有独立的程序计数器**，各记各的进度，互不干扰。

### 三、核心特点

| 特点 | 说明 |
|------|------|
| 线程私有 | 每个线程一个，线程启动时创建，线程结束时销毁 |
| 生命周期 | 与线程相同 |
| 大小固定 | 只需存一个指令地址，内存占用极小 |
| **唯一不会 OOM** | 规范中没有任何区域会OutOfMemoryError 的描述，也没有 `StackOverflowError` |
| 执行 Native 方法时 | 计数器值为 `undefined`（未定义）——Native 方法由本地（C/C++）直接执行，不经过字节码 |
| 执行 Java 方法时 | 记录正在执行的字节码指令地址 |

> 💡 **提示：** "Native 方法时值为 undefined" 是个高频面试点。`Object.hashCode()`、`Thread.start()` 底层都是 Native 方法，执行它们时字节码层面没有"下一条指令"的概念，所以计数器为空。

### 四、与执行引擎的关系

程序计数器不参与任何运算，它只是执行引擎的"进度条"：

```
┌────────────┐    取下一条指令（地址来自 PC）    ┌────────────┐
│  程序计数器  │ ───────────────────────────→ │  执行引擎    │
│  PC = 3     │                              │  解释器/JIT  │
│             │ ←──────────────────────────── │  执行一条指令 │
│             │        PC 更新为下一条地址      └────────────┘
└────────────┘
```

- **字节码解释器**：逐条取指令执行，每执行完一条就把 PC 指向下一条。
- **JIT 即时编译**：热点代码被编译成机器码后整体执行，此时 PC 的作用依然是标记执行位置（粒度变为本地代码段）。

### 五、常见问题与注意事项

#### Q1：程序计数器会内存溢出吗？

不会。它只存一个地址，大小固定且极小，是 JVM 规范中**唯一**没有定义 `OutOfMemoryError` 的区域。栈会 `StackOverflowError`，堆会 OOM，唯独它不会。

#### Q2：它是物理 CPU 寄存器吗？

不完全是。"Register" 只是沿用了汇编术语。字节码解释器实现时它通常就是一块普通内存；JIT 编译执行时则真的会用到物理寄存器（如 x86 的 `rip` 指令指针）。对 Java 程序员来说，只需理解它抽象上表示"当前执行位置"。

#### Q3：Java 代码能访问它吗？

不能。它完全是 JVM 内部使用的，没有任何 Java API 能读写程序计数器。这与堆（可通过引用访问）、栈（局部变量可见）不同。

### 六、总结

| 知识点 | 核心要点 |
|--------|---------|
| 是什么 | 当前线程所执行字节码的行号指示器 |
| 为什么私有 | 线程切换后必须能恢复到正确执行位置，各记各的进度 |
| 执行 Java 方法 | 记录字节码指令地址 |
| 执行 Native 方法 | 值为 `undefined` |
| 异常 | 唯一不会 `OutOfMemoryError` / `StackOverflowError` 的区域 |

**记住一句话**：程序计数器是线程的"书签"，小到没有溢出风险，私有到人手一份，Native 方法一执行就"失明"（undefined）。
