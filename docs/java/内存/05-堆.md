# 堆（Heap）

> 📖 官方文档：[The Java Virtual Machine Specification - Heap](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-2.html#jvms-2.5.3) ｜ [HotSpot GC Tuning Guide - Generations](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-collector-implementation.html)

---

### 一、概述

**堆（Heap）** 是 JVM 管理的**最大**一块内存区域，随虚拟机启动而创建，被**所有线程共享**。它的唯一使命：存放**几乎所有对象实例和数组**——只要写了 `new`，产出的对象就躺在堆里。

堆也是**垃圾回收（GC）的主战场**，所以又叫"GC 堆"（Garbage-Collected Heap）。后续要学的分代回收、Minor GC / Full GC、各种垃圾收集器，全都围绕这块区域展开。

> 💡 **通俗理解**：堆就是"成品仓库"。所有 `new` 出来的商品（对象）先入库，贴上"生产日期"（GC 分代年龄），没人认领的（不可达对象）定期被清理员（GC）搬走。仓库还分了"新货架区"（新生代）和"老货架区"（老年代），管理更有章法。

### 二、核心特点

| 特点 | 说明 |
|------|------|
| 线程共享 | 所有线程都能访问堆中的对象——这也是线程安全问题（可见性、竞争）的根源 |
| 生命周期 | 与 JVM 相同：虚拟机启动时创建，退出时销毁 |
| 大小可调 | `-Xms` 初始大小、`-Xmx` 最大大小；`-Xms` = `-Xmx` 可避免动态扩容抖动 |
| 物理上可不连续 | 逻辑上连续即可（大堆在服务器上通常由多个不连续的内存块组成） |
| GC 主战场 | 绝大多数垃圾收集发生在这里，内部分代就是为了更高效地回收 |
| 异常 | 分配对象时空间不足抛 `OutOfMemoryError: Java heap space` |

```bash
# 常用堆参数
java -Xms2g -Xmx2g MyApp     # 初始堆 2GB，最大堆 2GB（生产环境推荐两者相等）
java -Xmn512m MyApp          # 新生代 512MB（Sun 官方建议为新堆大小的 3/8）
java -XX:NewRatio=2          # 老年代 : 新生代 = 2 : 1（即新生代占堆 1/3）
java -XX:SurvivorRatio=8     # Eden : Survivor0 : Survivor1 = 8 : 1 : 1
```

### 三、分代设计：新生代与老年代

堆并不是"一锅粥"，HotSpot 按对象**存活时间**把它划分成两代（JDK 8 默认分代；JDK 8u+ 已可用 G1，JDK 9+ 默认 G1——G1 逻辑上依然有分代概念，只是物理布局变成一个个 Region）：

```
┌───────────────────────── 堆（Heap）───────────────────────────┐
│                            │                                  │
│      新生代（Young）        │         老年代（Old）             │
│  ┌─────────┬─────┬─────┐  │                                  │
│  │  Eden   │ S0  │ S1  │  │   存放"熬过多次 GC"的对象          │
│  │   8     │  1  │  1  │  │   以及大对象（直接进入）            │
│  └─────────┴─────┴─────┘  │                                  │
│   默认比例 8 : 1 : 1        │   默认占堆 2/3                    │
│   默认占堆 1/3              │                                  │
└────────────────────────────┴──────────────────────────────────┘
```

| 区域 | 存放内容 | 回收方式 | 回收频率 |
|------|---------|---------|---------|
| **Eden 区** | 绝大多数新对象出生在这里 | Minor GC（复制算法） | 频繁、速度快 |
| **Survivor 区**（S0/S1） | 从 Eden 熬过一次 Minor GC 的对象 | Minor GC | 频繁 |
| **老年代** | 年龄达标（默认 15 岁）的对象、大对象 | Major GC / Full GC（标记-清除或标记-整理） | 较少、慢 |

#### 为什么新生代用 8:1:1 的比例？

IBM 研究发现：新生代里 **98% 的对象"朝生夕灭"**，熬不过第一次 GC。所以不需要按 1:1 划分两块内存做复制算法，而是划出 **一块 Eden + 两块小的 Survivor**：

- 新对象只分配在 Eden 和一块 Survivor（S0）；
- GC 时把存活对象复制到另一块 Survivor（S1），然后 Eden 和 S0 整体清空；
- 浪费的内存只有 10%（一块 Survivor），而不是复制算法原本的 50%。

> 💡 **提示：** 两块 Survivor 的大小必须一样大，因为它们轮流当"幸存者安置区"。`-XX:SurvivorRatio=8` 控制 Eden 占新生代的 8/10，S0 和 S1 各占 1/10。

### 四、对象的一生：在堆中如何流转

跟踪一个对象从出生到死亡（或长生不死）的完整轨迹：

```
 new Object()
      │
      ▼
┌─────────┐  Eden 满了，触发 Minor GC
│  Eden   │ ──────────────────────────┐
└─────────┘                           ▼
                            存活对象复制到 S1，年龄+1
                            Eden 和 S0 一次性清空
                                      │
                                      ▼ 每熬过一次 Minor GC，年龄 +1
                     ┌──────── S0 ⇄ S1 反复倒腾 ────────┐
                     │                                  │
                     │ 年龄达到阈值（默认 15）            │ 对象太大
                     ▼                                  ▼ （超过 -XX:PretenureSizeThreshold）
              ┌─────────────┐                    ┌─────────────┐
              │   老年代     │ ←── 大对象直接进入 ──│             │
              └─────────────┘                    └─────────────┘
                     │
                     ▼ 空间不足时触发 Major GC / Full GC
              回收不可达对象；空间仍不足 → OutOfMemoryError
```

几个关键机制：

#### 1. 年龄阈值与动态晋升

- 对象每熬过一次 Minor GC，年龄 +1，达到 **15**（默认，`-XX:MaxTenuringThreshold` 可调）就晋升老年代。
- HotSpot 的对象头（Mark Word）中用 **4 位存储年龄**，所以上限是 15（`0b1111`），设大了无效。
- **动态年龄判定**：Survivor 中某年龄以下对象的总大小超过 Survivor 一半，该年龄及以上的对象直接晋升，不必等到 15 岁。

#### 2. 大对象直接进老年代

大对象（如超长数组、大字符串）直接在老年代分配，避免在新生代来回复制（复制成本高）。`-XX:PretenureSizeThreshold`（仅 Serial 和 ParNew 收集器生效）可设置阈值。

> ⚠️ **注意：** "朝生夕灭的小对象放新生代、长命对象放老年代"是分代假设。如果代码里大量短期大对象（如一次性的大数组）也进了老年代，会加速老年代填满、频繁触发 Full GC——这是典型的反模式。

#### 3. 空间分配担保

Minor GC 前，老年代要为"Survivor 装不下的存活对象"做担保：若老年代可用空间小于历次晋升的平均大小，就会先触发一次 Full GC 腾地方。

### 五、TLAB：堆中的"私有小地盘"

堆是共享的，但对象分配是极高频操作——所有线程都往 Eden 里抢地方，加锁太慢。JVM 的优化方案是 **TLAB（Thread Local Allocation Buffer，线程本地分配缓冲区）**：

```
┌─────────────────────── Eden ─────────────────────────┐
│ ┌────────────┐  ┌────────────┐  ┌────────────┐       │
│ │ TLAB 线程A  │  │ TLAB 线程B  │  │  公共区域    │       │
│ │（私有，不加锁）│ │（私有，不加锁）│  │（加锁分配）  │       │
│ └────────────┘  └────────────┘  └────────────┘       │
└──────────────────────────────────────────────────────┘
```

- 每个线程在 Eden 中预分配一小块私有缓冲区，线程在自己的 TLAB 里分配对象**不需要任何同步**；
- TLAB 装不下时，退回公共区域加锁分配（CAS），或重新申请新 TLAB；
- 默认开启（`-XX:+UseTLAB`），占 Eden 的比例约 1%——这是 Java 对象分配速度极快（接近栈分配）的关键。

> 💡 **提示：** TLAB 只解决"分配快不快"，不改变语义：对象仍然在堆（Eden）里，仍然对所有线程可见，只是"分地盘"这个动作私有了。

### 六、堆溢出实战（OOM 复现思路）

堆放不下新对象时抛 `OutOfMemoryError: Java heap space`。典型诱因：

```java
import java.util.ArrayList;
import java.util.List;

public class HeapOOM {
    public static void main(String[] args) {
        List<byte[]> list = new ArrayList<>();
        while (true) {
            // 每次申请 1MB 且一直持有引用（list 活着 → 对象可达 → GC 无法回收）
            list.add(new byte[1024 * 1024]);
        }
    }
}
// 运行：java -Xms20m -Xmx20m HeapOOM
// 结果：java.lang.OutOfMemoryError: Java heap space
```

排查思路：

| 排查手段 | 说明 |
|---------|------|
| `-XX:+HeapDumpOnOutOfMemoryError` | OOM 时自动生成堆转储文件（`.hprof`） |
| `-XX:HeapDumpPath=/path/` | 指定转储文件输出目录 |
| `jmap -dump:live,format=b,file=heap.hprof <pid>` | 手动抓取堆快照 |
| MAT / VisualVM / JProfiler | 分析 `.hprof`，找到占用最大的是哪类对象、谁在引用它们 |

> ⚠️ **内存溢出（OOM）vs 内存泄漏（Memory Leak）**：
> - **内存泄漏**：对象已经没用了，却还被引用着，GC 收不走（如静态集合只 add 不 remove）。泄漏不断积累，最终耗尽堆。
> - **内存溢出**：堆真的不够用了。泄漏是 OOM 的最常见原因之一。
>
> 排查口诀：先用 `-Xmx` 调大堆应急，再用 heap dump 找根因。详见 [11-内存溢出与泄漏排查.md](./11-内存溢出与泄漏排查.md)。

### 七、与相关区域的关联

| 关联对象 | 关系 |
|---------|------|
| **虚拟机栈** | 栈中局部变量存的是"指向堆对象的地址"，栈是入口、堆是实体 |
| **方法区** | 堆中每个对象的对象头里有类型指针，指向方法区的类元数据；字符串常量池（JDK 7+）也位于堆中 |
| **垃圾回收** | 堆是 GC 的绝对主战场，分代设计就是为了配合"朝生夕灭"的对象分布规律 |
| **直接内存** | 不属于堆，但常和堆做对比：NIO 的堆外内存绕过堆，避免复制开销 |

### 八、总结

| 知识点 | 核心要点 |
|--------|---------|
| 定位 | 最大内存区、线程共享、GC 主战场、`new` 出来的东西都在这 |
| 分代 | 新生代（Eden:S0:S1 = 8:1:1）+ 老年代（默认 2:1 占比） |
| 对象流转 | Eden 出生 → Survivor 倒腾 → 15 岁晋升老年代；大对象直接进老年代 |
| TLAB | Eden 里的线程私有缓冲区，让对象分配不用加锁 |
| 异常 | `OutOfMemoryError: Java heap space`，用 heap dump 定位元凶 |
| 参数 | `-Xms`/`-Xmx` 堆大小、`-Xmn` 新生代、`-XX:SurvivorRatio`、`-XX:MaxTenuringThreshold` |

**记住三句话**：

1. **`new` 出来的都在堆，堆被所有线程共享，堆是 GC 唯一的主战场。**
2. **新生代复制算法（Eden + 双 Survivor），老年代标记-清除/整理，15 岁晋升。**
3. **`-Xms` = `-Xmx` 防抖动，OOM 先 dump 再分析，别急着无脑调大堆。**
