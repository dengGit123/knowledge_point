# 类加载机制

> 📖 官方文档：[The Java Virtual Machine Specification - Class Loading, Linking, and Initializing](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html) ｜ [Class Loaders Guide (Oracle)](https://docs.oracle.com/en/java/javase/21/docs/specs/jvmti.html#ClassLoader)

---

### 一、概述

Java 代码要运行，`.java` 先被编译成 `.class` 字节码文件；但字节码本身是"静态数据"，必须由 JVM **加载进内存、验证、准备、解析、初始化**之后才能执行。这个把静态字节码变成"活的类"的过程，就是**类加载机制（Class Loading）**。

类加载是连接**编译期**与**运行期**的桥梁。它决定了：

- **静态代码块**什么时候执行、执行几次（见 [09-代码块与初始化顺序.md](./09-代码块与初始化顺序.md)）；
- **方法区**里什么时候多出一份类元数据（见 [06-方法区.md](./06-方法区.md)）；
- `new` 一个对象之前，JVM 为什么要先做"类加载检查"（见 [08-对象在内存中.md](./08-对象在内存中.md)）。

> 💡 **通俗理解**：类加载就像"新员工入职流程"——先把简历（`.class` 文件）收进来（加载），再背调核实简历真伪（验证），分配工位并初始化办公用品（准备），办理门禁把"工号"换成"人脸识别"（解析），最后正式上岗第一天做迎新培训（初始化）。整个流程走完，这名"员工"（类）才能被派活。

### 二、类的生命周期

一个类从进入 JVM 到被卸载，共经历 7 个阶段。前 5 个（加载→初始化）就是"类加载过程"：

```
 ┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐   ┌────────┐   ┌──────┐   ┌──────┐
 │ 加载  │ → │ 验证  │ → │ 准备  │ → │ 解析  │ → │ 初始化  │ → │ 使用  │ → │ 卸载  │
 └──────┘   └──────┘   └──────┘   └──────┘   └────────┘   └──────┘   └──────┘
 Loading   Verifying  Preparing   Resolving  Initializing   Using    Unloading
 └────────── 连接（Linking）──────────┘
```

其中**解析**阶段不一定紧跟着准备——它可以在初始化之后再触发（支持 Java 的**运行期绑定/晚绑定**，即多态）。数组类（如 `int[]`）不经过类加载器创建，由 JVM 直接在内存中动态构造。

### 三、类加载过程详解

#### 1. 加载（Loading）

把 Class 文件的字节流读入内存，做了三件事：

1. 通过类的**全限定名**（如 `java.lang.String`）获取定义此类的二进制字节流；
2. 把字节流的静态结构转化为方法区的**运行时数据结构**（类元信息）；
3. 在堆中生成一个 `java.lang.Class` 对象，作为访问这份元数据的入口（反射的基础）。

字节流的来源非常灵活——这正是各种动态技术的入口：

```java
// 来源 1：本地文件系统（最常见）
// 来源 2：JAR/WAR 包
// 来源 3：网络（Applet 时代）
// 来源 4：运行时动态生成（动态代理 CGLib/Byte Buddy、反射生成）
// 来源 5：数据库（某些中间件把类存在库里）
Class<?> clazz = Class.forName("com.demo.Person");   // 反射触发类加载
```

#### 2. 验证（Verification）

确保字节流符合 JVM 规范，防止恶意或损坏的字节码危害 JVM。包含四轮校验：

| 校验类型 | 检查内容 |
|---------|---------|
| 文件格式验证 | 魔数 `0xCAFEBABE`、版本号、常量池结构是否合法 |
| 元数据验证 | 语义合法性：有无父类、是否继承了 `final` 类、抽象方法实现是否完整 |
| 字节码验证 | 最复杂：数据流与控制流分析，确保跳转指令不会跳到方法体外等 |
| 符号引用验证 | 全限定名能否找到对应类、字段/方法的访问权限是否合法 |

#### 3. 准备（Preparing）

为**静态变量**分配内存并设置**零值**——注意是零值，不是代码里写的值！

```java
public class PrepareDemo {
    public static int a = 10;          // 准备阶段：a = 0（零值）；赋 10 要等初始化阶段
    public static final int B = 20;    // 准备阶段：B = 20（final 常量直接赋指定值）

    public static String s = "hi";     // 准备阶段：s = null；"hi" 在初始化阶段才赋值
}
```

> ⚠️ **注意（高频考点）：** `static int a = 10` 在准备阶段是 `0`，初始化阶段才变成 `10`。只有 `static final` 常量（ConstantValue 属性）会在准备阶段直接赋指定值。这也是"静态变量为什么有默认值"的原因——零值初始化发生在准备阶段。

#### 4. 解析（Resolving）

把常量池中的**符号引用**替换为**直接引用**：

- **符号引用**：用一组"名字"来描述目标（如 `java/lang/Object`），与内存布局无关；
- **直接引用**：指向目标的指针、相对偏移量或句柄，与内存布局直接相关。

解析时机灵活：JVM 规范允许初始化之后再解析（晚绑定），以支持多态——运行时才知道 `p.sayHi()` 调用的是哪个实现。

#### 5. 初始化（Initializing）

类加载的最后一步：执行静态变量赋值和静态代码块，编译器把它们收集成 **`<clinit>()` 方法**（类构造器）：

- `<clinit>()` 由编译器自动生成：收集**所有静态变量的显式赋值语句 + 静态代码块**，按**源码书写顺序**执行；
- JVM 保证 `<clinit>()` 在多线程下**只执行一次且加锁**——这是"单例模式利用类加载实现线程安全"的原理；
- 接口没有静态代码块，但可以有静态变量初始化，同样生成 `<clinit>()`（接口初始化不要求父接口先初始化）。

```java
public class ClinitDemo {
    static int a = 1;                       // ① 进入 <clinit>()：a = 1
    static {                                // ② 仍是 <clinit>() 的一部分，顺序执行
        System.out.println("静态代码块, a=" + a);
    }
    static int b = 2;                       // ③ 也在 <clinit>() 中，排在静态代码块之后
}
// 初始化阶段执行顺序：a=1 → 静态代码块 → b=2（严格按源码顺序）
```

### 四、类初始化的触发时机（主动引用 vs 被动引用）

JVM 规范规定：**有且只有 6 种情况**必须立即对类进行初始化（主动引用），其余都算被动引用，**不触发**初始化。

| 主动引用（触发初始化） | 被动引用（不触发） |
|----------------------|-------------------|
| `new`、读取/设置静态字段（非 `final` 常量）、调用静态方法 | 通过子类引用父类的静态字段（只初始化父类） |
| 反射调用：`Class.forName("...")` | 定义类数组：`Person[] arr` |
| 初始化一个类时，父类尚未初始化（先触发父类初始化） | 引用编译期常量：`Person.MAX`（`static final`，常量已进调用方常量池） |
| 虚拟机启动时初始化主类（`main` 所在类） | —— |
| `MethodHandle` 句柄对应的类未初始化 | —— |
| 接口含默认方法时，实现类初始化前先初始化接口 | —— |

```java
public class PassiveRefDemo {
    static class Father {
        public static int VALUE = 100;                    // 非 final，主动引用才触发
        static { System.out.println("Father 初始化"); }
    }

    static class Son extends Father {
        static { System.out.println("Son 初始化"); }
    }

    public static void main(String[] args) {
        System.out.println(Son.VALUE);  // 只输出 "Father 初始化" 和 100
                                        // 对于静态字段，只有直接定义该字段的类才被初始化
    }
}
```

### 五、类加载器与双亲委派模型

#### 1. 三层类加载器

| 类加载器 | 负责加载 | 实现语言 |
|---------|---------|---------|
| **Bootstrap ClassLoader**（启动类加载器） | `JAVA_HOME/lib` 核心库（如 `rt.jar`，JDK 9+ 为模块系统） | C++（JVM 自身一部分） |
| **Platform ClassLoader**（平台类加载器，JDK 9+；JDK 8 为 Extension） | 平台核心类库（JDK 8：`lib/ext`） | Java |
| **Application ClassLoader**（应用程序类加载器） | 用户类路径 classpath 上的类，默认加载器 | Java |

```java
public class LoaderDemo {
    public static void main(String[] args) {
        // 输出 null：Bootstrap 加载器由 C++ 实现，Java 层拿不到它的引用
        System.out.println(String.class.getClassLoader());

        System.out.println(LoaderDemo.class.getClassLoader());
        // 输出 jdk.internal.loader.ClassLoaders$AppClassLoader（JDK 9+）

        // 打印加载器链条：App → Platform → Bootstrap
        ClassLoader cl = LoaderDemo.class.getClassLoader();
        while (cl != null) {
            System.out.println(cl);
            cl = cl.getParent();
        }
    }
}
```

#### 2. 双亲委派模型（Parents Delegation Model）

类加载器收到加载请求时，**先委派给父加载器**，父加载器搞不定才自己动手：

```
自定义类加载器
     │ 委派 ↑      ↓ 失败才自己加载
Application ClassLoader
     │ 委派 ↑      ↓ 失败才自己加载
Platform ClassLoader
     │ 委派 ↑      ↓ 失败才自己加载
Bootstrap ClassLoader  ← 顶层，失败（找不到类）则一路返回
```

**工作流程**：收到请求 → 先问父加载器 → 层层上抛到 Bootstrap → 父加载器在自己的范围内找不到 → 逐层下放 → 最终由某个子加载器实际加载。

**这样设计的好处**：

1. **安全**：用户自己写一个 `java.lang.String` 也不会生效——委派到 Bootstrap 后发现已有同名的，直接返回核心库的版本，防止核心 API 被篡改；
2. **避免重复**：同一个类只会被同一个加载器加载一次，保证类的唯一性。

> ⚠️ **注意：** "同一个类"的唯一性判据是 **加载器 + 全限定名**。同一个 `.class` 被两个不同的加载器加载，会得到两个互不相干的 `Class` 对象——OSGi、Tomcat 多应用隔离正是利用了这一点。

#### 3. 打破双亲委派的场景

并非所有场景都遵守双亲委派，常见的"破坏者"：

| 场景 | 做法 |
|------|------|
| SPI（JDBC、JNDI） | 核心库（Bootstrap 加载）需要加载厂商实现类，用**线程上下文类加载器**反向委派给 Application 加载器 |
| Tomcat | 每个 Web 应用独立 `WebAppClassLoader`，**先自己加载**（隔离应用依赖），失败才委派 |
| OSGi / 热部署 | 网状委派 + 自定义加载器，实现模块级热替换 |
| 自定义加载器 | 重写 `loadClass()`（不委派）或只重写 `findClass()`（仍遵守委派） |

### 六、类的卸载

类被卸载需**同时满足**三个条件（相当苛刻）：

1. 该类**所有实例**都已被回收（堆中不存在）；
2. 加载该类的 **ClassLoader** 已被回收；
3. 该类对应的 **`Class` 对象**没有任何引用（无法通过反射访问）。

由 Bootstrap 加载的核心类（`String`、`Object` 等）永远不会被卸载（Bootstrap 加载器本身无法被回收）。这也是热部署/动态代理场景容易 `Metaspace` OOM 的原因——类被反复加载却无法卸载，元空间持续膨胀。

### 七、与相关概念的关联

| 关联知识点 | 关系 |
|-----------|------|
| **方法区** | 类加载的"产物"就落在方法区：类元信息、运行时常量池 |
| **对象创建** | `new` 的第一步是"类加载检查"——没加载先触发加载 |
| **静态代码块** | 执行时机 = 初始化阶段 = `<clinit>()` 执行，且只执行一次 |
| **单例模式** | 静态内部类单例利用"`<clinit>()` 线程安全且只执行一次"实现懒加载 |
| **反射** | `Class.forName()` 显式触发类加载，`Class` 对象是反射入口 |

### 八、总结

| 知识点 | 核心要点 |
|--------|---------|
| 生命周期 | 加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载 |
| 准备阶段 | 静态变量赋**零值**；`static final` 常量直接赋指定值 |
| 初始化阶段 | 执行 `<clinit>()`（静态赋值 + 静态代码块，按源码顺序） |
| 主动引用 | 6 种情况触发初始化（`new`、反射、`main` 类等） |
| 双亲委派 | 先委派父加载器，保证核心类安全、类不重复加载 |
| 类卸载 | 三条件同时满足，核心类永不卸载 |

**记住三句话**：

1. **准备阶段是零值，初始化阶段才是你写的值；`static final` 是例外。**
2. **`<clinit>()` 由编译器收集静态赋值和静态代码块生成，JVM 保证它线程安全且只执行一次。**
3. **双亲委派：先问爸爸，爸爸不行再自己上——核心类安全、类不重复。**
