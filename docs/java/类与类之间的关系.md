# 类与类之间的关系

> 参考资源：
> - [Oracle Java Tutorials - 继承、接口与多态](https://docs.oracle.com/javase/tutorial/java/IandI/index.html)
> - [菜鸟教程 - UML 类图](https://www.runoob.com/design-pattern/design-pattern-tutorial.html)
> - [UML 2.5.1 官方规范（OMG）](https://www.omg.org/spec/UML/2.5.1/)

## 一、概述

类不是孤岛。一个真实的 Java 项目里，成百上千个类之所以能协作成一个系统，靠的就是类与类之间的**关系**。把这些关系梳理清楚，是看懂别人代码、设计自己代码的第一步。

UML（统一建模语言）把类之间的关系归纳为 **6 种**，按耦合程度从弱到强排列：

```
依赖 ──→ 关联 ──→ 聚合 ──→ 组合
(最弱)                    (最强)

泛化（继承）、实现（接口）是两种纵向关系
```

| 关系 | 一句话理解 | 通俗类比 | Java 代码体现 | 耦合度 |
| --- | :---: | :---: | :---: | :---: |
| 依赖（Dependency） | use-a（用一下） | 借朋友的车开 | 局部变量、方法参数、静态方法调用 | ⭐ |
| 关联（Association） | has-a（长期拥有） | 我养了一只猫 | 成员变量 | ⭐⭐ |
| 聚合（Aggregation） | has-a（整体-部分，可分离） | 部门和员工 | 成员变量（生命周期独立） | ⭐⭐⭐ |
| 组合（Composition） | contains-a（整体-部分，同生共死） | 人和心脏 | 成员变量（生命周期绑定） | ⭐⭐⭐⭐ |
| 泛化（Generalization） | is-a（是一种） | 狗是一种动物 | `extends` | ⭐⭐⭐⭐⭐ |
| 实现（Realization） | is-a（能做某事） | 鸟实现了"会飞" | `implements` | ⭐⭐⭐⭐⭐ |

> 💡 **提示：** 记忆口诀——**横向看"用、有、聚、组"，纵向看"继、实"**。依赖和关联是"用与被用"，聚合和组合是"整体与部分"，泛化和实现是"父子与规范"。

## 二、如何理解：先分三个视角

六种关系乍看很多，其实可以从三个视角去理解，就不乱了：

1. **使用视角**——我只是"用"你：**依赖**
2. **拥有视角**——我长期"持有"你：**关联、聚合、组合**（聚合和组合是关联的两种特殊形式）
3. **归类视角**——我"是"你这一类：**泛化、实现**

```
        使用视角            拥有视角                归类视角
      ┌─────────┐   ┌──────────────────┐   ┌──────────────┐
      │  依赖    │   │ 关联 ⊃ 聚合 ⊃ 组合 │   │ 泛化 ｜ 实现  │
      └─────────┘   └──────────────────┘   └──────────────┘
       方法参数等        成员变量持有对方        extends / implements
      （临时用一下）     （长期持有引用）        （类型层面归属）
```

> 💡 **提示：** 判断两个类是什么关系，先问一句："A 需要 B 吗？怎么个需要法？"
> - 只是方法里用了一下 → **依赖**
> - 存成了成员变量长期用 → **关联**
> - 是"整体-部分"，但能拆开各过各的 → **聚合**
> - 是"整体-部分"，且同生共死 → **组合**
> - A 本身就是 B 的一种 → **泛化**
> - A 具备 B 定下的能力规范 → **实现**

## 三、六种关系详解

### 1. 依赖（Dependency）—— use-a

**概念**：一个类在**方法执行过程中临时用到**另一个类，用完即走，不持有长期引用。这是最弱、最临时性的关系。

**代码体现**（三种常见形态）：

```java
// 形态一：方法参数
public class Person {
    // Person 依赖 Car：只是 drive 方法执行时用到 Car，方法结束引用即消失
    public void drive(Car car) {
        car.run();
    }
}

// 形态二：方法内局部变量
public class Person {
    public void travel() {
        Car car = new Car();  // 局部变量，方法栈帧销毁后引用消失
        car.run();
    }
}

// 形态三：调用另一个类的静态方法（工具类是最典型的依赖）
public class OrderService {
    public BigDecimal calc(int price, int count) {
        // OrderService 依赖 BigDecimalUtil，只是借用它的静态方法
        return BigDecimalUtil.multiply(price, count);
    }
}
```

**UML 表示**：**虚线 + 箭头**，箭头指向被使用的类。

```
┌──────────┐        ┌──────┐
│  Person  │- - - -▶│  Car │
└──────────┘  依赖   └──────┘
```

**典型场景**：工具类调用、方法参数传值、`Utils` 类的使用。

> ⚠️ **注意：** 判断依赖 vs 关联，关键看**引用的存活时间**：方法执行完就没了是依赖；作为成员变量一直存在是关联。

### 2. 关联（Association）—— has-a

**概念**：一个类的成员变量持有另一个类的引用，两者是长期的、对等的协作关系。比依赖更强，是一种"长期拥有"。

**代码体现**：

```java
// 单向关联：Customer 持有 Address，Address 不知道 Customer 的存在
public class Customer {
    private String name;
    private Address address;  // 关联：成员变量长期持有
}

public class Address {
    private String city;
}
```

```java
// 双向关联：两边互相持有
public class Customer {
    private List<Order> orders;  // 客户持有订单
}

public class Order {
    private Customer customer;   // 订单也持有客户
}
```

**UML 表示**：**实线 + 箭头**（单向关联）；双向关联用不带箭头的实线。

```
┌──────────┐          ┌─────────┐
│ Customer │─────────▶│ Address │
└──────────┘  单向关联 └─────────┘

┌──────────┐          ┌─────────┐
│ Customer │◀────────▶│  Order  │
└──────────┘  双向关联 └─────────┘
```

**典型场景**：`订单-用户`、`学生-学校`、实体类之间的互相引用（如 JPA 的 `@ManyToOne`）。

关联还可以带**多重性（Multiplicity）**标注，说明"一个 A 对应几个 B"：

```
┌──────────┐  1        * ┌─────────┐
│ Customer │─────────────│  Order  │
└──────────┘             └─────────┘
   一个客户可以下多个订单（1 对多）
```

### 3. 聚合（Aggregation）—— 弱 has-a，可分离的整体-部分

**概念**：整体与部分的关系，但**部分可以独立于整体存在**。整体"拥有"部分，却不掌控部分的生命周期——整体没了，部分照样活。

**代码体现**：

```java
public class Department {
    private String deptName;
    // 聚合：部门聚合了员工，但员工对象不是部门创建的（外部传入），
    // 部门解散了，员工对象依然存在，可以去别的部门
    private List<Employee> employees;

    public Department(List<Employee> employees) {
        this.employees = employees;  // ✅ 从外部注入，不负责员工的创建与销毁
    }
}
```

**UML 表示**：**实线 + 空心菱形**，菱形放在**整体一端**。

```
┌───────────┐ ◇          ┌──────────┐
│ Department│────────────│ Employee │
└───────────┘  聚合      └──────────┘
   （整体）                   （部分）
```

**典型场景**：`部门-员工`、`班级-学生`、`汽车-轮胎`（轮胎拆下来能装到别的车上）。

### 4. 组合（Composition）—— 强 has-a，同生共死的整体-部分

**概念**：更强的整体-部分关系，**部分不能脱离整体存在**。整体负责部分的创建，整体消亡时部分随之消亡。

**代码体现**：

```java
public class Human {
    private String name;
    // 组合：心脏是"人"这个整体自己 new 出来的、私有的、不可共享的；
    // 人没了，这个心脏对象也就没有意义、随之销毁
    private Heart heart = new Heart();  // ✅ 整体自己创建部分

    public Human(String name) {
        this.name = name;
    }
}

public class Heart {
    private int beatRate = 75;
}
```

**UML 表示**：**实线 + 实心菱形**，菱形同样放在**整体一端**。

```
┌──────┐ ◆         ┌──────┐
│Human │───────────│ Heart│
└──────┘  组合     └──────┘
 （整体）             （部分）
```

**典型场景**：`人-心脏`、`公司-部门`（公司注销，部门不复存在）、`窗口-按钮`（窗口关闭，里面的按钮随之销毁）。

> 💡 **提示：** 聚合和组合在 **Java 语法层面完全一样**（都是成员变量），区别只体现在**谁创建、谁销毁、能否共享**这三个设计决策上，是纯语义层面的区分。

### 5. 泛化（Generalization）—— is-a，即继承

**概念**：特殊与一般的关系，子类是父类的一种特例。Java 中用 `extends` 实现，也就是我们熟悉的**继承**。

**代码体现**：

```java
public class Animal {
    public void eat() {
        System.out.println("吃东西");
    }
}

// Dog is-a Animal：狗是一种动物
public class Dog extends Animal {
    @Override
    public void eat() {
        System.out.println("狗啃骨头");
    }

    public void bark() {
        System.out.println("汪汪");
    }
}
```

**UML 表示**：**实线 + 空心三角箭头**，箭头指向父类。

```
┌──────┐                  ┌───────┐
│ Dog  │──────────────────▷│ Animal│
└──────┘  泛化（继承）      └───────┘
 （子类）                    （父类）
```

**典型场景**：模板方法、框架的 `BaseActivity`/`BaseController` 式基类、`ArrayList extends AbstractList`。

### 6. 实现（Realization）—— 能做什么，即实现接口

**概念**：类与接口的关系——类承诺实现接口规定的全部行为。本质也是一种 is-a（"我是一种能飞的动物"），但归类的依据是**能力契约**而非物种血缘。

**代码体现**：

```java
public interface Flyable {
    void fly();
}

// Bird 能飞，实现了 Flyable 契约
public class Bird implements Flyable {
    @Override
    public void fly() {
        System.out.println("扑翅膀飞");
    }
}

// 一架飞机也能飞——血缘完全不同，但能力相同，这正是接口的价值
public class Airplane implements Flyable {
    @Override
    public void fly() {
        System.out.println("喷气飞行");
    }
}
```

**UML 表示**：**虚线 + 空心三角箭头**，箭头指向接口。

```
┌──────┐                  ┌────────┐
│ Bird │- - - - - - - - -▷│ Flyable│
└──────┘  实现            └────────┘
  （类）                   （接口）
```

**典型场景**：`Comparable` / `Runnable` 等标准接口、策略模式的抽象、回调机制、依赖注入面向接口编程。

> 💡 **提示：** 泛化和实现的 UML 记法只差"线是实是虚"——**实线继承父类，虚线实现接口**。箭头都是空心三角，指向"被归类的一方"。

## 四、关系强弱与耦合度

六种关系按耦合度从弱到强排列：

```
依赖 ＜ 关联 ＜ 聚合 ＜ 组合 ＜ 泛化（继承）＝ 实现
```

**为什么耦合度越强越要谨慎？** 因为关系越强，两个类越"绑死"：

| 关系 | 改动影响 | 解耦手段 |
| :---: | :--- | :--- |
| 依赖 | 几乎无影响，改了工具类方法签名才需要跟着改 | 无需特别处理 |
| 关联 | 被持有类的结构变化会影响持有类 | 面向接口持有 |
| 聚合/组合 | 整体重构会牵连部分类 | 组合 + 接口 |
| 泛化/实现 | 子类依赖父类实现细节，父类一改子类可能崩 | **优先用组合替代继承** |

### ⭐ 重点关注：优先使用组合而不是继承

这是《Effective Java》第 18 条（*Favor composition over inheritance*）和 GoF《设计模式》开篇共同强调的原则。继承的两大坑：

1. **破坏封装**：子类依赖父类的实现细节（父类内部哪些方法互相调用通常没有文档），父类版本升级，子类可能在"谁都没改"的情况下悄悄出 bug。
2. **脆弱基类问题**：经典例子——想统计一个 `HashSet` 被添加过几次元素：

```java
// ❌ 错误示范：继承实现计数功能
public class CountingSet<E> extends HashSet<E> {
    private int count = 0;

    @Override
    public boolean add(E e) {
        count++;
        return super.add(e);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        count += c.size();
        return super.addAll(c);  // ❌ 坑在这里：HashSet.addAll() 内部会调用 add()
    }

    public int getCount() {
        return count;
    }
}

CountingSet<String> set = new CountingSet<>();
set.addAll(List.of("a", "b", "c"));
System.out.println(set.getCount());  // 期望 3，实际输出 6（addAll + 逐个 add 各计了一次）
```

```java
// ✅ 正确示范：用组合（包装类）实现同样功能
public class CountingSet<E> {
    private int count = 0;
    // 不继承，而是把 HashSet 作为成员变量持有（组合）
    private final HashSet<E> set = new HashSet<>();

    public boolean add(E e) {
        count++;
        return set.add(e);
    }

    public boolean addAll(Collection<? extends E> c) {
        count += c.size();
        return set.addAll(c);  // ✅ 只调用一次，计数正确
    }

    public int getCount() {
        return count;
    }
}

CountingSet<String> set = new CountingSet<>();
set.addAll(List.of("a", "b", "c"));
System.out.println(set.getCount());  // ✅ 输出 3
```

这正是 `java.io` 中 `BufferedInputStream` 包装 `InputStream` 的思路（**装饰器模式**）。当然，继承并非不能用——存在**稳定、真正的 is-a 关系**时（如 `Dog is-a Animal`），继承依然是自然选择。

> 📖 延伸阅读：[Refactoring.Guru - 设计模式](https://refactoring.guru/zh/design-patterns)（见「组合复用原则」「装饰器模式」相关章节）

## 五、实际应用场景

### 场景一：电商订单建模（关联 + 多重性）

```java
// 用户与订单：一对多关联
public class User {
    private Long id;
    private String name;
    private List<Order> orders = new ArrayList<>();  // 关联：一个用户多个订单

    public void addOrder(Order order) {
        orders.add(order);
        order.setUser(this);  // ⚠️ 双向关联要两边同步设置，漏一边会造成数据不一致
    }
}

public class Order {
    private Long id;
    private User user;           // 多对一关联
    private List<Item> items;    // 组合：订单明细离开订单无意义，随订单创建和销毁

    // 依赖：支付动作执行时才用到支付服务，用完即走，Order 不持有它
    public void pay(PaymentService service) {
        service.pay(this);
    }
}
```

### 场景二：框架中的基类抽取（泛化）

Spring MVC 中自定义控制器时复用公共逻辑：

```java
// 公共逻辑上移到基类（泛化）
public abstract class BaseController {
    protected User currentUser() {
        // 统一从 ThreadLocal / 上下文中取当前登录用户
        return UserContext.get();
    }
}

public class OrderController extends BaseController {
    public Result detail(Long id) {
        User user = currentUser();  // 子类直接复用基类能力
        return Result.ok(orderService.detail(user, id));
    }
}
```

### 场景三：策略模式——面向接口编程（实现 + 关联）

```java
// 定义排序策略契约（实现）
public interface SortStrategy {
    void sort(int[] arr);
}

public class QuickSort implements SortStrategy {
    @Override
    public void sort(int[] arr) { /* 快速排序 */ }
}

public class BubbleSort implements SortStrategy {
    @Override
    public void sort(int[] arr) { /* 冒泡排序 */ }
}

// 上下文通过接口持有策略（关联），而不是持有具体类 —— 关系从"泛化依赖"降为"接口关联"
public class Sorter {
    private SortStrategy strategy;  // ✅ 面向接口持有，可随时替换实现

    public Sorter(SortStrategy strategy) {
        this.strategy = strategy;
    }

    public void sort(int[] arr) {
        strategy.sort(arr);
    }
}
```

### 场景四：依赖注入容器（依赖/关联的解耦）

Spring 的核心思想就是**把关联对象的创建权移交出去**：

```java
@Service
public class OrderService {
    // ❌ 传统写法：自己 new，强耦合，难以测试
    // private OrderRepository repo = new OrderRepository();

    // ✅ 依赖注入：OrderService 只声明"我需要一个 OrderRepository"（关联关系），
    // 具体创建和装配交给 Spring 容器
    private final OrderRepository repo;

    public OrderService(OrderRepository repo) {  // 构造器注入
        this.repo = repo;
    }
}
```

### 场景五：图形界面组件树（组合）

```java
public class Window {
    // 组合：窗口持有它内部的所有面板，窗口关闭，面板随之销毁
    private List<Panel> panels = new ArrayList<>();

    public Panel createPanel() {
        Panel panel = new Panel();  // 由整体（Window）创建部分（Panel）
        panels.add(panel);
        return panel;
    }
}
```

## 六、UML 记法速查表

| 关系 | 线型 | 箭头/菱形 | 指向 | ASCII 示意 |
| :---: | :---: | :---: | :---: | :--- |
| 依赖 | 虚线 | 开放箭头 | 被使用的类 | `A - - -▶ B` |
| 关联 | 实线 | 开放箭头（双向可省略） | 被持有的类 | `A ──▶ B` |
| 聚合 | 实线 | **空心菱形 ◇** | 菱形在**整体**端 | `A ◇── B` |
| 组合 | 实线 | **实心菱形 ◆** | 菱形在**整体**端 | `A ◆── B` |
| 泛化 | 实线 | 空心三角 ▷ | 父类 | `A ────▷ B` |
| 实现 | 虚线 | 空心三角 ▷ | 接口 | `A - - -▷ B` |

> ⚠️ **注意：** 聚合/组合的菱形**永远画在"整体"那一端**。读图时容易顺着菱形方向读反——`部门 ◇── 员工` 应读作"**部门**拥有员工"，而不是"员工拥有部门"。

## 七、常见问题与注意事项

### 1. 聚合 vs 组合：语法一样，看语义

| 对比项 | 聚合 Aggregation | 组合 Composition |
| :---: | :--- | :--- |
| 关系强度 | 弱拥有 | 强拥有 |
| 部分能否独立存在 | ✅ 能（员工离开部门还能活） | ❌ 不能（心脏离开人体即死） |
| 部分由谁创建 | 外部创建后注入 | 整体自己创建 |
| 部分能否被多个整体共享 | ✅ 可以 | ❌ 一个部分只属于一个整体 |
| 整体销毁时 | 部分继续存在 | 部分随之销毁 |
| UML 记法 | 空心菱形 ◇ | 实心菱形 ◆ |

**判断技巧**：问一句"整体没了，部分还能去别处吗？"——能，聚合；不能，组合。

> 💡 **提示：** UML 2.5.1 规范中聚合的语义本就偏"软"（规范承认部分语义留给建模者解释），所以实际工作中不必纠结教科书式答案：能明确生命周期绑定的标组合，其余标聚合甚至关联即可，**关键是设计上想清楚谁创建、谁销毁**。

### 2. 依赖 vs 关联：只看引用存在多久

```java
// 依赖：引用活不过一次方法调用
public void drive(Car car) { car.run(); }

// 关联：引用跟着对象活
private Car myCar;  // 成员变量，一直都在
```

### 3. 双向关联的三个坑

```java
public class User {
    private List<Order> orders = new ArrayList<>();

    public void addOrder(Order order) {
        this.orders.add(order);
        order.setUser(this);  // ✅ 必须反向设置，否则 order.getUser() 为 null
    }
}
```

- **忘记同步**：只设置一边，另一半引用是 `null`，运行期才发现。
- **内存泄漏**：两个对象互相强引用，理论上有延迟回收风险（Java 的 GC 可处理循环引用，但 Android 等场景、以及监听器模式下的双向引用是真实的泄漏高发区）。
- **序列化死循环**：双向关联的类直接做 JSON 序列化会无限递归（如 Jackson 抛出 `StackOverflowError`），需用 `@JsonIgnore`、`@JsonManagedReference` / `@JsonBackReference` 或改单向解决。

### 4. 继承不是万能的复用手段

- 复用代码 ≠ 继承。只有满足 **is-a** 且父类**为扩展而设计**时才用继承；否则用组合/委托。
- Java 只有单继承，继承链太深（超过 2~3 层）会让"改一个方法影响谁"变得难以推理。
- 接口可以多实现，配合**面向接口持有引用**，能把耦合降到"只依赖契约"。

### 5. 设计上的实用准则

1. **能用依赖就不用关联**：临时借用胜过长期持有，耦合最低。
2. **持有引用优先面向接口**：`private SortStrategy strategy;` 优于 `private QuickSort sort;`。
3. **组合优于继承**（Effective Java 第 18 条）：拿不准时选组合。
4. **聚合/组合要明确生命周期归属**：谁创建、谁销毁、能否共享，写代码前想清楚，不要让部分对象"来路不明"。
5. **双向关联是权衡的结果**：能单向就单向；确实需要双向，封装好同步逻辑（如上面的 `addOrder`），不要让调用方自己维护两边。

## 八、总结

| 视角 | 关系 | 关键词 | 判断方法 |
| :---: | :---: | :---: | :--- |
| 使用 | 依赖 | use-a、临时 | 只在方法参数/局部变量中出现 |
| 拥有 | 关联 | has-a、长期 | 成员变量持有引用 |
| 拥有 | 聚合 | 整体-部分、可分离 | 外部注入、可共享、可独立存活 |
| 拥有 | 组合 | 整体-部分、同生共死 | 内部创建、独占、随之销毁 |
| 归类 | 泛化 | is-a、extends | 实线空心三角指向父类 |
| 归类 | 实现 | is-a、implements | 虚线空心三角指向接口 |

一句话收尾：**类的关系描述的是"耦合的方式与强度"**——依赖最松，组合与继承最紧。写代码时从弱关系开始考虑，能不加强就不加强；看代码时从成员变量和方法签名入手，先把"有没有、活多久"判断清楚，六种关系自然水落石出。
