# 浏览器性能监测

> 如何量化网页"快不快"、如何用代码采集真实用户的性能数据、如何用工具定位慢的原因——以及监测之后如何对症优化。

> 📖 官方文档：
> - [MDN：Performance API](https://developer.mozilla.org/zh-CN/docs/Web/API/Performance_API)
> - [MDN：PerformanceObserver](https://developer.mozilla.org/zh-CN/docs/Web/API/PerformanceObserver)
> - [web.dev：Web Vitals（指标定义与阈值）](https://web.dev/articles/vitals)
> - [GitHub：web-vitals 库](https://github.com/GoogleChrome/web-vitals)

### 一、监测什么、在哪测

性能监测回答两个问题："**慢不慢**"靠指标衡量，"**为什么慢**"靠工具排查。先认识评判标准——Google 提出的 Core Web Vitals（核心网页指标）：

| 指标 | 全称 | 通俗含义 | 良好 | 差 |
| ---- | ---- | ---- | ---- | ---- |
| LCP | Largest Contentful Paint（最大内容绘制） | 用户看到"主要内容大块头"的时刻 | ≤ 2.5s | > 4s |
| INP | Interaction to Next Paint（交互到下一帧） | 点一下到画面真正响应的延迟 | ≤ 200ms | > 500ms |
| CLS | Cumulative Layout Shift（累积布局偏移） | 页面内容"乱跳"的严重程度 | ≤ 0.1 | > 0.25 |

> 注：阈值来自 web.dev 的通行评估口径，按真实用户数据的 **75 分位**衡量；INP 于 2024 年 3 月取代了更早的 FID（只测输入延迟，不含处理与渲染）。

辅助指标：

| 指标 | 含义 | 参考值 |
| ---- | ---- | ---- |
| FCP（首次内容绘制） | 第一块真实内容（文字/图片）画出来的时刻 | ≤ 1.8s |
| TTFB（首字节时间） | 发出请求到收到响应第一个字节 | ≤ 0.8s |
| Long Task（长任务） | 主线程上超过 50ms 的任务 | 越少越好 |
| TBT（总阻塞时间） | 实验室指标：长任务中超出 50ms 部分的总和 | 越小越好 |

监测有两个互补的视角：

| 视角 | 工具 | 回答的问题 |
| ---- | ---- | ---- |
| 实验室（Lab） | DevTools、Lighthouse、PageSpeed Insights | 可控环境下"为什么慢"，可复现 |
| 真实用户（RUM） | Performance API 上报、web-vitals 库 | 真实设备与网络上"到底有多慢" |

> 💡 **提示：** 只看 Lighthouse 分数会失真——它跑在你的开发机上，不代表用户的千元机 + 弱网。正确姿势：RUM 发现"慢"，Lab 解释"为什么慢"。

### 二、Performance API 总览

浏览器把加载、绘制、交互的每个环节都自动记录成**性能条目**（Performance Entry），JavaScript 可以随时读取或监听。这是所有前端性能采集的底层能力。

两种读取方式：

```js
// 一次性读取：拿当前已记录的所有条目
performance.getEntriesByType('navigation');

// 持续监听（推荐）：新条目产生即回调
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log(entry.name, entry.startTime, entry.duration);
  }
}).observe({ type: 'paint', buffered: true }); // buffered: true 会补发监听建立前已产生的条目
```

常用 entryType 一览：

| entryType | 记录什么 | 读取方式 |
| ---- | ---- | ---- |
| `navigation` | 文档加载全过程时间线 | `getEntriesByType` |
| `resource` | 每个资源的耗时与体积 | `getEntriesByType` |
| `paint` | 首次绘制 / 首次内容绘制 | `getEntriesByType` |
| `largest-contentful-paint` | LCP 候选元素（随渲染更新） | PerformanceObserver |
| `event` | 交互事件耗时（INP 数据源） | PerformanceObserver |
| `layout-shift` | 布局偏移（CLS 数据源） | PerformanceObserver |
| `longtask` | 超过 50ms 的长任务 | PerformanceObserver |
| `mark` / `measure` | 自己打的性能点 | `getEntriesByName` |

> ⚠️ **注意：** `navigation` / `resource` / `paint` 支持最广；`largest-contentful-paint`、`layout-shift`、`longtask` 目前主要在 Chromium 系浏览器完整支持（部分仍标注为实验性），生产采集要容忍"部分用户采不到"的情况——这也是推荐生产环境用 web-vitals 库的原因之一。

> 💡 **提示：** 跨域资源的精细耗时默认拿不到（字段多为 0），需要资源服务端返回 `Timing-Allow-Origin` 响应头才可见。

### 三、具体实现：加载与绘制指标

加载指标回答"**网络和解析花了多久**"，数据源是 `navigation`、`resource`、`paint` 三类条目。

#### 1. 文档加载时间线：Navigation Timing

```js
const nav = performance.getEntriesByType('navigation')[0];

// navigation 条目的 startTime 恒为 0，各字段都是从导航开始的绝对毫秒数
console.log('TTFB（首字节）', nav.responseStart);
console.log('DNS 解析', nav.domainLookupEnd - nav.domainLookupStart);
console.log('TCP/TLS 建连', nav.connectEnd - nav.connectStart);
console.log('内容下载', nav.responseEnd - nav.responseStart);
console.log('DOM 解析完成', nav.domInteractive);
console.log('DOMContentLoaded 结束', nav.domContentLoadedEventEnd);
console.log('整页加载完成', nav.loadEventEnd);
```

| 字段 | 含义 |
| ---- | ---- |
| `responseStart` | 收到首字节，即 TTFB |
| `responseEnd` | 响应下载完成 |
| `domInteractive` | DOM 解析完成、可以开始交互 |
| `domContentLoadedEventEnd` | DCL 事件处理完成 |
| `loadEventEnd` | load 事件处理完成（整页加载完毕） |

> ⚠️ **注意：** 在 load 事件触发之前读取 `loadEventEnd` 会拿到 0——要等 `window` 的 load 事件后再读。

#### 2. 资源耗时与缓存命中：Resource Timing

```js
performance.getEntriesByType('resource')
  .filter((r) => r.initiatorType === 'script' || r.initiatorType === 'link')
  .forEach((r) => {
    console.log(r.name, `${Math.round(r.duration)}ms`);
    // 同域资源 transferSize 为 0 且 decodedBodySize 大于 0 → 命中缓存
    console.log('缓存命中：', r.transferSize === 0 && r.decodedBodySize > 0);
  });
```

`initiatorType` 表示资源由什么发起：`script`（JS 请求的）、`link`（样式表等）、`img`、`css`（CSS 里的资源）、`xmlhttprequest` / `fetch` 等。

> ⚠️ **注意：** 上一节的跨域限制在这里同样适用——跨域且无 `Timing-Allow-Origin` 时，`duration` 有值但 `transferSize` 等体积字段为 0，此时"为 0"不能当作缓存命中的判断依据。

#### 3. 绘制指标：Paint Timing 与 LCP

```js
// FCP：一次性读取
performance.getEntriesByType('paint').forEach((p) => {
  console.log(p.name, Math.round(p.startTime) + 'ms'); // first-paint / first-contentful-paint
});

// LCP：监听候选元素，LCP 会随渲染不断更新，通常取最后一个
let lcp = 0;
new PerformanceObserver((list) => {
  const entries = list.getEntries();
  lcp = entries[entries.length - 1].startTime;
}).observe({ type: 'largest-contentful-paint', buffered: true });
```

LCP 元素通常是首屏的大图或大标题块。浏览器在每次渲染后都会重新评估"最大的内容是谁"，所以条目会有多个——取**最后一个**；用户首次交互或页面隐藏后，LCP 正式定值。

### 四、具体实现：交互与稳定性指标

交互与稳定性指标回答"**用起来卡不卡、内容跳不跳**"，三个 Observer 对应三个 Core Web Vitals 的数据源。

#### 1. 交互延迟：Event Timing（INP 数据源）

```js
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    // duration：从事件发生到下一次画面更新的总时长
    if (entry.duration > 200) {
      console.log('慢交互', entry.name, Math.round(entry.duration) + 'ms', entry.interactionId);
    }
  }
}).observe({ type: 'event', durationThreshold: 16, buffered: true });
```

要点：

- `durationThreshold` 最小值是 16（毫秒），低于阈值的事件不上报
- `interactionId` 标识"同一次交互"——一次点击可能触发多个事件，取其中最大的 `duration` 作为该次交互的耗时
- 官方 INP 取整个页面生命周期中**最差的那次交互**（统计时用高分位剔除极端离群值），滚动和缩放不计入
- 上面的简化版适合开发期粗测，生产环境的精确 INP 交给 web-vitals 库

#### 2. 布局偏移：Layout Shift（CLS 数据源）

```js
let cls = 0;
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    // 用户输入后短时间内的偏移不计入（用户自己触发的变化不算"意外跳动"）
    if (!entry.hadRecentInput) cls += entry.value;
  }
}).observe({ type: 'layout-shift', buffered: true });
```

- `entry.value` 是单次偏移得分：视口内**可见内容移动的比例 × 移动距离的比例**
- 官方 CLS 按"会话窗口"聚合：偏移间隔超过 1 秒就切分新窗口、单窗口最长 5 秒，取**最大窗口**的累加值。上面的简单累加在"多段小偏移"场景会比官方值偏大，开发粗测够用

#### 3. 长任务：Long Task

```js
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    // 所有超过 50ms 的主线程任务——INP 差和掉帧的最大根源
    console.log('长任务', Math.round(entry.duration) + 'ms', entry.name);
  }
}).observe({ type: 'longtask', buffered: true });
```

> 💡 **提示：** 长任务数量和 INP 强相关：监测到长任务多，几乎必然交互卡。排查时优先看它。

### 五、生产接入：埋点、上报与 web-vitals

采集到数据后要"打点、上报、建看板"，生产环境还要处理 SPA 场景、兼容性和采样。

#### 1. 自定义埋点：mark 与 measure

SPA 的路由切换、弹窗打开没有现成条目，用 `performance.mark` 打点、`performance.measure` 量区间：

```js
performance.mark('route-start');
// ……路由组件渲染完成后……
performance.mark('route-end');
performance.measure('route-switch', 'route-start', 'route-end'); // 区间 = end - start

const [m] = performance.getEntriesByName('route-switch', 'measure');
console.log('路由切换耗时', Math.round(m.duration) + 'ms');
```

Vue Router 全局接入示例：

```js
router.beforeEach(() => performance.mark('route-start'));
router.afterEach(() => {
  performance.mark('route-end');
  performance.measure('route-switch', 'route-start', 'route-end');
});
```

#### 2. 上报：sendBeacon 与 visibilitychange

```js
function report(data) {
  navigator.sendBeacon('/api/perf', JSON.stringify(data));
}

// 在页面即将不可见时上报——这是最可靠的时机
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') {
    report(collectedMetrics);
  }
});
```

`sendBeacon` 专为"页面要关了也要把数据发出去"设计：不阻塞页面关闭，浏览器保证尽量送达。

> ⚠️ **注意：** 别在 `unload` 事件里用 XHR 上报——不可靠且会拖慢页面离开；`sendBeacon` 的载荷也有大小上限，超限会被丢弃，别把大批数据塞进一次调用。

#### 3. 生产标准：web-vitals 库

手写简化版够开发用；生产环境直接用 Google 官方的 web-vitals 库（`npm install web-vitals`），它处理了 LCP 定值时机、CLS 会话窗口、INP 交互分组等所有细节：

```js
import { onCLS, onINP, onLCP, onFCP, onTTFB } from 'web-vitals';

const report = (metric) => {
  navigator.sendBeacon('/api/perf', JSON.stringify({
    name: metric.name, // 'CLS' | 'INP' | 'LCP' ...
    value: metric.value,
    id: metric.id,     // 同一次访问内标识该指标，用于去重
    page: location.pathname,
  }));
};

onCLS(report);
onINP(report);
onLCP(report);
onFCP(report);
onTTFB(report);
```

它还提供 **attribution 构建**（`import { onLCP } from 'web-vitals/attribution'`），在指标对象上附带归因信息——LCP 是哪个元素、最慢的交互是哪个事件处理器，定位问题一步到位。

> 💡 **提示：** 大流量站点按比例采样即可（比如 10%）；指标超阈值或报错时全量上报，避免淹没在数据里。

### 六、DevTools 与 Lighthouse：实验室排查

RUM 告诉你"慢"，实验室工具告诉你"**为什么慢**"。

| 工具 | 用途 |
| ---- | ---- |
| Performance 面板 | 录制加载/交互过程，火焰图定位长任务、样式计算与布局耗时；布局偏移轨道可直接看到每次 CLS 的元凶 |
| Network 面板 | 资源瀑布图，按 TTFB 列排序找慢接口，查看请求优先级 |
| Lighthouse | 一键跑分，输出 LCP / CLS / TBT 等得分与"机会点"清单 |
| PageSpeed Insights | 线上版 Lighthouse，同时展示实验室分与真实用户分（CrUX 数据） |

Performance 面板使用要点：

- 先用内置的 **CPU 降速 + Fast 3G 网络节流**再录制，模拟真实用户环境
- 底部切换到 **Bottom-Up** 视图，按 Self Time 排序找最耗时的函数
- 长任务会带红色标记，点开看调用栈；`Layout Shifts` 轨道列出每次偏移及引发偏移的元素

### 七、如何优化：按指标对症下药

监测的价值在于**知道哪个指标差、差在哪**，然后按指标对症下药。

| 指标 | 典型病因 | 优化手段 |
| ---- | ---- | ---- |
| TTFB 慢 | 服务器慢、无缓存 | CDN、边缘缓存、SSR / 预渲染、HTTP 缓存 |
| LCP 慢 | 阻塞资源、关键资源发现晚 | 脚本 defer、关键 CSS 内联、preload LCP 图片、压缩图片 |
| INP 差 | 长任务、布局抖动、DOM 过大 | 拆长任务、读写分离、虚拟列表、防抖节流 |
| CLS 大 | 尺寸未预留、字体替换、动态插入 | 声明宽高、字体治理、骨架屏、transform 动画 |

#### 1. 优化 LCP：让主要内容早点画出来

```html
<!-- 预加载并提升 LCP 图片优先级 -->
<link rel="preload" as="image" href="/hero.webp" fetchpriority="high">
```

- 加载侧：LCP 图片用 `preload` + `fetchpriority="high"`；**首屏大图不要加 `loading="lazy"`**（懒加载会让 LCP 变晚）
- 渲染侧：CSSOM 就绪前浏览器不绘制任何内容，所以同步脚本和阻塞渲染的样式表都会直接拖慢 LCP——用 `defer`、关键 CSS 内联、其余 CSS 异步加载
- 服务侧：TTFB 快了 LCP 才有下限

#### 2. 优化 INP：让主线程别堵

```js
// ❌ 一次处理 1 万条数据，主线程卡死几百毫秒，期间所有点击都没响应
items.forEach(process);

// ✅ 分批处理，每批之间让主线程喘口气
function processInChunks(list, size = 100) {
  let i = 0;
  (function next() {
    list.slice(i, i + size).forEach(process);
    i += size;
    if (i < list.length) setTimeout(next); // 让出主线程，事件得以插队处理
  })();
}
```

其他手段：读写分离消除布局抖动（先批量读布局、再批量写样式）；长列表虚拟化；纯计算挪进 Web Worker；事件回调里避免同步等待网络。

#### 3. 优化 CLS：给所有"会动的东西"预留位置

```html
<!-- 图片、视频、iframe 都声明尺寸：加载前后布局完全一致 -->
<img src="hero.webp" width="1200" height="600" alt="首页大图">
```

```css
.ad-slot {
  min-height: 250px; /* 广告位等动态内容预留空间，返回后再填充 */
}
```

- 字体替换造成位移：`font-display: swap` 会先显示后备字体再替换——用 `size-adjust` 微调后备字体的尺寸度量使其占位一致，并 `preload` 字体缩短替换窗口
- 动态通知条不要插在已有内容上方，用 `transform` 弹出动画代替改变布局
- 动画只用 `transform` / `opacity`，别碰 `top` / `left` 等布局属性

### 八、总结

指标速查表：

| 指标 | 数据源 API | 良好阈值 | 优化关键词 |
| ---- | ---- | ---- | ---- |
| LCP | `largest-contentful-paint` | ≤ 2.5s | preload、关键 CSS、TTFB |
| INP | `event` | ≤ 200ms | 拆长任务、读写分离 |
| CLS | `layout-shift` | ≤ 0.1 | 尺寸预留、字体治理 |
| FCP | `paint` | ≤ 1.8s | 同 LCP |
| TTFB | `navigation` | ≤ 0.8s | CDN、缓存、SSR |

核心原则（每条一句话）：

1. 先 RUM 发现"慢"，再用 Lab 解释"为什么慢"，只看 Lighthouse 分数会失真
2. 生产采集用 web-vitals 库；手写 PerformanceObserver 用于开发粗测和自定义指标
3. 优化按指标对症：LCP 看资源加载，INP 看主线程占用，CLS 看尺寸预留
4. 上报用 `sendBeacon` + `visibilitychange`，大流量记得采样
