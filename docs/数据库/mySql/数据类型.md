# MySQL 数据类型详解

> 官方文档：[MySQL 8.0 Reference Manual - Data Types](https://dev.mysql.com/doc/refman/8.0/en/data-types.html)

MySQL 的数据类型决定了列能存储什么数据、占用多少存储空间以及如何参与运算。选择合适的数据类型，是数据库设计的基础，直接影响**存储空间、查询性能、数据完整性**。

## 总览

MySQL 数据类型分为四大类：

| 大类 | 包含类型 | 典型用途 |
| --- | --- | --- |
| 数值类型 | 整数、浮点、定点、BIT | 存储数字，参与运算 |
| 字符串类型 | CHAR、VARCHAR、TEXT、BLOB、ENUM、SET | 存储文本、二进制、枚举 |
| 日期时间类型 | DATE、TIME、DATETIME、TIMESTAMP、YEAR | 存储时间 |
| JSON 类型 | JSON | 存储半结构化数据 |

---

## 一、数值类型

### 1.1 整数类型

> 官方文档：[Integer Types](https://dev.mysql.com/doc/refman/8.0/en/integer-types.html)

| 类型 | 字节数 | 有符号范围 | 无符号范围（UNSIGNED） |
| --- | --- | --- | --- |
| TINYINT | 1 | -128 ~ 127 | 0 ~ 255 |
| SMALLINT | 2 | -32768 ~ 32767 | 0 ~ 65535 |
| MEDIUMINT | 3 | 约 -838万 ~ 838万 | 0 ~ 约 1677万 |
| INT / INTEGER | 4 | 约 -21亿 ~ 21亿 | 0 ~ 约 42.9亿 |
| BIGINT | 8 | 约 ±922 京（9.22×10^18） | 0 ~ 约 1.8×10^19 |

**具体描述：**

- 都是精确整数，不涉及小数与精度问题。
- 显示宽度：如 `INT(5)` 中的 `5` 只是显示宽度（配合 `ZEROFILL` 补零使用），**不影响存储范围**。MySQL 8.0.17 起已弃用显示宽度，不建议使用。
- `UNSIGNED` 表示无符号，范围翻倍但不能存负数。

**作用：** 存储整数值，占用空间固定、运算效率高、可作为主键。

**使用场景：**

| 类型 | 场景 |
| --- | --- |
| TINYINT | 状态标志（0/1）、性别、年龄、开关字段 |
| SMALLINT | 小范围计数、端口（0~65535） |
| MEDIUMINT | 中等规模计数 |
| INT | 通用整数：订单号、数量、普通表主键 |
| BIGINT | 大数据量主键（自增 ID）、雪花算法 ID、金额（以"分"存储）、时间戳 |

```sql
CREATE TABLE `user` (
  id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY, -- 大表主键
  age         TINYINT UNSIGNED,        -- 0~255 足够
  status      TINYINT NOT NULL DEFAULT 1, -- 1 启用 / 0 禁用
  points      INT UNSIGNED DEFAULT 0
);
```

> 💡 **实践建议**：主键自增 ID 建议用 `BIGINT UNSIGNED`，避免表数据量增长后溢出。

---

### 1.2 定点数类型（精确小数）

> 官方文档：[Fixed-Point Types (Exact Value)](https://dev.mysql.com/doc/refman/8.0/en/fixed-point-types.html)

**类型：** `DECIMAL(M, D)`（别名 `NUMERIC`）

**具体描述：**

- `M` 是总精度（有效数字位数，最大 65），`D` 是小数位数（最大 30），如 `DECIMAL(10,2)` 表示最多 10 位数字，其中 2 位小数。
- 以**字符串形式存储**，是精确值，不存在浮点误差。
- 存储空间约为每 9 位数字占 4 字节。

**作用：** 精确存储小数，保证运算（尤其是金额计算）无精度丢失。

**使用场景：**

- 💰 **金额、价格**（如 `DECIMAL(10,2)`：最大 99999999.99）
- 汇率、利率、税率等对精度敏感的数值
- 科学计算中要求精确结果的场景

```sql
CREATE TABLE `order` (
  id     BIGINT PRIMARY KEY,
  amount DECIMAL(10,2) NOT NULL DEFAULT 0.00  -- 金额必须用 DECIMAL
);
```

> ⚠️ **切忌**用 FLOAT/DOUBLE 存金额，浮点误差会导致对账不平。

---

### 1.3 浮点数类型（近似小数）

> 官方文档：[Floating-Point Types (Approximate Value)](https://dev.mysql.com/doc/refman/8.0/en/floating-point-types.html)

**类型：**

| 类型 | 字节数 | 说明 |
| --- | --- | --- |
| FLOAT | 4 | 单精度，约 7 位有效数字 |
| DOUBLE | 8 | 双精度，约 16 位有效数字 |

**具体描述：**

- 采用 IEEE 754 标准存储，是**近似值**，可能存在精度误差（如 `0.1 + 0.2 != 0.3`）。
- 可以带 `(M, D)` 声明精度，但 MySQL 8.0.17 起已弃用该写法。

**作用：** 存储对精度要求不高、范围大或有小数的数值，占用空间小、运算快。

**使用场景：**

- 温度、湿度等传感器数据
- 百分比、评分等允许微小误差的数值
- 统计近似值、科学计算中间结果

```sql
CREATE TABLE sensor_log (
  temperature FLOAT,   -- 温度允许微小误差
  humidity    DOUBLE
);
```

---

### 1.4 BIT 类型

> 官方文档：[Bit Type](https://dev.mysql.com/doc/refman/8.0/en/bit-type.html)

**类型：** `BIT(M)`，M 为位数，1 ~ 64。

**具体描述：** 存储位字段值，如 `BIT(8)` 存储 8 个二进制位。查询时需用 `b'101'` 字面量或 `BIN()`/`HEX()` 函数转换，否则显示乱码。

**作用：** 用一个字段压缩存储多个布尔标志位。

**使用场景：** 权限标记、一组开关位。日常开发中更常用多个 TINYINT 字段或 `SET` 类型，可读性更好。

---

## 二、字符串类型

### 2.1 CHAR 定长字符串

> 官方文档：[The CHAR and VARCHAR Types](https://dev.mysql.com/doc/refman/8.0/en/char.html)

**类型：** `CHAR(M)`，M 为 0 ~ 255 的字符数。

**具体描述：**

- **定长**：无论实际存多少字符，始终占用 M 个字符的空间（不足右侧填充空格，取出时截断空格）。
- 存取速度稳定，无长度记录开销。

**作用：** 存储长度固定或近似固定的短字符串。

**使用场景：**

- 身份证号 `CHAR(18)`（18 位固定）
- MD5 哈希 `CHAR(32)`、SHA-1 `CHAR(40)`
- 国家代码 `CHAR(2)`（如 `CN`、`US`）、手机号、邮编

---

### 2.2 VARCHAR 变长字符串

**类型：** `VARCHAR(M)`，M 为 0 ~ 65535 的字符数（受行大小限制，UTF-8 下实际更小）。

**具体描述：**

- **变长**：按实际内容长度存储，额外用 1~2 字节记录长度。
- 长度 M 是**字符数**而非字节数，与字符集有关（utf8mb4 下一个字符最多 4 字节）。
- 最大行大小 65535 字节是所有列共享的。

**作用：** 存储长度不确定的短文本，是**最常用的字符串类型**。

**使用场景：**

- 用户名、昵称 `VARCHAR(50)`
- 邮箱 `VARCHAR(100)`、地址、标题、摘要
- 短配置信息

> 💡 **实践建议**：能预估最大长度就指定合理值，不要一律 `VARCHAR(255)`；MySQL 的索引长度限制（767/3072 字节）与列定义长度有关。

**CHAR 与 VARCHAR 对比：**

| 维度 | CHAR | VARCHAR |
| --- | --- | --- |
| 长度 | 固定 | 变长 |
| 空间 | 可能浪费 | 按需分配 |
| 尾随空格 | 取出时被删除 | 保留 |
| 适用 | 长度固定的值 | 长度不定的值 |

---

### 2.3 TEXT 大文本类型

> 官方文档：[The BLOB and TEXT Types](https://dev.mysql.com/doc/refman/8.0/en/blob.html)

**类型：**

| 类型 | 最大长度 | 说明 |
| --- | --- | --- |
| TINYTEXT | 255 字节 | 极短文本 |
| TEXT | 64 KB（65535 字节） | 普通文本 |
| MEDIUMTEXT | 16 MB | 中等文本 |
| LONGTEXT | 4 GB | 超大文本 |

**具体描述：**

- 存储非二进制大文本，按字符集编码。
- 不能直接指定常量默认值（8.0.13 起支持表达式默认值如 `DEFAULT ('')`）；实际数据可能存储在行外（溢出页），查询开销比 VARCHAR 大。
- 不能整列设为索引（需前缀索引）。

**作用：** 存储超长文本，突破 VARCHAR 的行大小限制。

**使用场景：**

| 类型 | 场景 |
| --- | --- |
| TEXT | 文章正文、评论内容、接口报文 |
| MEDIUMTEXT | 富文本/HTML 页面、JSON 字符串、日志详情 |
| LONGTEXT | 书籍章节、超长日志、序列化大对象 |

> 💡 **实践建议**：大 TEXT 字段建议拆分到单独的扩展表，避免拖慢主表查询；全文检索考虑 FULLTEXT 索引或搜索引擎（如 ES）。

---

### 2.4 BLOB 二进制大对象

**类型：** `TINYBLOB` / `BLOB`（64 KB）/ `MEDIUMBLOB`（16 MB）/ `LONGBLOB`（4 GB）。

**具体描述：** 与 TEXT 一一对应，但存储**二进制字节流**，不涉及字符集和排序规则。

**作用：** 在数据库中直接存储二进制数据。

**使用场景：** 小图片、文件附件、加密后的二进制数据。

> ⚠️ **实践建议**：生产环境一般不在数据库中存大文件（图片/视频），而是存对象存储（OSS/S3），数据库只存 URL。仅当文件极小且强事务一致时才考虑 BLOB。

---

### 2.5 ENUM 枚举类型

> 官方文档：[The ENUM Type](https://dev.mysql.com/doc/refman/8.0/en/enum.html)

**类型：** `ENUM('值1','值2',...)`，最多 65535 个成员。

**具体描述：**

- 内部以**整数索引**存储（1、2、3...），因此非常省空间（1~2 字节）。
- 只能取定义时的合法值之一，插入非法值时在严格模式下报错，非严格模式下存为空串。
- 排序按定义顺序而非字母顺序。

**作用：** 限定字段只能从一组固定值中取一个，天然的数据校验。

**使用场景：** 订单状态、支付方式、性别等取值固定的字段。

> ⚠️ **实践建议**：实际项目中更常用 **TINYINT + 代码层枚举/字典表**。ENUM 的缺点：新增取值需要 `ALTER TABLE`，且值与索引的对应关系在应用层不直观。

```sql
-- 两种写法对比
status ENUM('pending','paid','cancelled')   -- ENUM 写法
status TINYINT NOT NULL DEFAULT 0           -- 推荐：TINYINT + 字典
```

---

### 2.6 SET 集合类型

> 官方文档：[The SET Type](https://dev.mysql.com/doc/refman/8.0/en/set.html)

**类型：** `SET('a','b','c',...)`，最多 64 个成员。

**具体描述：**

- 可以存储 0 个或多个成员的**组合**，如 `SET('read','write')` 可存 `'read'`、`'read,write'`。
- 内部用位图（bitmap）存储，64 个成员占 8 字节。
- 查询用 `FIND_IN_SET()` 函数，无法高效使用普通索引。

**作用：** 一个字段存储多个布尔型选项的组合。

**使用场景：** 用户权限集合、多选标签、开通的功能模块。

```sql
CREATE TABLE account (
  perms SET('read','write','admin')
);
INSERT INTO account VALUES ('read,write');
SELECT * FROM account WHERE FIND_IN_SET('write', perms) > 0;
```

> ⚠️ 与 ENUM 类似，修改成员需要改表结构，实践中常用"关联表"或位运算的 TINYINT/BIGINT 替代。

## 三、日期时间类型

> 官方文档：[Date and Time Types](https://dev.mysql.com/doc/refman/8.0/en/date-and-time-types.html)

### 3.1 类型总览

| 类型 | 字节数 | 格式 | 范围 | 时区 |
| --- | --- | --- | --- | --- |
| DATE | 3 | `YYYY-MM-DD` | 1000-01-01 ~ 9999-12-31 | 无关 |
| TIME | 3 | `HH:MM:SS` | -838:59:59 ~ 838:59:59 | 无关 |
| DATETIME | 8 | `YYYY-MM-DD HH:MM:SS` | 1000-01-01 00:00:00 ~ 9999-12-31 23:59:59 | **无关** |
| TIMESTAMP | 4 | `YYYY-MM-DD HH:MM:SS` | **1970-01-01 00:00:01 UTC ~ 2038-01-19**（UTC） | **有关** |
| YEAR | 1 | `YYYY` | 1901 ~ 2155 | 无关 |

### 3.2 DATE 日期

**具体描述：** 只存日期，不存时间。插入 `2026-11-10` 格式的值。

**作用与场景：** 生日、纪念日、账单日期等只需日期的字段。

```sql
CREATE TABLE employee (
  birthday DATE
);
```

### 3.3 TIME 时间

**具体描述：** 存时间或时间跨度，支持负值，可带小数秒 `TIME(3)`。

**场景：** 会议时长、营业时间段（跨天如 `26:00:00`）、视频时长。

### 3.4 DATETIME 日期时间

**具体描述：**

- 同时存日期和时间，**与时区无关**——存进去什么，取出来就是什么。
- 范围大（1000 ~ 9999 年），占 8 字节；8.0.19 起支持 `2026-11-10 20:30:00+08:00` 带时区写法（会转换为当前时区存储）。

**作用与场景：** 业务时间记录的**默认首选**：下单时间、预约时间、活动开始/结束时间。

```sql
CREATE TABLE `order` (
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  pay_time   DATETIME NULL
);
```

### 3.5 TIMESTAMP 时间戳

**具体描述：**

- 内部存储 **UTC 时间戳**（4 字节整数），读写时按连接时区自动转换，天然支持多时区。
- 范围只到 **2038-01-19**（著名的 "2038 问题"）。
- 默认小数秒精度为 0（即精确到秒），最大可到微秒，如 `TIMESTAMP(6)`。

**作用与场景：**

- 记录行数据的创建/更新时间，如 `updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`。
- 需要跨时区展示的系统（全球化应用）。

> ⚠️ 由于 2038 问题，新项目建议**统一用 BIGINT（毫秒时间戳）或 DATETIME(3)**。

**DATETIME 与 TIMESTAMP 对比：**

| 维度 | DATETIME | TIMESTAMP |
| --- | --- | --- |
| 存储空间 | 8 字节 | 4 字节 |
| 范围 | 1000 ~ 9999 年 | 1970 ~ 2038 年 |
| 时区 | 无关，存原值 | 有关，存 UTC 自动转换 |
| 默认值 | 8.0 起 `CURRENT_TIMESTAMP` 可用 | 支持 `CURRENT_TIMESTAMP` |
| 适用 | 通用业务时间 | 跨时区 / 自动更新时间 |

### 3.6 YEAR 年份

**具体描述：** 1 字节存 4 位年份（1901 ~ 2155）。

**场景：** 毕业年份、车型年份等只关心年份的字段。使用频率低。

### 3.7 小数秒精度

所有时间类型都支持小数秒，如 `DATETIME(6)` 精确到微秒。场景：高并发去重、追踪事件先后顺序（如 `created_at DATETIME(6)`）。

## 四、JSON 类型

> 官方文档：[The JSON Data Type](https://dev.mysql.com/doc/refman/8.0/en/json.html)

**类型：** `JSON`（MySQL 5.7.8+）

**具体描述：**

- 存储前校验 JSON 格式合法性，非法 JSON 直接报错。
- 内部以**二进制格式**存储，读取无需重复解析，比存 TEXT 快。
- 提供丰富的函数：`JSON_EXTRACT()`、`->`、`->>`、`JSON_SET()`、`JSON_CONTAINS()` 等。
- 可以对 JSON 的某个键建**多值索引/虚拟列索引**（8.0 支持）。

**作用：** 存储结构不固定的半结构化数据，兼顾灵活性。

**使用场景：**

- 商品扩展属性（不同品类属性不同）
- 接口请求/响应报文记录
- 配置信息、用户偏好设置
- 无法预先确定字段的表单数据

```sql
CREATE TABLE product (
  id        BIGINT PRIMARY KEY,
  attrs     JSON
);
INSERT INTO product VALUES (1, '{"color": "red", "size": 42}');

-- 用生成列 + 索引优化 JSON 查询
ALTER TABLE product
  ADD COLUMN color VARCHAR(20)
      GENERATED ALWAYS AS (attrs->>'$.color') VIRTUAL,
  ADD INDEX idx_color(color);

SELECT * FROM product WHERE color = 'red';
```

> ⚠️ **实践建议**：JSON 适合"补充属性"，不适合作为主要查询条件的数据。核心业务字段仍应设计为普通列，不要把整张表塞进一个 JSON 字段。

## 五、选型速查与实践总结

### 5.1 常见字段选型参考

| 业务字段 | 推荐类型 | 说明 |
| --- | --- | --- |
| 主键 ID | BIGINT UNSIGNED | 防溢出 |
| 金额 | DECIMAL(12,2) 或 BIGINT（分） | 绝不用 FLOAT |
| 状态/类型 | TINYINT | 配合字典 |
| 用户名/昵称 | VARCHAR(50) | 按需定长 |
| 手机号 | CHAR(11) | 定长 |
| 密码哈希 | CHAR(60) | bcrypt |
| 邮箱 | VARCHAR(100) | |
| 文章内容 | MEDIUMTEXT | |
| 创建/更新时间 | DATETIME(3) 或 BIGINT 时间戳 | 避开 2038 问题 |
| 生日 | DATE | |
| 是否删除 | TINYINT(1)（is_deleted） | |

### 5.2 核心原则

1. **够用且留余量**：选能满足业务范围的最小类型，类型越小索引越快、占空间越少。
2. **精确优先**：金额用 DECIMAL，时间避开 TIMESTAMP 的 2038 限制。
3. **定长优先**：能用 CHAR 不用 VARCHAR，能用 VARCHAR 不用 TEXT。
4. **避免滥用**：慎用 ENUM/SET（改表成本高）、不要在库里存大文件。
5. **统一规范**：字符集统一 `utf8mb4`，排序规则统一 `utf8mb4_general_ci` 或 `utf8mb4_0900_ai_ci`。
